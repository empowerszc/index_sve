**术语与口径**（全文一致，避免同一个词两种意思）：

| 词 | 含义 |
|---|---|
| **下界（可达下界）** | 同机、同工作集、同线程数下，探针能跑出来的**最好合法写法**；英文 *lower bound*，旧稿写作"地板"。它不是厂商峰值 |
| **在飞条数** | 同时发出、还没返回的访存数量。"延迟 ÷ 在飞条数"就是单次成本 |
| **每线程口径** | 墙钟 ÷ 每线程处理的元素数（或行数）。唯一能跨线程数比较的单位 |
| **已兑现** | 现状提升 ÷ 可达上限提升（同形态、同线程数），即"理论空间吃到了几成" |
| **固定账** | 每调用一次的成本（入口 + fork-join + 输出 first-touch），与 K 无关 |
| **line 放大** | 一次访问只用 64B line 的一部分时，实际搬运量 ÷ 有用字节 |
| **推算** | 由实测数据代入模型得到的数，不是直接测量；误差按 ±50% 读 |
| **推断** | 由实测现象 + 硬件常识给出的**机理判断**，没有直接测量；文中会标"推断"，并写明用什么实验可以推翻它 |
| **依赖链访问** | 下一条访问的地址要靠上一条读回的数据。一次只能等一个，成本就是满延迟 |
| **MSHR** | miss status holding register：每核记录"哪些 line 正在路上"的硬件表；表满即在飞条数到顶 |
| **RFO** | read-for-ownership：写一部分 line 前需要先把整条 line 读进来；整行写可以跳过 |
| **IPC** | instructions per cycle：每拍退休的指令数，用来看"核在算还是在等" |
| **SVE** | ARM 可伸缩向量扩展；本机 512-bit = 一次 8×f64 或 16×f32 |
| **NUMA** | 多 die 机器上内存分节点；本文数据都在 node 5（`--membind=5`），跨节点会再慢几十 ns |
| **行（row）** | 一次 index 命中的一整段连续数据，含 A 个元素。"行拷贝"就是"取 K 行、每行 A 个"。 |
| **桶化（bucket）** | 值域很小（dom≤2048）时，先把值映射进一张小表，再按桶批量取：把"随机的大数组访问"变成"小表常驻 L1"。 |
| **两遍模型（linearize）** | 第一遍扫下标、把命中的行号写成紧凑数组，第二遍按它拷贝。省掉逐行检查，代价是多读一遍下标。 |
| **fork-join** | `parallel_for` 的起停成本：分活给线程、最后汇合。每次调用都要付一次。 |
| **first-touch** | 新分配的页在第一次写时才真正拿到物理内存。8MB 输出 = 2048 次缺页，这是固定账的主要来源。 |
| **D（预取距离）** | 提前几行发 `prfm`。`D=0` = 关掉预取；单位是行，字节数 = `D × 行字节`（§1.6、§3.2）。 |
| **环长** | 指针追逐用的随机置换里，从起点回到起点经过的元素数。它才是真正的"工作集"（§1.1）。 |
| **BDP** | 带宽延迟积 = 带宽 × 延迟，等于"要打满带宽，必须有多少数据在飞"。用它交叉验证在飞条数（§1.2）。 |
| **算术强度** | 做的浮点运算数 ÷ 搬运的字节数（flop/byte）。本算子 = 0（§2.6）。 |
| **机器平衡点** | roofline 两条天花板的交点：算术强度低于它 → 带宽瓶颈，高于它 → 算力瓶颈。本机 ≈0.07 flop/byte（§2.6）。 |
| **GFLOPS / TFLOPS** | 每秒十亿/万亿次浮点运算。只在算术强度越过平衡点时才是有意义的尺子（§2.6）。 |

把这张表压成一条阶梯，就是全文的骨架：

1. **硬件**：每核能同时挂 **16-20 条** line，所以一次随机访问的下界是
   `137ns ÷ 16 ≈ 8.6ns`。
2. **aten**：实测只有 **0.85-1.05 条**在飞，于是每行 132-155ns——它几乎完全
   站在第 1 步给出的下界上。
3. **本仓**：A=16 的行拷贝 1t 到 **5.7 条**在飞（24ns/行），是 aten 的 6.3x，但
   离 `8.6-11.4ns` 还有 2.1x。
4. **剩下的 2.1x 不在"搬数据"**：它同时受每行指令数（105 条）与每行检查/地址计算
   约束（§2.3、§5.1）。

**本轮最重要的修正**（上一版把它归错了）：三个生产模型最贵的那一格
（`bucket K13824/55296/256000`）**不是**"大值域 1D gather"，而是 `dom≤2048` 的
桶化——表 8KB 常驻 L1，**没有 DRAM 延迟可藏**。它们的对手是 L1 的 **2.0ns**
（§2.16.1 的 `chase` 实测），测出来的下界是每线程 **0.66-0.71 ns/元素**（§2.20）。
用 DRAM 的 5.65ns 下界去套，会把空间估大 8-9 倍。三格的真实差距分别是 41x / 23x / 6.5x（对 L1 下界），
但成因完全不同：**SGI 与 PPT 是固定成本+遍数，Sonata 是"一条在飞"**。
（注意这三个 41x/23x/6.5x 是**对裸探针下界**，不是可得空间；把实测的固定成本地板
算进去只有 1.8-2.4x，见 §6.5。这个区别是本文后半程最重要的一个口径。）

## 1. 硬件基线：一颗核能给多少

全部实测（§2.16/§2.17/§2.20）。凡"延迟"都指**依赖链**（下一条地址要靠上一条
数据），不是流水线里能重叠的那种访问——这一点决定了后面所有公式的分母。

### 1.0 从零开始：一次访存到底发生了什么（熟悉硬件的可跳过）

要理解后面所有数字，只需要先记住一件事：**CPU 取一个数，要花多久**。

现代 CPU 一个周期约 0.5ns（本机 2.0GHz），做一次加法就是这个量级。但数据不在 CPU
里，它在内存条上；从"CPU 说要这个地址"到"数据送回寄存器"，走的距离不同，成本能差
20-30 倍：

| 数据在哪 | 一次访问要多久 | 直观感受 |
|---|---|---|
| L1（32KB，紧挨着核） | **2.0ns** | 从桌上拿一张纸 |
| L2（768KB，同一颗核） | **7.4-8.6ns** | 走到隔壁房间拿 |
| 本地 DRAM（64GB，内存条） | **131-137ns** | 下楼去仓库取 |

后面所有的"16 倍加速""下界 8.6ns"都建立在这张表上：**如果一次访问必须等 137ns，
而一颗核能同时等 16 个，那么平均每个只要 8.6ns。** 这是本文唯一的核心公式。

三件必须知道的事：

1. **搬运的最小单位是 64B，叫一条 cache line**。哪怕只读 4 个字节，内存也会把这条
   64B 一起送过来。所以"有用带宽"和"实际搬运带宽"不是一回事（§2.2）。
2. **访问有两种形状**。第一种叫**依赖链**：下一条访问的地址要靠上一条读回来的数据
   才能算出来（指针追逐、链表、以及 `dst[k] = table[idx[k]]` 里"先读 idx 再读
   table"）。这种形状一次只能等一个，成本就是满延迟。第二种是**独立访问**：地址
   提前都算好，CPU 可以一次发十几个出去，成本摊薄成 `延迟 ÷ 在飞条数`。
   `aten::index` 的行循环是第一种；H1 预取与 H2 批量化都是在把它改成第二种。
3. **写一整条 line 可以不先读**。只改 line 的一部分时，CPU 得先把整条读进来（叫
   **RFO**，read-for-ownership），这是"写比读贵"的来源。A=16 恰好 64B = 一整条
   line，所以整行写不产生额外读：perf 的"L1 缺行/行 = 1.00"正好等于"只读源行"，
   这条一致性是 §2.19 那些归因能成立的前提。

> 这三个概念（line 大小、两种访问形状、写策略）后面会反复出现。任何"为什么快/
> 为什么慢"的结论，最后都能回溯到这三条。

#### 1.0.1 缓存长什么样：为什么"容量"不等于"能装下"

CPU 比内存快两个数量级，于是在中间放几块又小又快的 SRAM（静态内存，用触发器存 1 bit，
比内存的电容快、也贵得多），把**最近用过的 64B 块**留下来。这就是缓存。

三个参数决定它的行为：

- **容量**：L1 32KB、L2 768KB（本机）。
- **块大小**：64B，叫一条 **cache line**。这是搬运的最小单位，哪怕你只读 1 个字节。
- **相联度**：每个"组"里能放几条 line。本机 L1 是 8 路、L2 是 12 路。

一个地址被硬件切成三段（以 L2 为例）：

```
 63                    16 15        6 5      0
+------------------------+-----------+--------+
|        tag（标签）      | set（组号）| offset |
+------------------------+-----------+--------+
                         10 bit      6 bit
                      → 1024 个组   → line 内第几字节
```

- **offset（低 6 位）**：一条 line 有 64B，所以要 6 位来选"line 里第几个字节"。
- **set（中间 10 位）**：1024 个组，所以要 10 位。**同一个地址永远只能进同一个组**
  ——这是硬件为了省比较器做的取舍。
- **tag（剩余高位）**：进组之后，靠 tag 确认"这一路里装的确实是我要的那条 line"。

画成图，L2 就是 1024 排货架，每排 12 个格子：

```
组   0 : [way0][way1][way2] ... [way11]
组   1 : [way0][way1][way2] ... [way11]
 ...
组1023 : [way0][way1][way2] ... [way11]
```

为什么要"组"而不是"随便放"：全相联（任意位置都能放）要同时比较 12288 个 tag，电路
代价不可接受；直接映射（每组只 1 格）又太容易冲突。8/12 路是这两者之间的折中——
**"差不多够用，又便宜"**。

替换策略是 **LRU 的近似**（最近最少用过的先扔）。这两件事（定组 + 组内 LRU）合起来，
就是 §1.1 里"有效容量只有 512KB"的全部原因：**组数是固定的 1024，而随机足迹落进
每个组的条数是不均匀的**，总有些组先满、先开始往外扔。

#### 1.0.2 一次 miss 的完整路径，以及 MSHR 是什么

一次 load 在硬件里是这样走的：

```
核发 load
  ├─ 命中 L1 ──────────────────→ 2ns 返回
  └─ miss L1
       ├─ 申请一个 MSHR 表项（"我要这条 line，谁在等我"）
       ├─ 问 L2
       │    ├─ 命中 L2 ─────────→ 8.6ns 回来，填进 L1
       │    └─ miss L2
       │         └─ 问内存控制器 → DRAM 约 130ns → 回来填 L2、填 L1
       └─ 数据回来时，用 MSHR 里记的信息唤醒等它的指令
```

**MSHR**（miss status holding register，缺失状态保持寄存器）就是"未完成订单的记账
本"：每条已经发出、还没回来的 line 占一个表项。它有两个作用：

1. **让多条 miss 同时在飞**——这是"在飞条数"能到 16 的物理基础。
2. **去重**——同一秒内两个核/两条指令要同一条 line，只发一次请求。

表项用完（本机实测 16-20 条，§1.2），新的 miss 只能排队。**它由电路决定，代码改不了**
——所以本文所有"提高在飞条数"的手段，本质都是"别让 MSHR 空着"，而不是"把表变大"。

#### 1.0.3 写为什么比读贵：RFO 与非临时存储

写有两个额外的坑：

- **写命中**：直接改 L1 里的那条 line，把它标成 dirty（脏），**等到被替换时才写回
  内存**（write-back）。这样连续写同一行只付一次内存流量。
- **写 miss**：要先从内存把这条 line **读进来**，改完再写回。为什么不能直接写？因为
  你可能只改 4B，剩下 60B 必须保持原值，硬件没法凭空知道。这一步叫 **RFO**
  （read-for-ownership，"先把所有权拿过来"）。

A=16 的行正好 64B = 一整条 line，硬件能识别"整条覆盖写"，于是**不需要 RFO**。这就是
perf 里"L1 缺行/行 = 1.00"（只读源行、写不产生额外读）的由来，也是 §2.19 那些归因
能成立的前提。A=3（12B）就不行，它只占一条 line 的 1/5，剩下的部分还得读回来。

**非临时存储**（`stnt1d`）是给这种场景的逃生门：告诉硬件"这条 line 我以后再也不读了，
别占缓存、也别 RFO，直接送内存"。听起来很美，本机实测收益 **0**（29.1 vs 29.1 @1t，
§1.5）——因为写侧 RFO 本来就不是这里的瓶颈。这条是本文的负结果之一。

#### 1.0.4 DRAM 内部：bank / row / column，以及"随机为什么慢"

DRAM 的存储单元是电容（充了电 = 1），按三级寻址：**bank（存储体）→ row（行）→
column（列）**。读一个单元要做三步：

1. **ACT（激活）**：把整行（通常 1-2KB）从电容阵列搬进 **row buffer**（一排灵敏
   放大器）。这一步要几十 ns。
2. **CAS（读列）**：从 row buffer 里取出你要的那几个字节。很快。
3. **PRE（预充电）**：关掉这一行，准备下一行。

关键在于：**同一个 row 里的第二次访问几乎免费**（row buffer hit），**换 row 就要重付
ACT+PRE**（row buffer miss）。另外电容会漏电，所以要定期 **refresh**，刷新期间不能
访问。

把它套到访存模式上：

| 访存模式 | row buffer | 结果 |
|---|---|---|
| 顺序扫（0,1,2,3…） | 几乎全 hit | 单核 19.4 GB/s，还吃到**硬件预取器** |
| 随机跳（下标乱序） | 几乎全 miss | 每次付 ACT+PRE+往返，单核 7.2 GB/s |

这就是 §1.3 那张带宽表的全部原因，也是"随机 gather 天生比 memcpy 慢"的物理来源。
顺序访问还有第二个便宜可占：**硬件预取器**会自己发现"你在按地址递增读"，提前把后面
的 line 取进来；随机访问没有这种规律可循，所以 H1 才需要手工发 `prfm`。

#### 1.0.5 地址是虚拟的：TLB、page walk、大页、NUMA

程序里用的地址是**虚拟地址**，内存条上是**物理地址**，中间靠**页表**翻译。页表本身
在内存里，每翻译一次都查表就太慢了，于是有了 **TLB**（翻译后备缓冲，本质是"页号 →
物理页号"的小缓存，每核几百项）。

- **TLB miss**：硬件走 **page walk**，沿着多级页表（一般是 4 级）一路读下去，最坏要
  4 次内存访问。听起来很贵，但它通常与数据 miss **并行**发生，藏在 130ns 后面
  ——§1.7 实测：开/关 2MB 大页，延迟没有差别（11.76 vs 11.66ns @36t）。
- **大页（THP，2MB）**：一个 TLB 表项覆盖 2MB 而不是 4KB，等于同样的 TLB 容量多覆盖
  512 倍。对"足迹大 + 随机"的场景本来应该有用，但实测被上面的并行掩盖了。
- **NUMA**：这台机器有 32 个内存节点（node），每个核访问本地 node 约 130ns，跨
  node 要经过片间互联，会再贵几十 ns。所以本文所有数字都绑 `--physcpubind=190-227
  --membind=5`：**线程在 node 5、内存也在 node 5**。不绑的话，同一个程序能差出几十
  ns，比本文讨论的很多优化都大。

#### 1.0.6 CPU 内部：为什么"频率 × 宽度"不等于性能

最后一组概念，用在 §1.5（指令墙）和 §2.19（IPC）：

- **超标量 / 乱序**：现代核每拍最多取 4 条指令（4 宽），并且会打乱顺序执行——只要
  数据依赖允许。乱序的容量由 **ROB**（重排序缓冲，几百条）决定，这就是"窗口"。
- **IPC**（每拍退休多少条指令）：本机实测 0.71（aten）到 2.69（hpc 8t），硬件上限是
  4。IPC 低通常意味着**在等数据**，不是核不会算。
- **端口**：load/store 单元数量有限（每拍 1-2 条 load）。所以"每元素要几条 load"比
  "每元素几条指令"更能决定 L1 常驻场景的下界（§1.4）。
- **SVE**：ARM 的可伸缩向量扩展，本机向量寄存器 **512 位** = 64B，一条 `ld1d` 能搬
  8 个 f64（或 16 个 f32），正好一条 line。它省的是**指令条数**，不是延迟——所以
  §1.5 的结论是"指令人下界很低，从来不是瓶颈"。

#### 1.0.7 硬件名词速查

后面正文里出现的所有硬件词，一句话版本（按首次出现顺序排）：

| 词 | 一句话 |
|---|---|
| **cache line** | 缓存与内存之间搬运的最小单位，本机 64B |
| **组相联（set-associative）** | 一条 line 只能进"由地址决定的那个组"，组内可放 N 路 |
| **路（way）** | 一个组里能放几条 line；L1 8 路、L2 12 路 |
| **tag / set / offset** | 地址的三段：确认身份 / 选组 / 选 line 内字节 |
| **LRU** | 组满了就扔掉"最久没被用过"的那条 |
| **命中 / 缺失（hit / miss）** | 要找的 line 在不在这一级 |
| **MSHR** | 未完成 miss 的记账本，决定"同时在飞几条"，本机 16-20 |
| **RFO** | 写 miss 时先把整条 line 读进来（read-for-ownership） |
| **write-back** | 脏 line 等到被替换时才写回内存，不是每次写都下去 |
| **非临时存储** | 绕过缓存直接写内存的指令（`stnt1d`），本机无收益 |
| **DRAM row buffer** | DRAM 里"已打开的那一行"，同一行再读几乎免费 |
| **ACT / PRE** | 打开一行 / 关掉一行，换行就要付这两笔 |
| **refresh** | DRAM 电容会漏电，必须定期重写，期间不能访问 |
| **硬件预取器** | 硬件自己猜"你接下来要读哪"，只对规律访问有效 |
| **TLB** | 页表的缓存（虚拟页号 → 物理页号） |
| **page walk** | TLB miss 后沿多级页表走一遍，通常与数据 miss 重叠 |
| **大页（THP）** | 2MB 一页，一个 TLB 项覆盖 512 倍范围 |
| **NUMA** | 内存分节点，本地快、远端慢，必须绑定 |
| **IPC** | 每拍退休的指令数，本机实测 0.71-2.69，上限 4 |
| **ROB / 乱序窗口** | 能同时"在途"的指令数，决定能重叠多少独立操作 |
| **SVE** | ARM 向量扩展，本机 512 位 = 64B = 一条 line |

### 1.1 本机缓存层级与延迟阶梯

先看这台机器实际有几级（`lscpu -C`、sysfs、`numactl -H` 实测）：

| 层级 | 容量 | 组织 | 归属 | 一次命中要多久 |
|---|---|---|---|---|
| L1d | 32KB | 8 路 × 64 组 × 64B | 每核私有 | **2.0 ns（4 拍）** |
| L2 | 768KB（**有效 512KB**，见下） | 12 路 × 1024 组 × 64B | 每核私有 | **7.4-8.6 ns（15-17 拍）** |
| **L3** | **没有这一级** | — | — | — |
| 本地 DRAM（node 5） | 64GB | — | 16 个 CPU node 之一 | 92-131 ns |

- **没有 L3**。`lscpu -C` 只列出 L1d/L1i/L2，`cache/index*` 到 index2 为止。所以
  "末级缓存命中/LLC 命中"这类说法在本机不成立；实测也支持：4MB 起 L2 miss/访问
  已到 0.85、8MB 0.93（RESULTS §2.16.1），中间没有可用的第三级。
- **16 个带 CPU 的 node + 16 个纯内存 node**。608 核 = 2 socket × 304 核，但只有
  node 0-15 带 CPU（各 38 核），node 16-31 只有内存。绑核必须
  `--physcpubind=190-227 --membind=5` 成对写：否则线程在 node 5、内存却来自别的
  node，延迟会再高几十 ns，本文所有数字都会失真。

延迟阶梯（依赖链；`chase` 探针，足迹**精确等于**数组大小；原始表 RESULTS §2.16.1）：

| 足迹 | 8KB | 32KB | 48KB | 64KB | 128KB | 256KB | 512KB | 768KB | 1MB | 2MB |
|---|---|---|---|---|---|---|---|---|---|---|
| ns/访问 | 2.0 | 2.0 | **3.6** | 4.2 | 5.3 | 7.4 | 8.6 | 21.6 | 45.3 | 76.1 |
| L2 miss/访问 | 0 | 0 | 0 | 0.00 | 0.00 | 0.00 | 0.001 | 0.14 | 0.32 | 0.69 |

| 足迹 | 4MB | 8MB | 16MB | 32MB | 64MB | 256MB |
|---|---|---|---|---|---|---|
| ns/访问 | 85.7 | 94.5 | 110.5 | 122.4 | 128.1 | **136.6**（`mlp`） |

**为什么 L1 是 2.0ns、L2 是 8.6ns（上一版这两个数是错的：5.07 / 10.5-11.7）**。
上一版用的是 `latency` 探针，它每轮都要把 `volatile` 的下标写回栈、再读出来（约
5 拍），这次 store→load 转发**落在依赖链上**，于是每个点都被抬高一个常量。新加的
`chase` 探针把"足迹"变成精确自变量（沿一个长度恰好 = n 的环走，见本节末的陷阱），
两者在 4-64MB 上只差 2.4-2.8ns——**恒定偏移，正好验证这个解释**；而在小尺寸上差得
多，因为 2.6ns 加在 2ns 上就是 130%。`137ns` 不受影响：它来自 `mlp`，循环体里没有
volatile。

四条读法：

- **L1 = 4 拍**：8/16/24/32KB 全是 2.0ns，48KB 跳到 3.6——拐点正好落在 L1 容量上，
  这是"探针没在说谎"的最好证据。
- **L2 命中 8.6ns**：256/384/512KB 三档的 L1 miss 是 0.89-0.95（几乎每次都要问 L2）、
  L2 miss ≤0.1%（几乎都命中），所以这几个数就是 L2 往返本身。
- **1-4MB 不是"某一级缓存"**：命中率在爬（0.32 → 0.69），**同时**单次 miss 也在变贵，
  两件事叠加出这段缓坡。本机没有 L3，16MB 是 110ns 而不是 5ns 就是这个原因。
- **8MB 之后 miss 率饱和、latency 还在涨**（94.5 → 128.1）：这一段纯粹是 DRAM 侧
  变贵，推断为 row buffer 命中率随足迹下降（同一条 row 被再次打开的概率变小）；
  4KB 页的 TLB 已被 §1.7 排除。建模直接用实测值。

**"有效容量 512KB 而不是 768KB"是什么意思**（这个数最容易被问住）：

768KB 是**物理容量**：1024 组 × 12 路 × 64B。但做性能模型时你要问的不是"能装多少"，
而是"装到多少还能跑满速"。实测：512KB 时 L2 miss 只有 0.1%，576KB 就 6.0%、640KB
11.5%、768KB 14.3%、1MB 31.9%。**在装满之前，命中率就已经在掉了。** 三层原因：

1. **12 路里"最后几个 way 用不上"**。足迹装满时，每个组平均要放 12 行——正好等于
   路数。而实际落进每组的行数是泊松涨落的：约一半的组会超过 12 行，超出的就被挤
   出去。按 `命中率 = E[min(1, 12/k)]、k ~ Poisson(足迹行数 ÷ 1024)` 算：512KB 掉
   0.9%、768KB 掉 8.4%、1MB 掉 23%；实测 0.1% / 14.3% / 31.9%，比模型更差一点
   （旁路流量的锅）。

   > 直观版：容量是"货架总格数"，但每本书只能放进编号固定的那一格；每格只有 12 个
   > 位置，而每个编号下的书数是随机的。于是总有些格子先满、先开始往外扔——**总格数
   > 够用，不等于每格都够用**。

2. **物理页映射（页着色）**。相邻两档能差一个数量级：448KB 掉 0.9%、512KB 只掉
   0.1%、576KB 掉 6.0%。同一台机器、同一份代码，只改分配大小，miss 率不是单调阶梯
   ——因为这 1024 个组怎么被 4KB 页覆盖，取决于物理页落在哪。
3. **旁路流量**。真实内核还有下标数组、输出写、预取、页表在抢同一批 way，能用的容量
   只会比裸探针更小。

所以口径是：**512KB 当"能当真"的容量，768KB 当"物理上限"**。做容量假设用前者；用
后者会在 700KB 附近就开始低估 miss（差 1/3 容量，约等于差一档缓存）。

**一个测量陷阱**：指针追逐的"工作集"是**置换的环长**，不是数组大小。1MB 数组换
一个种子，环长 2339 行 vs 10040 行，同一台机器上实测 **26.1 vs 46.4 ns**（RESULTS
§2.16.1）。所以做"命中率 vs 工作集"的曲线必须用 `chase`（环长 = n）；用随机置换的
探针时，1MB 这类尺寸的横轴是不可信的。

**这一节的数字怎么测出来的**（细节见 §9.3）：时间用 `memprobe chase SIZE_KB ACC`
（沿定长环走的依赖链，`ns/访问 = 墙钟 ÷ 访问次数`）；命中率用 `perf stat -e
l1d_cache_refill,l2d_cache_refill`，跑一遍 `ACC=0` 扣掉建表开销、再除以 `1.1×ACC`
（探针自己还会先跑 `ACC/10` 的预热）。**时间和命中率是同一次运行同时取的**——否则
"延迟涨了"到底是因为命中率掉了、还是单次 miss 变贵了，就分不清。

### 1.2 每核的"在飞窗口"（本文的核心曲线）

**要回答的问题**：一颗核能同时等几件事？只有 1 件时，"一次 137ns"就是硬成本；
能等 16 件时，成本就摊成 8.6ns。

**怎么测**：`memprobe mlp S` 造 S 条**互相独立**的指针追逐链。每条链内部是依赖的
（下一个地址来自上一个读回的值），所以一条链最多只有 1 个访问在飞；S 条并行，就
等于把"在飞条数"这个自变量**精确设定成 S**。这是这套方法最值钱的地方：不是估，
是直接设定。

| S（同时在飞的访问数） | 1 | 2 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|---|
| 256MB 源，ns/次 | 136.6 | 70.1 | 35.9 | 18.5 | 10.2 | **8.9** |
| 16MB 源，ns/次 | 113.8 | 57.3 | 29.8 | 15.7 | 9.1 | 8.0 |

**结果**：S 从 1 到 16，成本几乎精确地按 `137/S` 下降（1→2 是 136.6→70.1，正好
一半）；S 从 16 加到 32 只快 13-15%，然后平了。这条曲线同时给出两个数：

- **每核能同时挂 16-20 条 line**——这是硬件上限。
- **平台的纵坐标就是吞吐下界**：**8.6-8.9 ns/条 line**。

**为什么停在 16-20**：每颗核里有一张表叫 **MSHR**（miss status holding register，
见 §1.0.2 的完整路径图），
记录"哪些 line 已经发出、还没回来"。表项用完，新的 miss 只能排队等前面的回来，
这就是上限。它由电路决定，代码改不了。能改的只有两件事：**把窗口填满**（预取、
批量化），或者**少发几条 line**（提高 line 内利用率）。

换成三个常用单位：

- 8.9ns/line → 每秒 112M 条线 → **7.2 GB/s/核**（随机 line 吞吐）。
- 1 条在飞 = `64B ÷ 137ns` = **0.47 GB/s**。
- A=16 的一行正好 64B = 1 条 line，所以 **8.6ns/行** 就是行拷贝这一族的天花板。

**这一步为什么要交叉验证**：如果模型对，"带宽延迟积"应该自洽——`7.2GB/s × 137ns
≈ 986B ≈ 15.4 条 line`，与曲线给的 16-20 条对得上。饱和吞吐与延迟是两个独立测量，
它们互相印证，说明曲线不是探针伪影（方法见 §9.3）。再往上算一层：整个 NUMA 节点
读带宽 168GB/s × 137ns ≈ 23KB ≈ 360 条 line，而 36 个核各自挂 16 条就是 36KB——
**已经超过节点带宽能承载的量**，所以线程一多，先撞的是带宽墙而不是延迟墙（§1.3）。

**三个常见误解**（本文结论之所以反直觉，多半是踩了其中一条）：

1. **"延迟高 = 带宽低"**：延迟是一次往返（137ns），带宽是稳态吞吐（7.2GB/s/核）；
   两者只通过"在飞条数"联系，不能互相换算。
2. **"加线程就能追上"**：每个线程各自等延迟时，加线程只是把等待并行化，每核仍只有
   ~1 条在飞（aten 1t 322 拍/行、8t 318 拍/行，几乎没变，§3.5）。
3. **"指令越宽越快 / 预取越远越好"**：指令下界比实际实现低 1-2 个数量级（§1.5）；
   预取超过 MSHR 容量会把自己挤掉（A=64 8t 的 D=16 崩到 115ns，§1.6）。

### 1.3 带宽与线程：为什么顺序能跑 19.4GB/s，随机只有 7.2

| 线程 | 1 | 8 | 16 | 38 |
|---|---|---|---|---|
| 流式读（2048MB） | 19.4 | 127.4 | 169.2 | **168.0** GB/s |
| 流式拷贝（2048MB） | 28.9 | 132.3 | 145.0 | 116.3 GB/s |
| `clone`（8MB，读写合计） | 20.6 | 53.2 | 71.6 | 177.8 GB/s |

**为什么随机只有 7.2**（DRAM 内部结构见 §1.0.4）：DRAM 不是一块平坦的数组，它按
**bank**（存储体）和 **row**（行缓冲）组织——可以想成图书馆：bank 是书架，row 是
书架上的一整排书。读同一排的书几乎不额外花时间（row buffer 命中）；换一排就要先把
旧的放回、再把新的搬出来（ACT + PRE，合计几十 ns）。顺序访问大概率命中同一排，而且
**硬件预取器**还会提前把后面的行取进来；随机访问两样都吃不到，每次都要付完整的
"激活 + 往返"。

这也直接解释了 H1 为什么要手工发 `prfm`：随机行没有现成的硬件预取可用。

顺便解释一下这张表的另两行：**多线程**能把带宽顶到 168GB/s，是因为一条 DDR 通道
本身有很多 bank，多个核的请求可以落到不同 bank 上并行（bank 级并行）；但到了
38 线程就平了——那是内存控制器的通道数量与队列深度的上限，不是核不够。**写**
（拷贝那行）比读便宜不多，因为写还要占一份带宽做 RFO 回读（§1.0.3）。

**怎么测的**：`memprobe bandwidth 2048 t rd`，一次扫 2048MB（远大于任何缓存，避免
命中干扰），每档重复 3 遍取最好值（排除调度抖动）；拷贝是同一段扫描多写一路输出。
`clone` 那行来自 `x.clone()` 的实测，故意用小副本（8MB）暴露"每线程只有 1MB"时的
固定开销。

两条推论：

1. **节点读带宽 168GB/s 是硬顶**；36 核若都按 7.2GB/s 吃随机 line，就是 260GB/s
   > 168 —— 所以高线程下随机行流量先撞"带宽"，不再撞"延迟"。实测 36t 行流量只到
   读带宽的 56-61%（`degradation-analysis.md` §6.4）。
2. **小副本不能按 145GB/s 建模**：8MB 的 `clone` 在 8/16t 只有 53/72 GB/s，是
   "每线程 1MB 的粒度 + 固定开销"拖的。小 K 场景要按 §6.5.2 的固定项算。

### 1.4 两种下界：同一段 gather，源在 L1 和在 DRAM 差 8-9 倍

先说清楚 **gather** 是什么：给一串下标，把对应的元素取出来（`dst[k] = src[idx[k]]`）。
它有两种完全不同的成本，取决于源数组有多大——**能不能装进缓存**。

- **源大（几 MB 以上）**：每次都要去 DRAM 拿一条 line，成本由 §1.2 的窗口决定。
- **源小（几 KB）**：整张表常驻 L1，没有"等内存"这回事，成本变成**每拍能发几条
  load**（发射/端口吞吐）。

同一段 `load idx → load data`，只换源的工作集（RESULTS §2.20，每线程口径，
CHAINS=16/32）：

| 源 | 8KB（L1） | 32KB（L1 满） | 256KB（L2） | 16MB（DRAM） |
|---|---|---|---|---|
| ns/元素 | **0.66-0.71** | 1.45-1.76 | 1.11-1.26 | 5.62-5.98 |

- **L1 下界 0.7 ns/元素**：1t 就到，且**不随线程数变化**（1t 0.71、19t 0.67）——
  它是每核吞吐极限，不是延迟。线程只决定"几颗核各干一份"，不改变每核的速度。
- **CHAINS 1→16 在 8KB 上有 2.3x**（1.65→0.71）：连 L1 命中的 2.0ns 延迟也要靠在飞
  条数掩盖。这就是"批量化对桶化输出段同样有效"的直接证据（§7-H2b）。
- **为什么 L1 常驻不是"零成本"**：命中时没有 miss 可藏，成本变成发射/端口吞吐——
  每个元素要读 8B 下标（顺序）+ 4B 数据（随机）+ 累加，实测 0.66-0.71ns ≈ 1.3-1.4
  拍/元素（按 2.0GHz），已经贴着"每拍 1-2 条 load"的端口上限。这一档再加在飞条数
  没用，能动的只有**减少每元素的访问/指令数**。
- **32KB 为什么反而慢**：L1 是组相联的，工作集正好等于容量时冲突率上升；再叠加
  8MB 下标流从旁边冲刷，命中率就掉下来了。它**不能当"L1 常驻"建模**，要按 L2 读。
- **两条下界差 8-9 倍**。上一版把桶化套到 5.65ns 的 DRAM 下界上，把空间估大了一个
  数量级；反过来，把大值域 1D gather 套到 0.7ns 上也会低估。

**怎么测的**：`memprobe idxgather SIZE ACC t CHAINS`。它先从内存顺序读下标（和真实
内核同构：`load idx → load data`），再用取回的下标随机取数据；`CHAINS` 控制"每轮
先算好几个地址再一起发 load"，用来把"每核在飞条数"和"下标读取/检查"分开量。源大小
支持小数 MB（8KB 这一档就是要靠它才测得出来）。`ns/元素 = 墙钟 ÷ 每线程元素数`——
这个"每线程口径"是唯一能跨线程数比较的单位（§2.4）。

### 1.5 指令与 SVE：不是杠杆

一般人第一反应是"用向量指令就能快"。这一节就是先把这个念头排除掉，免得后面白花
力气：

| 写法 | ns/64B | 拍/64B |
|---|---|---|
| 标量 8B 循环 | 2.13 | 4.3 |
| **SVE 512-bit** | **1.26** | **2.5** |
| 源在 L2 时 | 1.40 | 2.8 |

- **512-bit 是什么**：SVE 是 ARM 的可伸缩向量扩展，本机向量寄存器 512 位，一条
  `ld1d`/`st1d` 能搬 64B（8 个 64 位 lane，或 16 个 32 位 lane）。2.5 拍搬 64B ≈
  每核单向 50GB/s，这就是指令侧的天花板。
- 一条 line 的"拷进拷出"指令下界只有 **1.26 ns**，比任何真实实现都低 1-2 个数量级
  （A=16 的实现在 11-81ns/行）。**所以指令发射从来不是 `aten::index` 的瓶颈**。
- **SVE gather 不比标量展开差**（4.73 vs 5.79 @16MB；5.18 vs 6.18 @256MB）——它把
  8 条 load 压成一条指令，发射侧更省；但一批只有 8 条 lane，收益上限就是"8-16 条
  在飞"。
- **非临时存储（`stnt1d`）收益 0**（29.1 vs 29.1 @1t、144.5 vs 146.4 @16t）。写侧
  RFO 不是这台机器的问题（回到 §1.0 的第 3 条）。

**怎么测的**：`sveprobe`（RESULTS §2.17），同一个"从源拷到目的"的循环写三遍：纯
标量、SVE 512-bit、SVE + 非临时存储；源分别放 L1（16KB）和 L2（256KB）两档。测的是
**纯拷贝指令**，不含下标、不含检查——所以它给的是"指令能有多快"的天花板，不是实现
的耗时。

> 有人会问"那算力呢，要不要算 GFLOPS"。这类算子的算术强度是 **0**（§2.6）：它不做
> 浮点运算，roofline 上永远贴着带宽那条水平线。计算确实有，但它是**整数/地址指令**，
> 天花板是 IPC 而不是 TFLOPS——这正是 SVE 省指令条数、却换不到延迟的原因。

### 1.6 预取：唯一的大杠杆，但有硬边界

预取指令 `prfm pldl1keep, [addr]` 的作用是"**先替我把这条 line 取到 L1，我不等它**"。

硬件上它做了三件事，理解了就不会用错（背景见 §1.0.2）：

1. **查 L1**：已经在就什么都不做（所以重复预取同一行不花钱）。
2. **不在就申请一个 MSHR 表项**，把"这条 line 我要"登记进去，然后立刻返回——**它不
   占目标寄存器，也就不会让后续指令等它**。这是它和普通 load 的唯一本质区别：普通
   load 会把"等数据"这个依赖写进指令流，预取不会。
3. **不保证顺序、可以被丢弃**：硬件可以在队列紧张时把预取请求丢掉，所以**预取是
   提示，不是命令**——这也意味着"预取没生效"不会报错，只能靠时间或计数器看出来。

所以它不违反 §1.2 的规律：它就是把"在飞条数"从 1 抬上去的唯一低成本的软件手段。
`pldl1keep` 是"取到 L1 并保留"的策略名（还有 `pldl1strm` 流式、`pldl2keep` 取到 L2
等，本机实测差别不大）。

**先约定一个记号：D = 预取距离**，单位是**行**——在处理第 i 行时，先对第 i+D 行的
起始地址发一条 `prfm`。所以 `D=0` 就是**关掉预取**（写法和预取前完全一样），
`D=8` / `D=16` 就是"提前 8 / 16 行把它们取到 L1"。A=16 时一行 64B，D=16 意味着
**提前 1KB 的地址**在路上；A=64 时一行 256B，同样的 D=16 就是 4KB——这就是为什么
"D 不能只看行数，要乘上行字节"（下面是本文最常引用的一对数字）。

`rowgather`（16MB 源，1t，ns/行）：

| 行宽 | plain（地址与取数同链） | 4 行流水 | 预取 8 行 | 预取 16 行 |
|---|---|---|---|---|
| A=3（12B） | 40.1 | **20.8** | 23.1 | 22.7 |
| A=16（64B） | 52.6 | 52.4 | 17.5 | **11.4** |
| A=64（256B） | 105.5 | 104.4 | **38.4** | 42.8 |

- **A=16：52.6 → 11.4（4.6x）**。机理是把"算地址 → 取 line → 拷"从一条链上摘下来，
  在飞从 ~1 抬到 ~12。这是 H1 的全部依据。
- **`prfm` 不是"更快的 load"**：它只是把第 `k+D` 行的地址提前交给 L1；效果等价于
  把这条访问从依赖链上摘下来。它占的是**同一个 MSHR 池**，所以 D 太大会把自己挤掉。
- **A=3 用 4 行流水就够了**（20.8 ≈ 预取 22.7）：12B 的行只占一条 line 的一小段，
  后面的行反正也在同一条 line 里。
- **距离要按行字节封顶**：A=64 用 D=16（4KB/轮 × 8t = 32KB 在飞）会把缺失队列挤爆，
  8t 反而崩到 115ns（D=8 是 54.8）。
- **超宽行不要预取**：A=256（1KB = 16 条 line）行内自己就填满窗口（§2.19.6）。

**怎么测的**：`rowgather` 把同一件事写成五种形式——`plain`（地址与取数串在一条链
上）、`memcpy`、`pipe`（4 行流水）、`pf8`/`pf16`（提前 8/16 行发预取）。**只改这一
个变量、其余全同**，所以差值就是"预取"这一项的贡献。这是这套文档里最常用的手法：
不是证明某个写法快，而是造出"除了它以外全都一样"的两个版本。

### 1.7 大页与 TLB：不是问题

**TLB 是什么**（背景见 §1.0.5）：CPU 用的是虚拟地址，内存用的是物理地址，中间要
查页表。TLB 就是这张页表的缓存。默认页 4KB，64MB 工作集就是 16384 个页，TLB 装不下
就会 miss，得去内存里走一遍多级页表（page walk）——最坏要 4 次额外内存访问，听起来
非常贵。

**实测收益 0**（RESULTS §2.16.6）：THP（2MB 大页）开与关，`latency` 与 `gather` 都
没有差别（36t 时 11.76 vs 11.66ns），`chains=1` 也一样（20.94 vs 21.06）。原因是
page walk 的处理与数据 miss 重叠，**藏在 137ns 后面**。

**不是所有"看起来该优化"的项都值得动**——这一条就是反例，写进 §8 的负结果里。

### 1.8 单位换算小抄（读表用）

全文在 ns、拍、GB/s、"每行"、"每元素"之间来回换。记不住就查这张表：

| 换算 | 式子 | 例子 |
|---|---|---|
| 拍 ↔ ns | `1 拍 = 1/f`，f = 2.0GHz | 137ns ≈ 274 拍 |
| line ↔ 带宽 | `GB/s = 64B ÷ (ns/line)` | 8.9ns/line → 7.2GB/s |
| 元素 ↔ 带宽 | `GB/s = 元素字节 ÷ (ns/元素)` | 4B ÷ 8.9ns = 0.45GB/s |
| ns/行 ↔ 带宽 | `GB/s = 行字节 ÷ (ns/行)` | 64B ÷ 24ns = 2.7GB/s |
| 加速比 | `ratio = aten ÷ hpc` | 152 ÷ 24 = 6.3x |

2.0GHz 是本机标称主频（`lscpu`：`CPU max MHz 2000`、boost disabled），也做过独立
核对：纯依赖加法的循环 2e8 次 / 0.809s，PMU 记 1.609e9 拍 → **1.99GHz**（`memprobe
freq`）。旧稿用过 2.07GHz（perf 反推 322 拍 ÷ 155.2ns），与 2.0 差 3.5%，在测量
误差内。换频点"拍 ↔ ns"会变，所以本文优先用 ns，只有指令/周期分析才换回拍。

**两个最容易混的口径**：

- **`ns/元素` 与 `ns/行`**：一行有 A 个元素，所以 `ns/行 = A × ns/元素`。行拷贝族
  用 ns/行，gather 族用 ns/元素，**不能直接比**。
- **每线程 ns 与聚合 GB/s**：前者不随线程数变（每核干自己那份），后者随线程数涨到
  带宽顶为止。判断"还能快多少"必须用前者（§2.4）。

### 1.9 这些数的可信度

- **独立 C 探针**（`benchmarks/memprobe.c`、`sveprobe.c`），不经过 Python 与 torch：
  `import torch` 要 7.2s、建 8MB 张量要 2.9s，混进来会把小规模测量彻底淹掉。
- **每格 3 遍取最好值**；`ns` 类数字用 `CLOCK_MONOTONIC` 直接量墙钟。
- **亲和与 NUMA**：全部 `numactl --physcpubind=190-227 --membind=5`，只测 node 5 的
  本地内存。**不绑 NUMA 的话，同一个程序能差出几十 ns**，这一条比探针写得好不好
  重要得多。
- **perf 类计数两段相减**（3s + 9s），排除进程启动与建表开销；缺行数只信
  `l1d_cache_refill`（§9.4 讲了为什么另外两个口径对不上）。
- **每个数字都有复现命令**，在 RESULTS 对应小节末尾；本文只做推导，冲突以 RESULTS
  为准。

方法本身（怎么设计探针、怎么交叉验证、怎么避免自欺）单独写在 **§9**，那里有一步
一步的例子。

## 2. 成本模型

记号：`K` 行被选中、每行 `A` 个元素、元素 `e` 字节、`t` 线程、`B` 广播因子。

把"一次调用要多久"写成一句话：

```
T ≈ max(在飞条数墙, 带宽墙, 指令墙) + 固定账
```

为什么是 `max` 而不是相加：三条墙**同时**在起作用，谁先饱和谁就是瓶颈；另一条还有
余量时不会额外加时间。这解释了一件很常见的事——**只修一条墙常常看不到收益**，
因为还有一条正好卡在同一个高度（§2.3 的实测就是这种情况）。

### 2.1 三堵墙 + 一笔固定账

| 墙 | 下界 | 什么时候是它 |
|---|---|---|
| **在飞条数墙** | `T = 行line数 × 137ns / 在飞条数 / t` | 随机行、工作集出 L2、地址与取数串在一条链上 |
| **带宽墙** | `T = (行line字节 + 写字节) / BW(t)` | 行很宽，或在飞条数已经抬到 16-20 |
| **指令墙** | `T = 每行指令数 / (IPC_max × f)` | 高线程 + 每行只有 1 条 line（此时指令数与 line 数脱钩） |
| **固定账** | `T += F` | `K` 小（≲4096）或每线程工作量 ≲16KB |

三条墙有先后顺序：随机行先撞**在飞条数**；把在飞抬到 16 之后才轮到**带宽**；而当
每行的指令数被"遍数/记账"抬起来时，**指令墙会先到**——这正是 8t 的现状（§5.2）。

**代入一个具体例子**（A=16、1t、8MB 输出，即 §3.2 的 r16 格）：

| 量 | 算式 | 结果 |
|---|---|---|
| 在飞条数墙 | `137ns ÷ 5.7 条在飞` | 24.0 ns/行 |
| 换成拍 | `24.0ns × 2.0GHz` | 48 拍 |
| 指令墙 | `105 条 ÷ IPC 2.14` | 49 拍 |
| 实测 | — | **23.5ns / 49 拍** |

两个模型从完全不同的方向算出同一个数（48 vs 49 拍），实测落在 23.5ns——这不是巧合，
它说明**两条墙此时一样高**，所以只调其中一个不会有用（§5.1）。

### 2.2 有用字节带宽是陷阱

内存按 64B line 计费。假设你只想读 4 个字节（A=1 的 f32），内存仍然会搬一整条
64B——**有用字节只占 1/16**，剩下 60B 白搬：

| 行宽 | A=1 f32 | A=3 | A=4 | A=8 | A=16 | ≥16 |
|---|---|---|---|---|---|---|
| 行字节 | 4 | 12 | 16 | 32 | 64 | ≥64 |
| line 放大 | **16x** | 5.3x | 4x | 2x | **1x** | 1x |

所以"1D f32 gather 只有 0.7 GB/s 有用带宽"不是实现烂，是结构如此：它每秒实际搬
0.7×16 ≈ 11 GB/s 的 line，已经超过单核随机 line 的上限 7.2GB/s——因为源小到能
常驻 L2 时不再受 DRAM 往返限制（§1.4 的 L1/L2 下界）。

这条也解释了为什么"提高行宽"是最划算的方向：A=16 让放大从 16x 变 1x，同样一次
随机访问能取回 16 倍有用的数据。

### 2.3 三条墙是"同时"起作用的：1t 与 8t 都已经在内存/指令的交叉点

把 §2.19.2 的实测代进三堵墙，会看到一件容易被忽略的事：**现在的行拷贝在 1t 和 8t
都同时贴着两条墙**（1t 每行 1 条 line、8t 每核 1 条 line，f≈2GHz）：

| 场景 | 每行周期 | 内存墙（274 ÷ 在飞） | 指令墙（指令数 ÷ IPC） | 结论 |
|---|---|---|---|---|
| 1t，A=16，D=16 | **49** | 274 / 5.7 ≈ 48 | 105 / 2.14 ≈ 49 | 两条墙几乎重合 |
| 8t，A=16，D=16 | **121** | 274 / 2.4 ≈ 114 | 326 / 2.69 ≈ 121 | 两条墙仍重合，但指令数 ×3 |

（`274` 就是 `137ns × 2.0GHz`：一次随机访问等于 274 拍，摊到 5.7 条在飞上就是 48
拍。表里的"每行周期"是 perf 直接量的。）

所以：

- **只抬在飞条数**（再加预取/再加 D）会被指令墙挡住：1t 再怎么预取也到不了
  11.4ns/行（105 条指令 ÷ IPC 4 ≈ 13ns 已经是上限）。
- **只砍指令**也会被内存墙挡住：8t 把 326 条砍到 120 条能到 ~45 拍/行，但那时
  2.4 条在飞才真正成为瓶颈，需要同时把在飞抬上去。
- 这解释了为什么 H1 的收益是 2.5-2.9x 而不是"16x 的一半"：它只动了分母，而分子的
  指令账在 8t 已经很高（`ins/行` 从 80 涨到 326 是两遍模型 + 逐行记账的账）。

**这条是"高线程不能靠预取继续加码"的量化依据**，也是 H3/H6 必须和 H2 一起做的原因。

### 2.4 两种下界，两个单位

- **DRAM 下界**（大值域 1D、随机行）：5.6-6.0 ns/元素、8.6-8.9 ns/行（1 条 line）。
- **L1/L2 下界**（桶化、小源、dom≤2048）：0.66-0.71 ns/元素。
- **单位必须是"每线程"**：§2.20 的线程扫描显示每线程 ns 不随 t 变，所以
  "K/t 个元素 × 每线程 ns"才是可跨线程数比较的成本；聚合带宽在低线程会骗人。

拿错下界的后果不是"差一点"，而是**差一个数量级**：三格桶化用 DRAM 下界算会得出
"还有 41x"，实际上限是 6.5x（§4.2）。

### 2.5 固定账

除了逐行/逐元素的成本，每次调用还有一笔与 `K` 无关的开销：入口、两次 `parallel_for`
的 fork-join、输出张量的分配与 first-touch（8MB = 2048 次缺页）。

`t = F + c·K` 拟合（§2.18.5，1t，A=16，8MB 输出）：`F ≈ 0.54 ms/调用`，
`c = 19.4 ns/行`。`K≲32768` 时 `F` 把 ns/行 抬到 2-3 倍——**小 K 的账不在行循环里**。

另一口径（`degradation-analysis.md` §6.5.2，小 K 整次调用）：固定项 1t 10.0µs、
19t 15.7µs。两者不矛盾：一个摊到 8MB 输出的行数上，一个是小调用的整次开销。同一个
`F`，看你把它除到多少个行上。

### 2.6 为什么这份分析里没有 GFLOPS

性能分析常从"这台机器多少 TFLOPS"开始。**对本算子这条轴完全用不上**——它一次浮点
运算都不做。但"不用 GFLOPS"和"不用管计算"是两件事，这一节把区别说清，免得以后
换了算子还用错尺子。

#### 2.6.1 roofline 的两条轴，和"算术强度 = 0"意味着什么

roofline 模型画两条天花板：

- **算力墙**（斜线）：`性能 ≤ 峰值 FLOPS`。
- **带宽墙**（水平线）：`性能 ≤ 峰值带宽 × 算术强度`。

横轴是**算术强度**（arithmetic intensity）= `做了多少浮点运算 ÷ 搬了多少字节`
（flop/byte）。横轴越往右，算力越可能先到；越往左，越是被带宽卡住。两条线的交点叫
**机器平衡点**。

| 算子 | 算术强度 | 瓶颈 | 该看的指标 |
|---|---|---|---|
| `memcpy` / `index` gather / 行拷贝 | **0** flop/B | 带宽 + 延迟 | GB/s、ns/line、在飞条数 |
| 缩放 / 反量化（每元素 1-2 次乘加） | 0.25-0.5 | 带宽（贴近平衡点） | GB/s，外加算力复核 |
| 小矩阵乘 / attention | 10-1000 | **算力** | TFLOPS、MAC 利用率 |

本算子落在第一行：**算术强度恒等于 0**。roofline 图上它是一条贴着 y 轴的竖线，
永远只可能碰到水平那条带宽线。所以谈 GFLOPS 没有意义——**不是"算力不重要"，而是
"这个算子的 x 坐标是 0"**。

#### 2.6.2 本机的平衡点：每字节约 0.07 次浮点，才够到算力墙

- **峰值浮点**（ISA 上界**估算**，未实测）：2 条 512 位 FP 流水 × 8 个 f64 lane ×
  2 flop（FMA）× 2.0GHz ≈ **64 GFLOPS/核**；38 核 ≈ **2.4 TFLOPS**。
- **节点读带宽**（实测，§1.3）：**168 GB/s**。
- **平衡点** = `168 GB/s ÷ 2.4 TFLOPS` ≈ **0.07 flop/byte**。

也就是说：**每搬 1 字节，至少要做 1/14 次浮点运算，才算"有可能"撞到算力墙**。本算子
是 0，离这条线差无穷倍；即便把峰值浮点估错一倍（平衡点 0.035-0.14），结论也不变。
**这就是"可以用带宽模型而不做算力模型"的定量理由。**

#### 2.6.3 但计算并没有消失：这里的"计算"是整数

桶化路径每元素要做整除/取模（`p/K`、`p - (p/K)*K`）、边界检查、写回——**这些不是
浮点，但确实要吃发射带宽**。所以要用另一把尺子：**每元素多少条指令 ÷ IPC**。

```
每元素指令下界 = 指令数 ÷ (IPC × 频率)
```

代入本机实测（IPC 上限 4、2.0GHz）：**每元素 10 条整数指令 → 1.25ns/元素**。而 §5.3
倒推出来的"整数账"是 **2.15ns/元素**（Sonata 4.53 − 2.0 查表）——同一量级，
说明那 2.15ns 里主要就是指令，而不是"某种未知的缓存效应"。**这就是为什么 §5.3 敢说
"要砍整数账"，也是为什么本文的第二把尺子是 IPC 而不是 GFLOPS。**

于是本文只用四把尺子，它们覆盖"算术强度 0 + 少量整数"的全部情形：

| 尺子 | 量什么 | 天花板 | 在本文哪里 |
|---|---|---|---|
| **GB/s**（聚合/每核） | 带宽 | 168 GB/s（节点）、7.2 GB/s（单核随机 line） | §1.2/§1.3 |
| **ns/line 与在飞条数** | 延迟 | 137ns ÷ 16-20 | §1.2 |
| **指令/元素 与 IPC** | 发射 | 4 IPC × 2.0GHz | §1.5/§5.3 |
| **load 端口** | 每拍能发几条 load | 1-2 条/拍 | §1.4 |

#### 2.6.4 什么时候才该把 GFLOPS 请回来

如果算子形态变了——比如在 gather 之后接一个 `dequant`（每元素 2-4 次浮点）、或者把
`index` 融进矩阵乘的 epilogue——算术强度会从 0 爬到 0.1-1 flop/byte，**越过 0.07 的
平衡点**。那时带宽模型仍然成立（它给出上界），但必须再检查算力侧；否则会把"算力不足"
误判成"带宽不足"，修错方向。

判据只有一句：**`算术强度 > 平衡点` 才需要 TFLOPS，否则只看 GB/s 与在飞条数。**

## 3. `aten::index` 的实现解剖

### 3.1 源码里的三条硬事实

先说 `aten::index` 在做什么：给它一个张量和一串下标，它把对应位置的元素取出来，
放进一个新张量。二维（行）形态就是"取 K 行、每行 A 个元素"。实现在
`aten/src/ATen/native/cpu/IndexKernel.cpp` 加 `TensorAdvancedIndexingUtils.h`，读它
只需要记住三条：

1. **逐元素走 `TensorIterator`**：`cpu_index_kernel` 的循环体就是
   `offset = indexer.get(i); *(scalar_t*)dst = load(src + offset)`——每一步都带越界
   检查与负索引归一。`perf record` 确认热点落在
   `cpu_index_kernel → TensorIteratorBase::loop_2d_from_1d`（§2.19.7）。
2. **每行只算一次下标**：`is_constant_index` 分支让内层 A 个元素共用一次 offset，
   所以每行 ≈ 一次随机访问 + A 次标量拷贝。**这是 aten 唯一的"批量化"**，也是它
   在 A 变大时能摊薄成本的原因。
3. **int32 下标先转 int64**（`make_info` 里 `indice.to(at::kLong)`）：多一遍
   `K×4B` 读 + `K×8B` 写。本仓不交这个税（T16 直接吃 int32）。

### 3.2 实测位置（1t）

| A | 1 | 3 | 8 | 16 | 64 |
|---|---|---|---|---|---|
| aten ns/行 | 29.1 | 141.6 | 150.8 | 168.9 | 283.0 |
| `137 / 该值` → 在飞条数 | 4.7 | **1.0** | **0.9** | **0.8** | 1.9（4 条 line/行） |

A≥3 之后每行成本基本是常数——**A 变大只摊薄，不改善**，这正是"一次访问的延迟"的
形状。

A=1 那一行是个例外，值得解释：它的等效在飞有 4.7，不是因为它写得好，而是因为循环体
短——每行只有几条指令，乱序窗口能同时塞下 4-5 次迭代，于是四五条随机 load 真的重叠
了。A≥3 之后循环体变成 A 倍长，一次迭代就把窗口占满，于是退回"一次只等一条"。
**这件事本身就是 §1.2 的推论：窗口不变时，循环体越短，能同时等的事越多。**

perf（§2.19.2，r16 = A=16 K=131072，1t）把这件事钉死：

| 指标 | aten | hpc D=0 | hpc D=16 |
|---|---|---|---|
| ns/行 | 155.2 | 78.7 | **23.5** |
| 周期/行 | 322 | 152 | **49** |
| 指令/行 | 227 | 80 | 105 |
| IPC | 0.71 | 0.52 | 2.14 |
| L1 缺行/行 | 1.07 | 1.02 | 1.02 |
| 等效在飞 | **0.9** | 1.8 | **5.7** |

**两列 `hpc` 是同一个实现的两种配置**（§1.6 的 D）：`D=0` 把 `HPC_PF_DIST` 设成 0、
**关掉预取**，等价于 H1 之前的形态；`D=16` 是 A=16 的默认档（提前 16 行 = 1KB）。
把它们并排放，是为了让"预取"成为唯一变量：同一个算子、同一份数据、同一个线程数，
差别只有那几条 `prfm`。所以 `152 拍 → 49 拍` 这个 3.1x 可以直接记在"预取 + 由此
带来的在飞条数"账上，而不是记在"实现本身变好了"上。

**"等效在飞"这一列是怎么算出来的**，值得单独记住，因为它把"周期"翻译成了"同时等
几件事"：

```
在飞条数 = 274 拍 ÷ 每行周期         # 274 拍 = 137ns × 2.0GHz
```

于是 aten 是 `274 ÷ 322 = 0.85`，hpc D=0 是 `274 ÷ 152 = 1.8`，hpc D=16 是
`274 ÷ 49 = 5.6`。这个换算是自洽的：**如果每行只等一次延迟、且只等一条，周期数就
应该正好是 274**；实测 322（多出来的 15% 是写回与指令），所以 aten 确实"一次只等
一条"。

`l1d_cache_refill` 在 A≤16 的行上正好是 1.00-1.19 条/行（= 每行读一条 line；写整行
不需要 RFO，§1.0），所以可以直接当"line 数"用。这是三种形态、两种独立口径互校之后
的结论（§9.3），也是后面所有"在飞条数"数字的来源。

### 3.3 aten 自己的理论倍数

| 形态 | aten 1t | 下界 | 自己还有 |
|---|---|---|---|
| 随机行 A=3-16（1 条 line/行） | 132-155 ns/行 | 8.6-8.9 ns（16-20 条在飞，§1.2） | **15-18x** |
| 宽行 A=64（4 条 line/行） | 252 ns/行（K=8192，同轮） | 38 ns（预取 8 行） | 6.6x |
| 超大行 A=256（16 条 line/行） | 531 ns/行 | 198 ns（行内已 16 条在飞） | 2.7x |
| 1D 大值域 gather（A=1，DRAM） | 29.2 ns/元素 | 5.65（CHAINS=32） | 5.2x |
| 1D 小值域 gather（A=1，L1） | —（aten 无桶化；按每元素 ~5ns 推算） | 0.7 ns/元素 | ~7x（推算） |

行拷贝的 aten 一列取 §2.18.3 同轮比值反推（K 随 A 变），与 §3.2 的 §2.16.5 口径
（K≈32k）差 10-20%，那是规模效应；算倍数要用同轮的两个数，不要跨表除。

**这正是"vs aten 只有 1.5-3x 从来不代表接近硬件"的含义**：两边常同时贴着各自的下界，
比值只说明谁先离开这条下界。

### 3.4 它为什么拿不到：瓶颈清单

| # | 瓶颈 | 硬件依据 | 量级 |
|---|---|---|---|
| B1 | 每行/每元素一次**依赖取数**，行与行之间不重叠 | 137ns ÷ 1 条在飞 | 15x |
| B2 | 行内也是**逐元素标量拷贝**（A=256 时每行 1149 拍 ≈ 4.2×137ns） | 行内 16 条 line 只摊到 ~4 条在飞 | 2.7x |
| B3 | 每元素越界检查 + 负索引归一 | 227 指令/行（A=16） | 高线程时进位主因 |
| B4 | int32→int64 转换遍 | K×12B 流量；K=2.1M ≈ 25MB ≈ 1.3ms@1t | 1-4% |
| B5 | TensorIterator 逐行回调（`loop_2d_from_1d`） | 55.5% 周期 | 与 B3 同源 |
| B6 | mask 先 `nonzero` 物化再 gather（两遍 + 中间数组） | 两遍带宽 | 小 K 时被固定开销放大 |
| B7 | 多索引/广播每维算 offset | 每元素更多整数运算 | 中低线程 2-3x |
| B8 | 高线程下每核仍 ~1 条在飞 | 8t 仍 0.9（§2.19.2） | 吃不到带宽，见 §5.2 |

### 3.5 一个反直觉：aten 在多线程也没救

8t 时 aten 的 `cyc/行` 仍是 318（1t 是 322），即**每核还是等一条 line**；它只是
把同样的等待并行了 8 份。所以"多线程能追平"这个直觉在**每个线程各自等延迟**的
形态上不成立——除非每核的在飞条数也上去。

## 4. 本仓现在在哪

这一章回答"我们现在离硬件有多远"。四个列的口径先说清楚，否则很容易读错：

- **现状**：本仓在这个形态上的实测 ns/行（或 ns/元素）。
- **在飞**：由实测**反推**——`137ns × 行line数 ÷ 每行成本`。A=16 是 24ns/行、1 条
  line/行，于是 `137 ÷ 24 = 5.7` 条。反推值只有 A=16 那一行有 perf 的独立实测可以
  对照（也是 5.7，吻合），其余按同一公式推。
- **下界**：探针在**同一形态、同一线程数**下跑出来的最好值（§1.4 的两种下界之一）。
- **剩余** = 现状 ÷ 下界；**对 aten** = aten ÷ 现状。两个比值都是越大表示"还有空间"
  或"已经更快"，方向一致但含义不同，别混着读。

### 4.1 行拷贝族（H1 之后，1t，8MB 输出/16MB 源）

`现状`取 §2.18.3 的"按默认 D 跑"列；`在飞`由 `137ns ÷ 每行成本 × 行内 line 数` 估，
A=16 那一行同时给 perf 实测值（§2.19.5）；`下界`取探针里已跑出来的最好合法写法。

| 形态 | 现状 ns/行 | 在飞 | 下界 | 剩余 | 对 aten |
|---|---|---|---|---|---|
| A=3（12B） | 26.9 | 5.1 | 20.8（4 行流水） | 1.3x | 4.99x |
| A=16（64B） | 24.0 | **5.7（perf）** | 11.4（预取 16） | 2.1x | 6.33x |
| A=32（128B） | 34.0 | 5.9 | ~19（2 条 line/行，按 9.6/line 推） | ~1.8x | 5.94x |
| A=64（256B） | 44.3 | 12.4 | 38.4（预取 8） | 1.15x | 5.68x |
| A=128（512B） | 117.5 | 6.1 | —（8 条 line/行，无干净探针） | — | 3.12x |
| A=256（1KB） | 225.7 | 9.7 | 关掉预取 | —（行内已满窗口） | 2.41x |

读法：

- H1 把整族抬了一档（A=3 79→27、A=16 83→24、A=64 108→44），剩余从 2.6-7.1x
  收窄到 **1.15-2.1x**。
- **A=16 的 2.1x 不在"多发 prfm"上**：稳态斜率 19.4ns/行 对下界 11.4 差 1.7x，
  账是每行的检查/地址计算（+26 条指令/行，1t 上 105 vs 80）+ 固定成本 0.54ms。
- **A=3 只剩 1.3x**：预取与探针的 4 行流水是同一机理，没有第三个杠杆。
- **A=64 只剩 1.15x**：行内 4 条 line 本身提供 4 条在飞，预取边际小。
- **A=256 不要预取**：行内 16 条 line 已经占满窗口（hpc 369 拍/行 ≈ 1.35×137ns），
  再加 D 行预取只会占队位。

### 4.2 1D 元素族：两条子族、两种下界

**(a) 大值域（源 > L2，DRAM 下界）**：`single_1d_sve` / `single_1d` /
`bucket_gather_pure_raw` 的落选形态。1t 现状 **22.3 ns/元素**，6.1 条在飞，
下界 5.65 → **剩 3.9x**，对 aten 1.31x（已兑现 25%）。

**(b) 小值域/桶化（dom≤2048，L1 下界）**：这是生产里最贵的三格。用 §2.20 的
"每线程口径"算（`K/t` × 每线程 ns）：

| 格子 | K | t | 耗时 µs | 每线程元素 | 每线程 ns/元素 | 对 0.7 下界 | 结构 |
|---|---|---|---|---|---|---|---|
| SGI `K13824` | 13824 | 12 | 32.9 | 1152 | **28.6** | 41x | 固定成本 + 串行段 |
| PPT `K55296` | 55296 | 19 | 46.9 | 2910 | **16.1** | 23x | 遍数 + 串行表填充 |
| Sonata `K256000` | 256000 | 6 | 193.4 | 42667 | **4.53** | 6.5x | **1 条在飞** |

三格不能用同一个动作修，这是本文最重要的操作性结论（详见 §5.3、§7-H2/H4/H7）。

### 4.3 宽行高线程：指令墙先到

同一格 r16（A=16，64B/行），8t（`D=0` = 关预取、`D=16` = 默认档，见 §3.2）：

| 指标 | hpc D=0 | hpc D=16 |
|---|---|---|
| 周期/行（每核） | 192 | **121** |
| 指令/行 | 326 | 326 |
| IPC | 1.70 | **2.69** |
| 缺行/行 | 1.05 | 1.06 |
| 等效在飞/核 | 1.5 | 2.4 |

8t 上每核 121 拍搬 64B、要发 326 条指令（IPC 2.69，已经贴近 4 宽的上限）。
**内存侧还有 16-20 条的窗口可用（2.4/16），但指令侧先满了**——所以高线程的对手是
**每行的指令数**（线性化 + 逐行记账），不是"再多发预取"。同理 A≥128 在 16/36t
掉到 0.80-0.89x，而 `index_select` 在同形态上是我们的 2 倍（§2.16.5）。

### 4.4 其余路由的位置（细节见 `path-matrix.md`）

| 路由 | 结构上限 | 现状（§2.14.1） | 一句话 |
|---|---|---|---|
| `rowcopy_direct`（R10） | 块拷贝，接近带宽 | 1t 11.4x、8t 3.6x | 判据本身就是最大开关，翻面慢一个数量级 |
| `small_single` / `small_multi` | 省掉 normalize + 通用路由的固定成本 | 1t 2.1-12.8x、8t 1.6-2.6x | 收益随线程数衰减，价值在"小调用的固定账" |
| `strided_rows` | 有连续 run 就值块拷贝 | 1.7-3.5x | run 判据本身只值 1.1-1.55x |
| `rowcopy_fused`（多索引） | 块拷贝 + 广播 | 8t 2.47x / 16t 2.52x | 线程门（≥16）两侧差 2.26x |
| mask 单遍 | ATen 的 `nonzero` 固定成本 + 两遍带宽 | 0.77-2.55x（不稳） | 规模一上来回到 1x，必须分档读 |
| 两遍模型（linearize） | 多一遍下标扫描 + fork-join | 1t 1.1-6.8x；8/16t 在 1D 小源 0.96-1.10 | 行 gather 上不亏，1D 小源上把正收益吃成负 |
| `gather_direct`（K<1024） | 逐元素 + 每元素边界检查 | 0.19-1.45x | 只是兜底；K 小但 A 大是**路由悬崖** |

### 4.5 汇总：族 × 现状 × 下界 × 已兑现

`已兑现 = 现状比值 ÷ 可达上限`（同形态同线程，1t）：

| 族 | aten | 现状 | 比值 | 可达上限 | 已兑现 |
|---|---|---|---|---|---|
| 1D 大值域 gather | 29.2 ns/el | 22.3 | 1.31x | 5.2x | **25%** |
| 短行 A=3 | 134 ns/行 | 26.9 | 4.99x | 6.4x | **77%** |
| 整行 A=16 | 152 | 24.0 | 6.33x | 13.3x | **48%** |
| 宽行 A=64 | 252 | 44.3 | 5.68x | 6.6x | **87%** |
| 超大行 A=256 | 531 | 225.7 | 2.41x | 2.7x | **88%** |
| 桶化（大 K，L1） | 见 §4.2 | 见 §4.2 | 0.71-1.20x | 6.5x（Sonata 口径） | 15%（Sonata） |
| 桶化（小 K） | — | — | 0.74-1.62x | 取决于固定成本 | 不可比 |

前四行的可达上限 = `aten 耗时 ÷ 探针下界`（同形态、同线程数）；桶化没有可比的 aten 上限
（aten 没有桶化），只能用 §2.20 的 L1 下界，因此单列。

**"已兑现"这一列同样按裸探针算**，它回答"离最理想的循环还差多远"，不回答"能拿到多少"。
后者要再叠一层固定成本地板，见 §6.5——两者能差 3-20 倍（桶化三格尤其明显）。

## 5. 差距分解：每一纳秒的账

本章把 §4 的"剩余"拆成具体项：这 2.1x 里，几成是预取不够、几成是指令太多、几成是
固定成本。**拆不开的差距就等于没有差距**——它没法变成行动。

### 5.1 行拷贝 1t：19.4 vs 11.4

| 项 | 量 | 依据 |
|---|---|---|
| 稳态斜率 | **19.4 ns/行** | §2.18.5（K=131072/262144 两点拟合） |
| 探针下界（A=16，预取 16） | 11.4 | §2.16.4 |
| 差 | **8.0 ns/行（1.7x）** | |
| 其中：预取记账 | ~12 拍 ≈ 6 ns/行 的指令窗口 | §2.19.5（105 vs 80 指令/行，IPC 2.14） |
| 其中：越界检查/地址计算 | 其余 | H6 的目标 |
| 固定账 | 0.54 ms/调用 | 只在小 K 时影响 ns/行 |
| 指令侧对照 | 105 指令 ÷ 39 拍（19.4ns）≈ IPC 2.7；实测 23.5ns/行 那一档 IPC 2.14 = 49 拍 | §2.3/§2.19.2 |

**这两个数怎么来的**。19.4 是拟合出来的斜率：把 K=131072 与 K=262144 两点的总耗时
代进 `t = F + c·K`，解出 `c`。用两点而不是一点，是为了把固定账 `F` 消掉（K 越大，
`F` 的占比越小，斜率越接近真实边际成本；单点除法会把 `F` 摊进来，小 K 时能差 2-3
倍）。11.4 则是**探针**：`rowgather` 的 `pf16` 写法在同样的 16MB 源上跑到 11.4ns/行，
它没有下标检查、没有负归一、没有固定账——所以它是"同样的访存模式下，代码能有多快"，
不是"我们现在的代码该有多快"。

**这 8ns 不是"还能再预取"**：105 条指令即便跑满 IPC 4 也要 26 拍（13ns），比 11.4ns
的探针下界还高；何况实测 IPC 只有 2.14-2.7。**要往 11.4 走，必须同时砍指令（H6）**；
只调 D 会在交叉点上来回摆（§2.18.2 里 A=16 的 D=24/32 与 D=16 打平就是这个原因）。

### 5.2 行拷贝 8t：从"等内存"变成"发指令"

- 每核 121 拍/行、326 指令/行、IPC 2.69：**指令侧已经接近上限**（与内存墙 114 拍
  重合，见 §2.3）。
- 同一行只有 1.06 条 line，内存窗口 16-20 条里只用了 2.4 条。
- 所以 8t 的 2.4 → 16 条在飞不会带来 6x：**要先砍指令**。粗算：326 条降到 ~120 条
  （1t raw 的量级），121 拍可降到 ~45 拍，还有 2-2.5x——这就是 H3/H6 的位置。
- 反过来说，如果只加预取距离（D 更大）而不砍指令，8t 会在指令墙上撞死（§2.18.2
  里 A=64 8t 的 D=16 崩到 30.6ns 就是这个机理 + 队列挤爆）。

### 5.3 桶化：三种结构，三张账

桶化的输出段是一句 `dst[k] = table[v[k] - mn]`：一次**串行**的小表查表。它该值多少？
现在可以算准了——§1.1 的 `chase` 给了 L1 命中 = **2.0ns（4 拍）**，所以一次串行查表
就是 2.0ns/元素；两遍（先算 `v`、再查表）就是 4.0ns/元素。把这个尺子架到三格上：

| 格子 | 每线程元素 | 实测 ns/元素 | 其中"查表"该占 | 剩下的 |
|---|---|---|---|---|
| SGI | 1152 | 28.6 | ≤4.0（两遍） | **≈25 ns/元素**，即整次 ~28µs |
| PPT | 2910 | 16.1 | ≤4.0（两遍） | **≈12 ns/元素**，即整次 ~35µs |
| Sonata | 42667 | 4.53 | 2.0（一遍） | **≈2.5 ns/元素**，即整次 ~107µs |

**SGI K=13824/12t（28.6 ns/元素）**：每线程只有 1152 个元素。两遍查表合计只有
4.6µs，实测 32.9µs——**28µs 以上是固定成本与串行段**：两次 `parallel_for` 的
fork-join、串行归约（`vmn/vmx` 合并）、串行表填充（`dom=2048` 个元素）、入口开销。
**这一格的第一杠杆是 H4/H7，不是 H2**：即使把查表压到零，也就省掉 4.6µs（14%）。

**PPT K=55296/19t（16.1 ns/元素）**：每线程 2910 个元素。两遍查表 11.6µs，实测
46.9µs，缺的 **35µs** 落在**表填充（串行）+ 两次 `parallel_for` 的 fork-join + 入口**
（仍未逐项分离——这是下一轮要补的测量，见 §9.7）。杠杆是"遍数 + 串行段"；H2 能把
查表那 11.6µs 的大部分藏掉，但拿不到数量级。

**Sonata K=256000/6t（4.53 ns/元素）**：每线程 42667 个元素。一次串行查表 2.0ns，
占 4.53 的 44%；剩下 **2.5ns/元素**（≈107µs）是每元素的整除/取模、边界、写回与
循环——**没有在飞，整数账也没省**。这一格是纯 H2b：把 `v` 批量算好再一起取表，让
查表这 2.0ns 被多条在飞摊掉。

> Sonata 的 2.5ns 是什么，目前是**推断**（按"总时间 − 一次 L1 命中"倒推，没有逐条
> 指令的记账）。它决定 H2b 的天花板：如果这 2.5ns 也能压到探针的水平，193µs →
> **30-40µs**；如果压不下去，光把查表摊掉只有 193 → **~107µs**。所以 H2b 的第一步
> 不是改代码，而是**先量这个 2.5ns**（`perf` 的每元素指令数 + 一个只做整数运算的
> 微循环）。这就是 §9.1 第一条在实操里的样子：**先量下界，再动手**。

三格的共同点只有一个：**都不在 DRAM 上**。上一版把它们记成"剩余 3.7x、H2 杠杆最大"
是把 Sonata 的结构套到了 SGI/PPT 上，而且当时用的 L1 延迟是 5.07ns（含探针开销），
于是把"查表"的份额高估了 2.5 倍——**分母错了，杠杆就指错了**。

### 5.4 宽行 A=256：行内并行已经够

hpc 369 拍/行 ≈ 1.35×137ns：16 条 line 基本落在同一个延迟窗口里。aten 是 1149 拍
≈ 4.2×137ns。所以这一格的差距（1t 531 → 226ns）来自 **aten 行内 line 之间没并行**，
而本仓已经接近"行内 16 条全在飞"的极限；再往上只能靠**行间**并行，而 1KB/行 × D
行预取会把窗口挤爆（实测全档为负）。**2.41x 的剩余很小（上限 ~2.7x）**。

### 5.5 小 K：固定账

`F ≈ 0.54 ms`（8MB 输出）与 §6.5.2 的 10.0/15.7µs（小调用）是同一件事的两种口径：
**入口 + fork-join + 输出分配 first-touch**。K≲32768 时它把 ns/行 抬 2-3 倍，
且**预取前后不变**（§2.18.5 两列同 F）。要动它只能削遍数（H5）或改分配/回收
策略（H7）——这是小 K 场景唯一剩下的数量级空间。

### 5.6 路由悬崖：不是内核问题

- `K<1024` 的短路排在所有行拷贝路由之前 → "K 小但 A 大"落到标量直取
  （cl4d K=512 vs 1024 差 5.2-5.4 倍，§2.14.3）。
- 值域门 2048/2049 两侧差 1.46-1.98 倍（§2.14.2）：桶化接管与不接管的台阶。
- 下标 i64 vs i32：`r9_big_i32` → `r6_sve` 1.10-1.44 倍，同一形态换下标宽度就掉
  到两遍模型上。

这些都是**判据顺序**造成的，修法在 H5/`path-matrix.md` §5，不在本文的"在飞条数"。

## 6. 端到端：理论上限能换多少

### 6.1 现状

15 个生产形态的 `aten/hpc` 是 **0.71-3.03x**；按反馈热点表加权后 **1.28-1.30x**
（§2.12.2，**H1 之前**的构建，H1 之后没有再跑一遍加权）。H1 只动行拷贝形态，而三
个模型里行拷贝的耗时份额是 9-41%（SGI 最大），按 §2.18.4 的 1.3-2x 推算，**SGI 会
到 ~1.4-1.6x、另外两个 ~1.3-1.45x**；这一条是推算，不是测量。

**耗时排名与收益排名不一致**（这是端到端分析的起点）：

| 模型 | 最贵形态 | 占 hpc 时间 | 当前比值 |
|---|---|---|---|
| SGI | `bucket_K13824_dom2048` | **37%** | **0.86x** |
| PPT | `bucket_K55296_dom2048` | **33%** | **0.71x** |
| Sonata | `bucket_K256000_dom2048` | **39%** | 1.20x |

### 6.2 逐格上限：下界 → 地板，要打两次折（推算，±50%）

§5.3 已经把三格的账拆开了。但"下界"回答不了"能到多少"，因为它**不含固定成本**，
而这三格每线程只有几千个元素，固定成本摊下来不是小数。正确的做法是：

```
每元素地板 = 固定成本 ÷ 每线程元素数  +  该族的下界（在飞化之后用 max，不是相加）
空间       = 现状 ns/元素 ÷ 地板 ns/元素
```

固定成本不是估的：`T = F + c·K` 拟合（degradation §6.5.2）给出 hpc 6t **14.9µs**、
12t **15.5µs**、19t **15.7µs**，其中"空 parallel region"两趟 6.4µs（19t）、
`x[idx]` 的空调用入口 5.8µs——**这三项就是地板的全部原料**。

| 格子 | 每线程元素 | 现状 | 固定成本摊到每元素 | 保守地板（固定成本不变、只在飞化） | 空间 | 理想地板（固定成本压到 10µs、单趟） | 空间 |
|---|---|---|---|---|---|---|---|
| SGI K13824/12t | 1152 | 28.6 | 13.5 | 13.5 + 1.4（两遍 ×0.7） = **14.9** | **1.9x** | 8.7 + 0.7 = 9.4 | 3.0x |
| PPT K55296/19t | 2910 | 16.1 | 5.4 | 5.4 + 1.4 = **6.8** | **2.4x** | 3.4 + 0.7 = 4.1 | 3.9x |
| Sonata K256000/6t | 42667 | 4.53 | 0.35 | 0.35 + max(0.7, 2.15) = **2.5** | **1.8x** | 0.23 + max(0.7, 1.08) = 1.31 | 3.5x |

三个读法，每一个都能对上一个实测数：

- **SGI 的 41x 是假的**：光固定成本就有 13.5ns/元素，比下界 0.7 大 19 倍。把查表压到
  零，这一格也只从 32.9µs 掉到 15.5µs（2.1x）——**41x 里的 39x 是"不可能付的账"**。
- **Sonata 的 6.5x 也是假的**：它要求 4.53 → 0.7（连整数账一起归零）。而实测里
  2.15ns/元素是整除/取模 + 写回 + 循环，**不会因为批量化而消失**。批量化只能把
  2.0ns 的串行查表摊进吞吐，于是 4.53 → 2.5ns（**1.8x**）。要再往上，得单独砍整数账
  （2.15 → ~1.0），那才到 2.2-3.5x。
- **PPT 的 2.4x 比它看起来的样子重要**：它现在是 0.71x（唯一明显慢于 aten 的格子），
  而固定成本 15.7µs 占 46.9µs 的三分之一。**这一格的空间主要不在内核，在"每次调用
  都要付的那笔钱"**。

### 6.3 端到端：热点加权 1.3 → 1.6-1.9x，全程 1.05 → 1.2-1.3x

把 §6.2 的三格代进 §2.12.2 的耗时份额（其余形态不动，`加权 = Σ 份额 × 比值`，这是
§2.12.2 的口径；它**不是**总耗时之比，别混）：

| 模型 | 现在 | 三格到"保守地板" | 再叠加行拷贝 H3/H6（1.1-1.4x，§5.2） | 理想线 |
|---|---|---|---|---|
| SGI | 1.30x | 1.58x | **~1.9x** | ~2.0x |
| PPT | 1.28x | 1.59x | **~1.8x** | ~1.9x |
| Sonata | 1.28x | 1.51x | **~1.6x** | ~1.8x |

**为什么不是 2.5x 以上**：上一版写"1.7-2.5x 可达"，用的是"(B) SGI 6-8µs / Sonata
5x"，那两个数都低于实测地板——SGI 的 6-8µs 比"空 parallel region 两趟 6.4µs + 入口
5.8µs"还小，Sonata 的 5x 要求整数账归零。**按实测地板重算，稳妥线是 1.6-1.9x，
理想线 1.8-2.0x**。差的那 0.5x 只能来自"连固定成本都换掉"（H7 改分配/复用输出）。

**全程口径还要再打一次折**（这是最容易被忽略、也最有说服力的一个数）：

| 口径 | 覆盖 | 现在 | 空间 |
|---|---|---|---|
| 热点加权 | 23-40% 的**调用** | 1.28-1.30x | 1.6-1.9x |
| 全程① / 全程③ | 100% 调用 | **1.05-1.10x** / 0.58-0.67x | 1.2-1.3x |

反解一下：设热点占全程 hpc 时间的一半，由 `1.10 = 0.5×1.30 + 0.5×R_rest` 得
`R_rest ≈ 0.90`——**长尾形态目前比 aten 略慢**。把热点从 1.3 提到 1.9（时间 ÷1.46）
再代回去，全程只有 **~1.25x**。所以"再优化 1.5 倍"和"用户感知再快 1.5 倍"差得很远，
中间隔着覆盖率——这是 §6.5.6 的结论。

### 6.4 不确定性的三个来源

1. **探针到内核的损耗**：§2.20 的下界是裸循环；内核还要读下标、做越界检查、
   写输出、分摊固定成本。经验折扣 1.5-2x。
2. **整数除/取模与 `adaptive_grain`**：桶化每元素要算 `p/K`、`p - (p/K)*K`
   （§4.2 代码），这批整数运算在批量化之后会成为新墙——**这是 H2 的隐藏成本**，
   也是 §6.2 里 Sonata 只用 max 而不是相加的原因。
3. **覆盖率**：加权只覆盖 23-40% 的调用，全程口径仍夹在 1.0 附近；**任何"再快 2x"
   的说法都必须说明它作用在这 23-40% 上，还是全量上**。

### 6.5 还有多大空间：三把尺子、一条优先级

这一节只回答一个问题：**从"离理论上限还远"这个角度看，当前实现还有多大提升空间。**
答案不是一个数，而是三个数——取决于你拿哪把尺子。

#### 6.5.1 三把尺子，别拿错

同一个格子（Sonata K256000/6t，193.4µs）用三种口径量，答案差 5 倍：

| 尺子 | 答案 | 这个数回答了什么 | 什么时候会用错 |
|---|---|---|---|
| **裸探针下界**（0.7 ns/元素） | **6.5x** | "如果整数运算也不要钱、固定成本也不要钱" | 拿它当目标 → 承诺 6x，交付 1.6x |
| **实测地板**（§6.2：2.5 ns/元素） | **1.8x** | "在同样的结构与同样的固定成本下，把串行查表在飞化" | 拿它当全部 → 漏掉"改结构可以降地板" |
| **端到端加权**（§6.3） | **+0.23x**（1.28→1.51） | "用户能感知到多少" | 拿它当悲观 → 忽略它只覆盖 39% 的时间 |

三把尺子都合法，**混用才不合法**。本文所有"还剩多少"的表述现在都标了口径；下面
这张表是三个族 × 三把尺子的完整对照，可以直接当"承诺-交付"的换算表：

| 族 / 格子 | 现状 | 裸探针下界 | 实测地板 | **能拿到的空间** | 端到端份额 |
|---|---|---|---|---|---|
| SGI K13824/12t | 32.9µs | 41x（对 0.7） | 14.9 ns/元素 | **1.9-3.0x** | 该模型 37% |
| PPT K55296/19t | 46.9µs | 23x | 6.8 ns/元素 | **2.4-3.9x** | 33% |
| Sonata K256000/6t | 193.4µs | 6.5x | 2.5 ns/元素 | **1.8-3.5x** | 39% |
| 行拷贝 A=16（稳态） | 24.0 ns/行 | 2.1x（对 11.4） | 13.1 ns/行（指令墙） | **1.8-2.1x** | 9-41% |
| 行拷贝 A=3 / A=64 | 26.9 / 44.3 | 1.3x / 1.15x | 同左 | **1.15-1.3x** | 同上 |
| 行拷贝 A=256 | 225.7 | —（无干净探针） | 行内 16 条已满窗口 | **≈1.0-1.2x** | 同上 |
| 1D 大值域 gather | 22.3 ns/el | **3.9x** | 5.65 ns/el | **3.9x，但端到端 = 0** | 0% |

**最后一行是这张表最值钱的地方**：单形态空间最大的那一族（3.9x），在生产里一例都
没有。**按"离下界多远"排优先级会把你带到没有用户的地方**；必须同时看份额。

#### 6.5.2 三个"看起来很大、其实拿不到"的空间

| 看起来的空间 | 真实的空间 | 差在哪 | 依据 |
|---|---|---|---|
| SGI 41x | **1.9x** | 固定成本 15.5µs，摊到 1152 个元素是 13.5ns/元素 | §6.2；degradation §6.5.2 |
| Sonata 6.5x | **1.8x**（再砍整数才 2.2-3.5x） | 2.15ns/元素是整除/取模 + 写回，不是查表 | §5.3 的减法 |
| 1D 大值域 3.9x | **0** | 15 个生产形态里没有一例 | §2.12.2 |

反过来，真正能换到时间的三件事，按端到端收益排序：

| 动作 | 单格 | 端到端 Δ（加权） | 成本 | 依据 |
|---|---|---|---|---|
| **H4/H7 固定成本**（两趟 → 一趟、复用输出、砍串行段） | SGI 1.9x / PPT 2.4x | **+0.29 / +0.31** | 中（改结构，不动内核） | 15.5/15.7µs 实测地板 |
| **H2b 桶化输出段批量化** | Sonata 1.8x | **+0.23** | 中（SVE gather + 整数摊薄） | 2.0ns 串行查表 |
| **H3/H6 行拷贝砍指令**（高线程） | 121→45 拍（2-2.5x） | **+0.1-0.3**（看份额） | 高（重写线性化/记账） | §5.2 |
| H5 减遍数 | 含在上面 | 已计入 | 中 | 两趟 → 一趟 |
| H7 入口 10µs（小 K） | 小 K 调用 ×2 | 全程 +0.05-0.1，加权 ≈0 | 低 | §2.12.1 |
| H2a 大值域批量化 | 3.9x | **0** | 中 | 无生产形态 |

结论和直觉相反：**优先级第一不是"最贵的格子"（Sonata），而是"两格共同的那笔固定
成本"**——它同时抬高 SGI 与 PPT 的地板，而且改的是结构不是内核。这也是 §7 里
H4/H7 排在 H2b 前面的原因。

#### 6.5.3 这个预测怎么被推翻（三条可证伪的验收）

上面的数字都是"输入是实测、推论是模型"，所以必须写清什么时候算错：

1. **H4/H7 若真把 12t 固定成本压到 ≤10µs**，`bucket K13824/12t` 必须 ≤19µs
   （现在 32.9）。测出来还停在 28-32µs，说明"固定成本是主要账"这个判断错了，
   应回头查串行段（`vmn/vmx` 归约、表填充）的实际占比。
2. **H2b 之后若 Sonata 仍 ≥150µs**，说明"2.0ns 是串行查表"的归因错了。验证方法：
   换成"只做整除/取模、不查表"的微循环，看是否也接近 2.15ns/元素（§9.1 的下界法）。
3. **加权比值若提不到 1.5**，先别改代码，先看覆盖率有没有变（23-40%）——**分母换了，
   任何"提升"都不可比**。

#### 6.5.4 一句话

**从"离下界"看还有 2-6.5x，从"能拿到"看是 1.6-1.9x（热点）/1.2-1.3x（全程）。**
再往上不是内核问题，是覆盖率问题：长尾形态（占 60-77% 的调用）现在约 0.9x，
把它们做到 1.2x 的收益，比把 Sonata 从 1.8x 做到 3.5x 更大。

## 7. 欠账清单

按"投入产出 + 覆盖面"排序，编号与 `status.md` §7 一致。**排序依据是 §6.5 的端到端
Δ（加权），不是单形态倍数**——所以 H4/H7（固定成本，两格共同的地板）排在 H2b
（最贵的单格）前面。

### H1 行拷贝软件预取 —— 已实做

`rowcopy_raw_single` / `rowcopy_sve` 提前 D 行读下标、对行首地址发 `prfm pldl1keep`，
D 按行字节分档（≤64B→16、65-512B→8、>512B→关）。实测 1t 2.26-2.91x、64MB 源
3.05-4.20x（§2.18）。perf 证明缺行数不变、周期掉 2.5-3.1 倍（§2.19.5）。
**剩下的 1.15-2.1x 不在预取本身**，见 H6。

### H2 "算完一批再取" —— 分两个子项，别混为一谈

上一版把 H2 写成"1D 元素 gather 批量化、端到端杠杆最大、预期 2-3.5x"，并把它
指向"大值域 1D gather"。**修正**：

- **H2a（大值域 1D，DRAM 下界）**：现状 22.3 → 下界 5.65 ns/元素（3.9x），
  但 15 个生产形态里**没有一例**落在这里，所以端到端杠杆 ≈ 0。只对"1D 大值域"
  用户有单形态价值，优先级应低于 H2b。
- **H2b（桶化输出段，L1 下界）**：`dst[k] = table[v-mn]` 现在是**一条在飞**的
  查表（Sonata 4.53ns/元素 = 2.0ns 串行查表 + 2.15ns 整数 + 0.35ns 固定成本）。
  只对"每线程元素数 ≥ 1 万"的格子有效（Sonata K=256000/6t，占该模型 39% 时间）。
  **预期要按地板算（§6.2）**：只把查表在飞化是 **1.8x**（193→108µs）；再把整数账
  砍半才到 2.2-3.5x。上一版写的 4-5x 假设"整数免费"，已被 §6.2 否掉。e2e：Sonata
  1.28 → 1.51（+0.23）。
- **对小 K 的桶化（SGI/PPT）无效**：它们的账是固定成本与串行段，批量化只值
  1.2-1.4x。

### H3 两遍模型的输出段（高线程）

`A ≥ 128` 在 16/36t 掉到 0.80-0.89x，`index_select` 在同形态是 2 倍（§2.16.5）。
perf 显示 8t 每核 121 拍/行、326 指令/行、IPC 2.69——**是指令墙不是内存墙**。
欠的是 linearize 的逐元素记账 + fork-join。预期 **1.5-2.5x**（宽行高线程）。

### H4 去掉桶化的串行段

值域归约与建表是串行的（§4.2 代码：`vmn/vmx` 合并、`table` 填充），19t 上合计
4.4µs（§6.5.2），SGI 那种"每线程 1152 元素"的格子里它占大头。改成每线程局部桶 +
一次性合并。预期 **1.2-2x**（小 K 桶化），主要价值是把"高线程反而更差"翻正。

### H5 减少遍数与 fork-join

`K<1024` 的短路悬崖（同 A、K 减半慢 5.2x，§2.14.3）是路由顺序；两遍模型在 1D
小源 8t 只有 0.96-0.98（§2.14.3）。这一条不是提速，是**堵漏**，但堵住以后
小 K 的 1.5-3x 才拿得到。

### H6 预取记账的 26 条指令/行（H1 的尾巴）

1t 每行多 26 条指令（80→105），在 49 拍/行里约 12 拍；8t 上 326 条/行、IPC 2.69，
记账的占比更高。把"读 `idx[k+D]` + 越界判断 + 地址计算 + `prfm`"改成**每 4 行
一批**（一次读 4 个下标、算 4 个地址、发 4 条 `prfm`）。预期 **1.1-1.2x（1t）**，
高线程更多；附带给 `strided_rows_raw` / `rowcopy_fused` 也加上预取。

### H7 每调用固定成本 ≈ 0.54ms

`t = F + c·K`，F ≈ 0.54ms（§2.18.5）；K≲32768 时把 ns/行 抬 2-3 倍，且预取前后
不变。要动它得看输出分配的 first-touch（8MB = 2048 次缺页）与两遍 fork-join。
对小 K（SGI 的 1152 元素/线程）这是**第一杠杆**。预期 **1.5-3x**（小 K 场景）。

### H8 路由悬崖（从 R1 提级）

`K<1024` 短路把"小 K 宽行"挡在行拷贝之外（cl4d 5.2-5.4x）。修法是把宽行从短路里
摘出来单独判，而不是优化 `gather_direct`。与 H5 同源，但它是**判据顺序**问题，
放在内核改造之前做更划算。

## 8. 负结果与陷阱

- **指令/SVE 指令延迟**：不是瓶颈（64B 拷贝下界 1.26ns，比实现低 1-2 个数量级）。
- **SVE gather**：不比标量展开差（4.73 vs 5.79），但一批只有 8 lane；能不能用
  取决于能否多条在飞。
- **非临时存储**：收益 0。
- **大页（THP）**：收益 0。
- **手工展开循环**：CHAINS=1 就 ~10ns，展开到 32 只快 42%；要提在飞条数必须把
  地址计算挪到取数之前。
- **"32KB 工作集"不能当 L1 常驻**：1.45-1.76ns/元素且不随 CHAINS 改善（set 冲突）。
- **套错下界**：把小值域桶化套到 5.65ns（DRAM）会把空间估大 8-9 倍；把大值域
  1D 套到 0.7ns 会低估。
- **用 145GB/s 的拷贝上限给小副本建模**：8MB 的 `clone` 在 8/16t 只有 53/72 GB/s，
  照最大值算会**高估**收益（小副本被固定开销和每线程粒度拖住）。
- **排序/通用桶化**：把随机变顺序能到 168GB/s，但 `O(K log K)` 的代价远超访问
  本身；只有"下标静态 + 反复调用"才划算。
- **拿 32/36t 的比值当收益**：aten 在高线程自己会变慢，比值里混着它的劣化。
- **"按线程数收缩预取距离"**：实测没有收益，真正的变量是行字节。

## 9. 方法论：这些数是怎么测出来的

这一节写给两种人：想复核某个数字的人，以及想在别的机器上把同一套测量重做一遍的人。
它不讲结论，讲**步骤**——同一个数，怎么设计测量、怎么知道测得对、怎么避免骗自己。
（如果只关心结论，可以跳过本节直接看 §10。）

### 9.1 五条原则

1. **先量下界，再看实现**。不要一上来就 perf 自己的代码——你无法判断 24ns/行 是好
   还是坏。先写一个只做同一件事的最小循环（`rowgather` 的 `pf16`），量出"这台机器
   在最好的写法下能到多少"，再拿实现去对。**没有下界的性能数字是没有意义的。**
2. **一次只改一个变量**。想证明"预取有用"，就造出两个版本：除了预取以外全都一样
   （同样的源、同样的行数、同样的循环体）。任何两个因素一起变，结论就归因不了。
   本文里 `rowgather` 的 `plain`/`pipe`/`pf8`/`pf16` 就是这个手法的产物。
3. **交叉验证**。一个重要结论至少要有两条独立证据。例：§1.2 的"16-20 条在飞"来自
   S 曲线（吞吐）；再用"带宽延迟积"（延迟 × 带宽）算一遍，两条路给出同一个数，才
   说明它不是探针伪影。
4. **要相除的两个数必须同一轮取**。不同时间、不同线程数、不同 K 的两个数相除，误差
   能到 20% 以上（§3.3 的脚注就是这件事）。比值尤其是这样：aten 和 hpc 必须交替跑。
5. **新测的数字先落 RESULTS，再在别处引用**。文档里只写推导；原始表只有一个出处，
   冲突时以它为准。

### 9.2 探针要分三种形状

同一个"取数"动作，按你想测的东西，探针写法完全不同：

| 形状 | 它回答的问题 | 本仓的探针 | 设计要点 |
|---|---|---|---|
| **依赖链** | 一次往返要多久（延迟） | `latency SIZE_KB`、`mlp S=1` | 下一条地址必须来自上一条的数据，否则 CPU 会自己重叠 |
| **受控并发** | 能同时等几件事（窗口） | `mlp S`（S 条独立链） | 每条链内依赖、链间独立 → 在飞条数正好等于 S |
| **真实内核形状** | 内核实际能拿到多少 | `idxgather`、`rowgather` | 复刻 `load idx → load data` 的依赖关系与 line 放大 |

为什么必须分开：如果把三者混在一个程序里，你测到的既不是延迟也不是吞吐，而是三者
的混合物，任何结论都归因不了。**"先造出干净的自变量，再去测因变量"**——这是整套
方法里唯一真正需要动脑的地方。

### 9.3 一次完整的测量：从"怀疑"到"定案"

拿本轮最有意思的一次做例子：**1-4MB 的延迟缓坡，到底是不是某一级缓存？**（上一版
把它写成了"L3 混合带"，那是错的。）

**第 1 步：把结论写成可以被证伪的形式。** 不要写"这里大概是 L3"，要写"如果 45-86ns
这段缓坡是某一级缓存在命中，那么它的**命中率**应该显著高于 8MB 之后（那边是 7%）"。
这样就有了一个可以直接量的量。

**第 2 步：找一个能区分的观测量。** 时间本身区分不了——"命中率下降"和"单次 miss
变贵"都会让时间变长，但它们的解法完全不同（前者要改数据布局，后者要改访问模式或
认命）。计数器能区分：`l2d_cache_refill` 数的是"L2 没命中、真的去了内存"的次数。

**第 3 步：控制变量，同一轮取两个量。** 同一次运行里同时拿 `ns/访问` 和两个 refill
计数（`perf stat` 包住同一个进程），否则两次运行的噪声会伪装成相关性。

**第 4 步：验模型自洽。** 拿命中率反解"单次 miss 的代价"：

```
ns/访问 = (1 - m) × 8.6ns + m × miss代价      # m = L2 miss/访问，8.6ns = L2 命中
```

| 足迹 | `m` | 实测 ns/访问 | 反解出的 miss 代价 |
|---|---|---|---|
| 4MB | 0.85 | 85.7 | ≈99 ns |
| 8MB | 0.93 | 94.5 | ≈101 ns |
| 16MB | ≈0.99 | 110.5 | ≈111 ns |
| 64MB | 1.00 | 128.1 | 128 ns |

**miss 率已经饱和而延迟还在涨**（99 → 128ns），只有"单次 miss 变贵"能解释，缓存层
解释不了。于是假设被否掉，同时得到新结论。

（这个式子是"零阶模型"：把一切非命中都当成同一个代价。它不精确——L2 命中也不是
恒定 8.6ns、miss 也可能有预取干扰——但它足够区分"命中率下降"与"单次代价上升"这两
种解释，而这两种解释对应完全不同的修法。**建模的目的是分辨，不是复现。**）

**第 5 步：主动找反例（这一步最容易省，但最值钱）。** 换一个探针量同一个工作集：1MB
数组，`mlp` 给 26.1ns、`latency` 给 46.4ns，1.8x 的差。如果"1MB 的延迟"是硬件的
属性，两个探针不该差这么多。查下去发现：指针追逐沿的是**置换的环**，环长由种子决定
（18709 元素 vs 80318 元素），而环长才是真正的工作集。**于是 1MB 那一格被降级为
"不可当常数"，并在文档里写清楚**。这一步同时救了两个结论：大尺寸的曲线不受影响
（环长远大于 L2），而 1MB 那格从此不再被引用。

**第 6 步：说清能说什么、不能说什么。** 定案后文档里写的是"1-4MB 是命中率与单次
miss 代价的叠加；8MB 之后只剩后者，机理推断为 DRAM row buffer（TLB 已由 §1.7 排除）"
——**实测的写实测，推断的标推断**，并给出可推翻它的方法。这就是"专业"和"自信"的
区别。

**第 7 步（后来补的）：同一手法再自查一次，这次查出的是探针自己。** 用户追问"有效
容量 512KB 是怎么来的"，逼着我做"命中率 vs 足迹"的细曲线，于是写了一个新探针
`chase`（沿定长环走，足迹精确 = 数组大小）。结果它给的小尺寸数字**系统性比 `latency`
低 2.4-2.8ns**。差值是常量，说明不是"哪一级缓存"的事，而是 `latency` 的循环体里那个
`volatile` 下标：每轮都要写回栈再读出来，这次 store→load 转发（约 5 拍 ≈2.5ns）**落在
依赖链上**，于是每个点都被抬高一个常量。在 128ns 上无所谓（2%），在 2ns 上就是 130%
——**上一版写的"L1 = 5.07ns"正是这么来的**。教训：小尺寸测量对常量偏移极其敏感，
凡小尺寸结论都要换一个不同形状的探针复核。

复盘一下我最初错在哪：只看了**时间**曲线，没看计数。时间曲线上任何一段"没那么快也
没那么慢"的缓坡，都很容易被脑补成"某一级缓存在打底"；**只有计数器能证明命中发生在
哪一级**。所以从这次开始，本文所有"命中/未命中"的说法都必须有 refill 计数支撑。

### 9.4 十一个坑（症状 → 原因 → 修法）

| # | 症状 | 原因 | 修法 |
|---|---|---|---|
| 1 | 小规模测量完全不可信 | `import torch` 7.2s、建张量 2.9s | 用独立 C 探针；或两段相减（§2.19.1） |
| 2 | perf 的周期数是朴素预期的 4 倍 | 计数含进程启动与建表 | 跑 `acc=0` 版相减（§2.19.1） |
| 3 | 每访问的指令/周期数偏高 10% | 探针先跑了 `acc/10` 的预热，但 perf 也算进去了 | 除以 `1.1×acc` 而不是 `acc` |
| 4 | 同一台机器两次测差几十 ns | 没绑 NUMA，或内存来自远端 node | `numactl --physcpubind --membind` 成对写 |
| 5 | 第二个用例比第一个快很多 | 第一个用例把数据带进了缓存 | 每个用例重新分配/换工作集，或取多遍中位数 |
| 6 | **小尺寸延迟普遍偏高一个常量** | **探针把下标放在 `volatile` 里，store→load 转发落在依赖链上** | **换无 volatile 的定长环探针（`chase`）；或在 64MB 上标定偏移再减掉** |
| 7 | 工作集和数组大小对不上 | 指针追逐的环长 < n（§1.1） | 换种子看是否稳定；或改定长环（`chase`） |
| 8 | 比值波动 20% 以上 | aten 与 hpc 不是同一轮、或线程数/K 不同 | 同轮交替跑，比值只用同一轮的两个数 |
| 9 | 单线程收益算出 100x | 用聚合带宽（168GB/s）去推单线程 | 用每线程 ns（§2.4） |
| 10 | 加了预取反而更慢 | D 超过 MSHR 容量，把自己挤掉 | 按行字节封顶 D（§1.6） |
| 11 | "我们只差 1.5x，快到头了" | 两边都贴着各自的下界，比值说明不了剩余 | 用"现状 ÷ 下界"算剩余（§4.5） |

### 9.5 从测量到结论：四个换算

测量给的是 ns 和计数，结论要的是"还能快多少"。中间只有四个换算：

1. **ns ↔ 拍**：`拍 = ns × 2.0GHz`（本机实测 1.99GHz，§1.8）。
2. **周期 → 在飞条数**：`在飞 = 274 ÷ 每行周期`（274 = 137ns × 2GHz）。322 拍 →
   0.85 条；49 拍 → 5.6 条。这一个式子把 perf 的原始数据变成了"同时等几件事"。
3. **延迟 ÷ 在飞条数 → 下界**：`137 ÷ 16 = 8.6ns`。反过来，`下界 × 在飞条数 ÷ 137`
   告诉你"要想达到某个下界，至少需要几条在飞"。
4. **现状 ÷ 下界 → 剩余**；`现状比值 ÷ 可达上限 → 已兑现`。

**一个完整例子**（A=16 行拷贝，1t）：实测 23.5ns/行 = 49 拍 → 在飞 5.6 条 →
离下界 11.4ns 还差 2.1x → 但 105 条指令 ÷ IPC 4 = 26 拍 = 13ns 已经是指令侧的天花板
→ **结论：剩下的 2.1x 必须"同时"砍指令与抬在飞，单做一件只能拿到一点点**（§5.1）。
这条推理链上没有一步是猜的，每一步都能指回一个实测数。

### 9.6 误差怎么给

本文只在三种情况下给"±50%"这类区间，含义各不相同：

- **推算**（§6.2）：把实测的每线程 ns 乘上元素数，再叠加多个假设（固定成本会不会
  变、串行段能不能去掉）。误差主要来自假设，按 ±50% 读。
- **探针到内核的折扣**：裸循环没有下标检查/写回/固定账，实现通常要多 1.5-2x（§6.4）。
- **不同轮的比值**：同轮交替能压到 ±5%，跨轮可以到 ±20%（§3.3）。

反过来，**硬件常数的误差很小**：同一天、同一 node、3 遍取最好值，`latency` 的重复
性在 1-2% 以内（1MB 那格除外，原因是 §1.1 的环长）。所以"137ns""8.9ns/line"这类
数可以直接当常数用；"1.5-2x 收益"这类数必须带区间。

**顺便解释"取最好值"**：同一格连跑三遍，`rowgather pf16` 会给出 12.8 / 11.7 / 11.3ns
（RESULTS §2.16.4 的复测）——最差与最好差 14%，而它们量的是同一份代码。所以一条
经验：**报"硬件能力"用最好值，报"用户实际体验"用中位数，两者不能混着比**。本文里
所有"下界"都是最好值，所有"现状/比值"都是同轮交替跑出来的典型值。

### 9.7 复核清单

照这个顺序做一遍，本文的每个数字都能复现（命令在 RESULTS §2.16.7/§2.17.6/§2.20 末）：

1. `lscpu -C` + `numactl -H`：确认缓存层级与 node 划分（**别假设有 L3**）。
2. `memprobe freq 2e8` + `perf stat -e cpu_cycles`：确认主频，再换算拍。
3. `memprobe latency 256 3000000`：单点延迟，与 137ns 对照。
4. `for S in 1 2 4 8 16 32; do ./memprobe mlp 256 $S 1e8; done`：画出在飞曲线，
   读出窗口与饱和吞吐。
5. `for t in 1 8 16 38; do ./memprobe bandwidth 2048 $t rd; done`：确认带宽顶。
6. `for M in plain pipe pf8 pf16; do ./memprobe rowgather 16 16 1 200000 $M; done`：
   确认预取的下界与边界（A=16 那行是 52.6 → 11.4 的来源）。
7. `./memprobe idxgather 0.008 1e8 1 16` 与 `./memprobe idxgather 16 1e8 1 32`：
   两种 gather 下界（L1 0.7 vs DRAM 5.65 ns/元素）。
8. `perf stat -e l1d_cache_refill,l2d_cache_refill`：命中率归因（**这一步决定你信
   不信"缓存"这类解释**）。
