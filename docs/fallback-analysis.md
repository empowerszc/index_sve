# 慢场景与回退路径深度分析

> **这篇讲什么**：本算子为什么在某些形态下仍慢于 aten、受什么限制，以及为什么最终
> 选择“不按性能回退”。
> **读完你能回答**：慢场景有哪几个根本机制？当前哪些形态仍 <1x？回退到 aten 能买到
> 什么、要付什么代价？遇到慢查询先查哪里？
> **本篇代号**：M1-M4（机制：行放大/两遍/串行/无内核）、S1/P1/M1-M6/shortq（场景与
> 负载）、A/B/K（索引几何）、R10（2026-10-29 布局直写轮）。机制与负载的 M1 同名
> 不同义，见 [glossary.md](glossary.md) §3。

本文回答一个问题：**为什么本算子在某些形态下性能不佳（甚至慢于 `aten::index`），
受限于什么**。这是“回退到 aten”类问题（`integration.md` §7）背后的完整技术分析：
触发条件、根本机制、硬件/算法限制、实测数据，以及为什么最终选择“不 fallback”。

> **读者**：想理解本项目性能边界的人 / agent。结论摘要看 §1 与 §4；§3.2 是当前
> 慢形态速查，§3.1 与附录保留机制与历史数据。

> **TL;DR**：慢场景分四类——(M1) 64B 行放大 + DRAM 延迟、(M2) linearize 两遍
> 固定开销、(M3) 串行/低并行阶段、(M4) 没有 SVE 内核只能标量。**都不适合用
> “回退 aten”修**：aten 同样受 M1 限制，而 Python 包装层每次调用还要 ~45µs，
> 小算子会被这笔固定开销吃掉（§4）。正确做法是针对性内核优化（T5-T15）或
> 接受硬件上限。“回退”本身分三层：机制级（内核链内的桶化/SVE/标量选择）与
> 进程级（`HPC_INDEX_NO_OVERRIDE=1`）**已实现**，被否决的只是“按性能猜测
> 改调 true aten”的第三层——完整论证见 §4.1-4.7。
>
> **名词**：**fallback（回退）** = 放弃本算子、转调 aten；**cache line** = CPU
> 搬数据的最小单位（64B）；**MLP** = memory-level parallelism，能同时在途的
> 访存数；**wrapper** = Python 层调用包装；**dispatch_scalar** = 本算子内部
> 的标量兜底内核；**linearize** = 下标→一维偏移的换算/检查过程。

> **数据时点（先读这段）**：附录里的逐场景数字来自 **T8 及之前**，其中多处标着
> 「已修」的劣化项是**历史问题**，现状已不含它们。**当前仍慢的形态**只有下面
> 五类（R10 轮实测，`benchmarks/RESULTS.md` §2.9.1）：
>
> | 当前仍 <1x | 区间 | 根因节 |
> |---|---|---|
> | 空 mask（全 False N=1M） | 4-38t 0.42-0.66x | §3.2 + aten 并行早退（绝对差 1.5-2ms） |
> | 1B（int8/uint8）4-16t | 0.91-0.99x | §1 M1（64B 行放大） |
> | complex64 1-16t | 0.92-0.95x | §1 M4（无 SVE 内核） |
> | 非连续 mask 1-32t | 0.79-0.98x | §3.2（R2 未做） |
> | S4 f64 `x[perm]` 8/16/38t | 0.77-0.92x | §1 M3（每线程工作量小） |
>
> 其余场景全部 ≥1.00x。下文“已修”一律标【历史·已修】，只作背景与因果追溯。

## 1. 总览：四个根本机制

所有慢形态都可归因于以下四个机制之一（或叠加）：

| 机制 | 本质 | 影响的形态 | 能否软件修复 |
|---|---|---|---|
| **M1 缓存行放大 + DRAM 延迟** | 随机 gather 每个输出元素要拉一条 64B cache line，4B 元素只用 4B（16x 放大）；工作集超过 LLC 后受 DRAM 延迟/行流量限制。同构建 A/B 实测 SVE 4B 与标量持平（1.85 vs 1.86 ms），**不是 SVE 指令 MLP 缺陷** | 4B（f32/i32）大 K 大值域 pure gather；高线程数下尤甚 | 部分（小值域桶化、预取、改行 gather）；随机访问的行放大不可消除 |
| **M2 两遍模型固定开销** | linearize 先物化偏移数组、gather 再读它 = 两次遍历 + 一次分配；小 K 时固定开销占比高；1 线程无并行加速 | 1 线程所有需 linearize 的形态 | 【历史·已修】（T5 单遍路径） |
| **M3 串行/低并行阶段** | 某些形态内部有无法并行化的阶段（如 scalar_gather 的 col_off 解引用） | A<4 短行 rowcopy | 结构性问题，难修 |
| **M4 语义强制的标量回退** | 某些 dtype/形状**根本没有 SVE 内核可走**，只能落 `dispatch_scalar` | 2B/1B、complex、非连续 after、f32 超大 numel | 需新增内核（未做） |

此外有一个**全局性开销**：Python wrapper（若做 fallback）会给每次调用加 ~45µs
（见 §4.2），远大于小 op 本身耗时。

> **代号消歧**：本表的 M1-M4 是**机制**代号；performance/RESULTS 里的
> M1-M6 是 **AI4S 负载**代号（权重块、spconv 特征等），两套互不相干。
> 全部场景/负载代号与形状记号的白话速查见 `glossary.md`。

## 2. 路由与回退路径全图

`index_impl`（op.cpp）与 `gather_index`（gather.cpp）的决策树，标出每个**回退
（非 SVE 主路径）**与触发条件：

```
index_impl(self, indices)
  normalize → IndexSpec（B=行前, K=被索引, A=行后）
  │
  ├─ 单 mask && 覆盖前 m 维 && 连续 && CPU → gather_mask（T8 单遍压实）
  ├─ 单整数下标 && K<=4096 && 连续 && CPU → small_single_index（T9）
  ├─ K < 1024                    → gather_direct（快速路径，无 linearize）
  ├─ 单索引 && (A>=4096||A<16||(A<=64&&B*K<=65536)) && 连续 && f32/f64
  │                                    → M1 raw rowcopy（skip-linearize）★主路径
  ├─ 单索引 && B==1 && A==1      → T4 raw 桶化（值域≤2048 查表）
  │     ├─ 值域>2048 && f32/i32 数据+i64 下标 && 源>512KB && >1t
  │     │                       → gather_single_1d_sve（T15-C 单遍 SVE）
  │     └─ 值域>2048 其余（1 线程/小源/其他 dtype）→ gather_single_1d（T5 单遍标量）
  ├─ 1 线程 && 单索引 && A>1     → A>=4 连续 ? raw rowcopy : gather_fused（T11）
  │
  └─ linearize + gather_index
        │  （A==1 或 [连续 && A>=4 && f32/f64]）
        │
        ▼ gather_index 内部分支（按优先级）
  pure(A==1):
     1. 值域≤2048 ? bucket_gather_pure（查表）★主路径
     2. !idx32 && f64/i64        → 8B SVE gather ★主路径（高效）
     3. idx32  && f32/i32        → 4B SVE gather ⚠（M1 硬件限制）
     4. 其他 dtype/idx 组合      → dispatch_scalar ←【回退】
  rowcopy(A>1):
     1. 连续 && A>=4 && f32/f64  → rowcopy_sve ★主路径
     2. 其他（A<4/非连续/非f32f64）→ dispatch_scalar ←【回退】
  │
  └─ 其余（A<4 或非连续小块）    → gather_fused（T3/T5 单遍）
```

**回退落点汇总**（`dispatch_scalar` 或单遍标量，皆非 SVE）：

| 触发条件 | 回退内核 | 慢机制 |
|---|---|---|
| dtype ∈ {half, bf16, i16, i8, u8, bool} 纯 gather | dispatch_scalar | M4（无 4B/8B 覆盖）|
| complex 纯 gather | dispatch_scalar | M4 |
| f32 且 numel ≥ 2^31（防 i32 越界） | 2^31..2^32 多线程走 `gather_single_1d_sve`（T15-C）；≥2^32、1t、小源 → 标量 | M4（idx 被迫 int64；8B 分支只认 f64/i64 out，4B 直连内核需源>512KB）|
| rowcopy A∈[2,3] 短行 | dispatch_scalar | M3（col_off 逐个解引用）|
| 非连续 after 且存在 ≥4 连续 run | `strided_rows_raw`（T12） | M3 已缓解（run 块拷贝）|
| 非连续 after 且 run=1（纯转置） | gather_fused / 标量 | M3（无连续块可向量化）|
| 4B 大 K 大值域 pure gather（idx32+f32/i32） | 4B SVE gather（与标量持平，cache-line 放大） | M1 |
| mask（bool） | T8 gather_mask 单遍压实（不可融合时仍 nonzero + gather） | 旧路径 M3+M2；T8【历史·已修】 |
| 1 线程单索引 A==1 大值域 | gather_single_1d（T5，已追平） | M2（【历史·已修】）|

## 3. 逐场景深度分析

### 3.1 4B（f32/i32）大 K 大值域 pure gather —— cache-line 放大 + DRAM 延迟

**触发**：`pure && idx32 && sve_512_ok() && out∈{f32,i32}`，即 int32 索引的
1D 纯 gather，且值域 >2048（否则 T4 桶化接管）。典型：`x[i32]`，x 为 10M 以上
f32 张量、i 为 int32 随机下标。

**为什么慢**：这是**纯随机访存**形态：每个输出元素 `dst[p] = src[idx[p]]`，
src 地址随机。内存系统按 64B cache line 搬运，一个 4B 元素只用其中 4B（**16x
行放大**；8B 元素是 8x）。工作集超过 LLC 后，时间由"要拉多少条 line"和 DRAM
延迟决定，而不是 SVE 指令能发多少在途请求：

- **同构建 A/B（真实内核，同一随机模式）**：SVE 4B gather vs 标量循环，
  8/38 线程下 src=8MB 为 **1.85 vs 1.86 ms**，src=256MB 为
  **7.46 vs 7.45 ms**——两者持平。换指令或回退标量都不能改善。
- **早期独立探针的 0.75 vs 3.4 GB/s 不能端到端复现**（工作集/预取状态与真实
  内核不同），已撤回作为归因依据；RESULTS §3.7 记录了复核。
- 8B 路径（f64/i64）更快，是因为同样条数的 cache line 携带 2x 有用字节
  （行放大减半），并非 8B gather 的 MLP 更高。
- **硬件实测**（degradation §6.4）：本地 DRAM 随机延迟 115-192ns，单节点读
  带宽 73GB/s；同模式 C 探针的 dTLB miss ≈1.1-1.2 次/访问，IPC 0.34-0.48。
  真实内核 4B K=2M 在 1t/36t 的行流量为 2.8/73-76GB/s——**1t 是延迟受限，
  36t 是行带宽受限**，中间线程则是两者叠加。

**限制性质**：随机元素 gather 的行放大是访存模式问题，不是 920F 4B 指令缺陷。
软件只能减少行流量或隐藏延迟：
- 值域 ≤2048 → T4 桶化：把随机地址变成 L1/L2 常驻小表，行放大消失 ✅ 已实现；
- 值域大 → 软件预取/软件流水、按 cache line 分桶排序，或把"按元素 gather"
  改成"按行 gather"（A≥4 连续块，一次 line 拉多个有用字节）。回退 aten 或
  内核内标量均无收益（A/B 已持平），还受 §4.2 全局开销制约。

### 3.2 当前 <1x 形态速查（R10）

当前仍 <1x 的只有五个可复现家族 + 噪声级单格（另计）。逐族根因与处置：

| 家族 | 当前区间 | 根因 | 处置 |
|---|---|---|---|
| 空 mask（全 False N=1M） | 4-38t 0.42-0.66x | aten 并行早退；绝对差 1.5-2ms | 观察项（入口早退可做），非回退 |
| 1B（int8/uint8） | 4-16t 0.91-0.99x | 64B 行放大 64x，aten 同为标量 | 硬件上限；值域桶化除外 |
| complex64 | 1-16t 0.92-0.95x | 无 SVE 内核，走标量单遍 | 可复用 8B gather，当前不值得 |
| 非连续 mask | 1-32t 0.79-0.98x | T8 只融合连续 mask，回退 nonzero+linearize | R2：按 stride 读 mask |
| S4 f64 `x[perm]` | 8/16/38t 0.77-0.92x | 每线程工作量 <100KB，fork-join 成本占主导 | 使用侧少开线程 |

其余形态多数已 ≥1x：4B 大 K 大值域已反超；1D 小源高线程仍差 0.90-0.95x
（R1 待修）。它们的机制解释与时点无关的部分见 §3.1 与 §4.2。

## 4. 为什么不做"按性能 fallback 到 aten::index"

这是最高频的评审问题："既然某些场景比 aten 慢，为什么不就地回退到 aten，
保证处处不弱？"本章给出完整回答。先区分三层"回退"——前两层已经实现，
被否决的只是第三层（integration.md §7 有 Python 层可行性调查）：

### 4.1 三层"回退"的区分（前两层已存在）

| 层级 | 机制 | 状态 |
|---|---|---|
| **机制级** | 算子内部每条路径本身就是回退链：bucket 桶化 → SVE gather → rowcopy → `dispatch_scalar` 标量；dtype/形状没有 SVE 内核就落标量；非连续 mask 直接复用 aten 的 `at::nonzero` 原语而不重写 | **已实现**。按 shape/dtype 的**静态属性**选实现，判断零成本、结果确定 |
| **进程级** | `HPC_INDEX_NO_OVERRIDE=1` 让整个进程退回纯 aten | **已实现**（基准对拍即用此开关） |
| **性能级** | 运行时按"该形态是否比 aten 慢"改调 true aten | **否决**，理由见 4.2-4.7 |

### 4.2 残余慢格子多数是双方共同的硬件上限，回退买不到速度

当前仍 <1x 的五个可复现家族 + 噪声级单格（另计）逐个看 aten 侧对照；表末两个
“对照项”已反超或只剩待修的小差距（degradation §5.9、RESULTS §2.9.1）：

| 家族 | 我们 | aten 侧实测 | 回退能买到什么 |
|---|---|---|---|
| 空 mask（全 False N=1M） | 4-38t 0.42-0.66x | aten 并行早退恒 ~1.44ms；绝对差 1.5-2ms | 1.5-2ms，但仅此一家族；修法是入口早退（观察项） |
| 1B（int8/uint8）4-16t | 0.91-0.99x | 同为标量、同为 64B 行放大（双方有效带宽都 ~0.7GB/s） | 0-9% 的循环形态差 |
| 小工作量 8-16t（S4 = `x[perm]` 随机置换、multi 多索引） | 0.77-0.94x | 同样付 fork-join；且对 K=1023×A>=3 在 16/38t 有 **539-615µs** 的 fork-join 病理（我们串行 17µs 免疫，realpath 表 22-26x 格子即此） | ≤23%，且方向随线程数/箱态摆动 |
| 非连续 mask | 0.79-0.98x | 我们内部已在调 `at::nonzero`（就是 aten 的原语），差的是后续 linearize+gather 遍数 | R2（按 stride 读 mask）修根因更便宜 |
| complex64 1-16t | 0.92-0.95x | 同为标量单遍 | ≤8% |
| 4B 大 K 大值域（对照项，机制 M1，曾最严重） | **1-16t 1.06-1.16x**；i64 下标大源 8t 2.22x（T15-C） | 受同样行放大 + DRAM 延迟（SVE 4B ≈ 标量 ≈ aten） | 已反超，无需买 |
| 1D 小源高线程（对照项，K=8192/65536） | 0.90-0.95x | 唯一“aten 确实更快”的可修家族：残余是 ~15µs 前置值域扫描 | **R1 修根因**（省 15µs 拉回 ≥1x） |

诚实注记：小工作量家族里 aten 的强扩展效率确实更高（S4 16t 效率 56% vs
我们 38%，degradation §5.4；1t 我们快 1.27x、16t aten 快 0.86x）——
但根因是我们的小规模并行结构（grain/有效线程数），修法是阈值缩放（T15
已对 `small_single_index` 兑现 `max(16384, 512×nt)`）与使用侧建议，不是
加回退分支。

### 4.3 固定成本会精准伤害收益主体（Python 层 ~45µs/调用）

若在 Python 层做 fallback（`torch.library.get_kernel` + `with_keyset` +
`call_boxed` 调回 true aten）：实测每次 `x[...]` 增加 **~45µs**（小 op
13.7µs→63µs，即 4.6x 回归；S1 4ms 场景 +1%）。对本项目——收益主体是
RowCopy 小/中张量（单次调用本就 <100µs）——45µs 是**全局性回归**：一行
"慢就 fallback"的分支逻辑，会让所有快场景买单。

### 4.4 "哪个格子慢"不可预知、不稳定，静态回退表只能追噪声

- **随线程数反转**：1D f32 K=10M 在 1t 是 1.06x、36t 是 3.92x；1D K=65536
  在 1-16t 约 1x、36t 只有 0.90x。同一形态低/高线程优劣方向相反，回退
  条件只能按 (形态 × dtype × 线程数) 展开。
- **随箱态漂移**：同格矩阵 vs 聚焦复测可差 10-20%（degradation §5.8-F），
  共享箱上 aten 绝对时间本身摆动，"慢"的判定不稳定。
- **误路由代价大**：主力格 RowCopy 1t 1.5-2.1x、S1/P1 的代表值见
  `performance.md` §3（R10 轮；T11 轻载轮曾测 3.58-4.46x）——分类错一格，
  就是把 1.5-3x 的收益变成 1x。
- **运行时两边跑取优** = 每调用双倍工作量，严格更差。
- **每机器校准债**：所有门值按 920F/node5 实测标定（porting.md 明确换
  机器须重标），回退表同样只在这台机器上成立。

### 4.5 根因修复被 15 轮迭代验证有效，fallback 会冻结它

历史上每个 <1x 家族的处置都是"定位根因 → 修路由/内核"，全部兑现：

| 轮次 | 根因 | 数字 |
|---|---|---|
| T5 | 1 线程 linearize 两遍模型 | 多形态 0.6-0.9x → ≥1.07x |
| T8 | mask 多遍物化 | → 1.2-3.8x（P3 场景 `x[mask]` 1t 2.23x） |
| T11 | `x[:,i]` 逐元素迭代器开销 | 0.4-0.7x → 1.1-2.0x |
| T13 | 多索引小 K 走全量路径 | 0.74x → 1.6-2.0x |
| T14 | shortq（短行 A=2-4）标量循环 | 0.84x → 2.6x+ |
| T15 | 路由空档 / 大源缺 SVE / 并行阈值 | 0.73/0.76x → 1.26-2.17x；1.32→2.22x；1.84→2.83-4.57x |

若当年加了 fallback，这些格子会被盖在 ~1x 下面，修复动力消失。剩余两个
可修家族（R1 小源扫描合并、R2 mask stride）同理走根因修复，见
`status.md` §7 演进方向。

### 4.6 C++ 内核内回退：可行，但期望值为负

在 C++ 里对慢形态直接调 true aten（保存 dispatcher 里的原 CPU kernel
引用，绕开覆盖，无递归）技术上可行且无 45µs 税，但：
- 该判断每次调用都要执行，且静态表的所有问题（4.4）原样继承；
- 窄域写死（如"1B 大 K 8-16t 回退"）收益只有 0-9% 且机器相关（4.2
  实测 aten 在同一堵墙上）；
- 历史收益最大的场景（`x[:,i]` 0.4-0.7x）已用根因修复拿到 1.1-2.0x，
  比"拉回 ~1x"的 fallback 上限更好。

复杂度和每机器校准成本，买不到成比例的收益。

### 4.7 真正的差距与兜底

- 唯一**功能上**不如 aten 的地方：barebones dtype（u16/u32/u64、float8、
  complex32）抛 `NotImplementedError`（semantics §4）——这是覆盖缺口不是
  性能缺口，修法是扩 dispatch 白名单（演进方向 R8），不是回退。
- 期望值不对称总结（R10 轮，代表值见 `performance.md` §3、矩阵见 RESULTS §2.9）：
  赢的格子大而稳（RowCopy 1t、shortq、mask 1t、4B 大源 gather 8t）；
  输的格子小而少（五个可复现家族 + 噪声级单格，0.42-0.99x，其中空 mask 的
  1.5-2ms 绝对差与 1B/complex 的硬墙合计占绝大多数，其余 ≤10-20%）。

**结论**：**不实现性能级 fallback**。机制级回退已在内核链里，进程级逃生门
已有；"各场景不弱于 aten"的正确路径是根因修复（R1/R2/R8，`status.md`
§7）。fallback 是用确定的成本（45µs 税或每机器校准表债）去买不确定且
微小的收益。

## 附录：历史逐场景

> 本附录保留原 §3.1-§3.8 的历史表与逐场景数字，**只作追溯，不代表当前状态**。
> 当前 <1x 清单见文首表与 §3.2；当前值见 `benchmarks/RESULTS.md` §2.9.1。

### A.1 原 §3.1：4B 大 K 的 T11 矩阵

> **数据轮次：T11（2026-10-22）｜历史。**

**实测**（T11 修正矩阵，node 5，interleaved median；RESULTS §2）：

| 线程 | 1t | 2t | 4t | 8t | 16t | 32t | 36t |
|---|---|---|---|---|---|---|---|
| 1D f32 K=10M 相对 aten | 1.06x | 1.11x | 1.11x | 1.14x | 1.16x | 2.28x | 3.92x |

1-16t 基本持平（行放大决定的上限），32/36t 的高比值有一部分来自 aten 在带宽
饱和后变慢（绝对带宽见 degradation-analysis.md §6）。**随机行放大本身仍在**，
它决定"绝对带宽上限"，不是"相对 aten 的比值"。旧文档的 2-36t 数字（如 2t
13.9x）因扩展实际使用 libomp 默认 38 worker 而失真，已作废。

### A.2 原 §3.2：2B/1B（half/bf16/i16/i8/u8/bool）与 complex 纯 gather

**触发**：`pure && A==1` 但 out dtype 不在 {f64,i64,f32,i32}。SVE 内核只写了
8B/4B 两种元素宽度的 gather/rowcopy，2B/1B 与 complex 没有向量实现。

**为什么慢**：纯 `dispatch_scalar` 标量逐元素。没有内核覆盖（M4）。但要注意：
- 这不是"比 aten 慢"，只是"没吃到 SVE 加速"。aten 也是标量 TensorIterator。
- T11 修复后 half/bf16 K=2M：1.22-2.40x（1-36t），1-16t 也全部 ≥1.22x。
- complex64 K=2M：0.95-2.76x（1-16t 0.95-1.00x，32/36t 1.78/2.76x）—— complex 是 8B 元素但**走标量**（没有 complex
  的 SVE gather 内核），收益来自单遍路径而非向量化；基本与 aten 持平。

**限制性质**：实现空白（可补），非硬件。未来加 2B/1B SVE gather（或用
`svld1_gather_u64index` 按字节偏移 trick）即可覆盖。当前不值得——这些 dtype
在 AI4S 模型 gather 路径罕见。

### A.3 原 §3.3：rowcopy 短行 A∈[2,3]

**触发**：`A>1 && A<4`（或 A>=4 但非连续/dtype 不符）。M2 spconv 的
`pos[src]` 是 A=3 短行——**这是真实模型形态**。

**为什么慢**：`dispatch_scalar` 的 `scalar_gather` 每元素要
`d[c] = s[col_off[c]]`——A=3 时每行 3 次解引用（col_off 数组查），且行间随机
跳转。SVE rowcopy 门槛 A>=4 是有意为之（A=2,3 时 SVE 向量化收益被加载开销
吃掉，T1 微基准已测）。A=3 无连续块向量化。

**但实测并不差**：T11 矩阵里 rowcopy A=3 K=200k 为 1.34-3.34x（1-36t），
P2 A=3 E=2M 为 1.78-8.73x。**这形态是"慢于 SVE 主路径"而非"慢于 aten"**——
相对 aten 是赢的，只是幅度不如长行；旧文档的 8t 7.58x 来自失真的线程标签。

**限制性质**：结构性（短行无法向量化拷贝）。不可修，但也不是回归。

### A.4 原 §3.4：rowcopy 非连续 after 维

**触发**：`A>1` 但 after 维 stride 不连续（如 `x.t()` 后的 `x[i]`、或
`x[:, i, :]` 中 i 后还有非连续段）。`rowcopy_sve` 要求 `after_contiguous`
（`col_off[c]==c`），否则整行不是一段连续内存。

**为什么慢**：必须逐元素解引用 col_off，SVE 连续 `ld1/st1` 用不上（M3/M4）。
同附录 A.3（原 §3.3）——相对 aten 通常仍有收益，只是吃不到向量化。

**T12 改进**：`col_off` 中相邻（+1）的元素合并成 run；run≥4 时
`strided_rows_raw` 对每个 run 做块拷贝（≤64B 用 memcpy），把“每元素一次
load/store”变成“每 run 一次”。实测 tail `[64,200,16]`（A=1024，64 段×16）
1t 10.56→4.74ms（2.23x）、8t 1.71x。**run=1 的纯转置没有连续后缀**，块拷贝
只能退化为逐元素，仍走 `gather_fused`；8t ~0.84x 是既有低线程尾部，见
`docs/archive/index_sve_vs_fastindex_gap_20261023.md` §19.1。

**限制性质**：run 长度由 after 维的 stride 布局决定；纯转置结构性无解（除非
换固定 col_off 的 SVE gather 内核，尚未实现）。

### A.5 原 §3.5：mask（bool 索引）

**【历史·已修】（T8 后）**：旧路径 bool 掩码 → `normalize` 先 `index.nonzero()`
展开成位置下标，再走 linearize + gather。两段式 + nonzero 输出长度数据相关、
并行度差，高线程比值退化（P3 38t 0.35x）。

T8 在入口识别"单 mask + 覆盖前 m 维 + mask/self 连续 + CPU"走 `gather_mask`：
一遍计数 + 前缀和，第二遍直接压实并整行拷贝，跳过 nonzero 与第二次 gather。
P3（N=200k C=16 nnz≈60k，T11 修正矩阵）：1t 4.86→2.05ms（2.23x vs aten）、
8t 2.66→0.85ms（1.34x；旧 "8.0x" 是 38 worker 标签失真）、36t 0.94ms
（4.20x，32t 0.72ms / 5.60 GB/s 为最好点）。非连续 mask/self、混合其它
下标仍走旧路径（正确性不变）。

### A.6 原 §3.6：多索引广播形态（x[i,j]）

**触发**：多索引且形状需广播（如 `x[i, j]`，i/j 不同长或含标量）。走
linearize（混合进制 decode）+ gather。

**为什么慢（历史）**：1 线程时 linearize 两遍模型固定开销 + 每次访问
at::Tensor 方法（引用计数/虚调用）→ 0.66x。**T5【历史·已修】**（nb==1 全长连续
快路径 + 属性预提取）：linearize 4.84→1.10ms，x[i,j] 1t 0.66x→**1.21x**（T11
重新测量 1.19x）。
T13 矩阵为 1t-4t 1.04-1.20x；8/16t 0.97/0.92x 是 400KB 小输出的任务切分
成本（focused 复测同值）；32/36t 1.70/1.98x 含 aten 退化放大。

**T13 补充**：索引同 shape/连续且 `n≤65536` 的短调用，在 normalize 之前直接
走 `small_multi_index`（偏移预计算 + dom1 fill + 逐行 memcpy）。K=512 实测
A=1 1t/8t/36t 为 1.59/1.99/1.67x，A=4 为 1.90/2.31/1.64x。

**剩余限制**：非全长/非连续索引（广播标量等）仍走 generic decode，慢于快路径，
但正确性不受影响；相对 aten 仍 ≥1x。

### A.7 原 §3.7：f32 且 numel ≥ 2^31（防 int32 越界）

**触发**：`self.numel() >= 2^31` 时 `use_i32=false`，f32 也强制 int64 索引——
因为元素偏移必须 ≥2^31 时 int32 装不下。而 8B SVE gather 分支只认
`out∈{f64,i64}`，f32+int64idx 落标量（M4）。

**为什么慢**：语义安全优先于性能——这是**正确的**选择（2^31 元素越界 int32）。
超大张量本身罕见；标量路径相对 aten 通常仍有收益（idx 变 8B 使 linearize
写放大，但 gather 段二者都标量）。

**限制性质**：语义强制的实现空白。**T15 已补**（多线程主体）：新增直连
单遍内核 `pure_gather_sve_4b_i64idx`——读原始 i64 下标、向量边界检查/负
归一、uzp1 抽低 32 位后复用 u32index gather（不做 linearize 物化），路由门
为 `源>512KB && size<2^32 && >1 线程`；numel≥2^31 的 f32 源必 >512KB，
落在 2^31..2^32 区间的即走此内核（聚焦 A/B：1D f32 K=10M idx64 源 8MB
8t 1.32→2.22x）。仍落标量的只剩 numel≥2^32（uzp1 低 32 位会截断）、小源
（L1 常驻下标量快于 4B gather 微码下限）或 1 线程——均罕见且标量不劣于
aten。原“8B 偏移存取（off 按 8B 存、按 4B 取）”的物化方案不再需要。

### A.8 原 §3.8：【历史·已修】1 线程（T5）

历史 1 线程多形态 0.6-0.9x（M2：linearize 两遍固定开销；SVE 单线程在此形态
并无 MLP 优势）。T5
（bd21485）用**单遍标量**（`gather_single_1d`、1 线程短行 fused）+ nb==1 快路径
修复，表中形态回到 ≥1.07x（T11 复核）：

| 形态 | 修复前 | 修复后 |
|---|---|---|
| 1D pure f32/f64 K=5M | 0.75x / 0.71x | 1.07x / 1.24x |
| x[i,j] 1t | 0.66x | 1.21x |
| rowcopy A=4 1t | 0.87x | 1.39x（T11 2.41x） |
| mask 1t | ~1.0x | **2.1x**（T8）|

详细见 `optimizations.md` §9。
