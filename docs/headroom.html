还有多大空间？
—— `aten::index` 慢在哪、我们已经拿到多少

本文是 docs/headroom.md 的插图版导读：所有数字与结论均出自该文档及其引用的 benchmarks/RESULTS.md， 两者冲突时以 RESULTS 为准。

一次访存的成本 = 延迟 ÷ 在飞条数
延迟由硬件决定（本机 DRAM ≈ 137ns），代码能改的只有“在飞条数”： 一次只等一条，就要付满 137ns；一次等 16 条，摊到每条 ≈ 8.6ns。全文都是这一个公式。
数据轮次：R10（2026-10-29）及 2026-11 月补丁轮 ｜ 机器：鲲鹏 920F，node 5（38 核）

01一页看懂：四级阶梯

把全文压成四级台阶——每级只回答一个问题。

1

硬件能给多少？

每核可同时挂 16–20 条 cache line 在飞；一条随机访问的下界 8.6–8.9 ns。

= 137ns ÷ 16。这是物理天花板。

2

aten 站在哪？

实测只有 0.85–1.05 条在飞，每行 132–155ns—— 几乎就站在下界上，没吃到并行等待的红利。

3

本仓拿到多少？

A=16 行拷贝 1t 已到 5.7 条在飞（24ns/行，aten 的 6.3x）， 但离 8.6–11.4ns 还有 2.1x。

4

剩下的在哪？

不在“搬数据”，在每核在飞条数与固定成本。三格各撞一面墙： 在飞条数、固定成本、覆盖率。

本轮最重要的修正：三个生产模型（SGI / PPT / Sonata）最贵的一格都是 值域 ≤2048 的桶化 gather，不是“大值域 1D gather”。两族访问的内存层不同， 量空间的尺子也不同——拿错尺子会把空间虚大 8–9 倍。

02硬件原理：一次访存到底花多久

数据不在 CPU 里，在内存条上。距离不同，成本差 20–70 倍。 记牢这张延迟阶梯，后面所有数字都有出处。

① 搬运的最小单位是 64B

哪怕只读 4 字节，整条 64B 的 cache line 也会被搬过来。 随机取 4B，有用字节只有 1/16——这是“行放大”，4B gather 一族的天花板来源。

② 访问有两种形状

依赖链：下一条地址要靠上一条读回的数据（如 dst[k] = table[idx[k]]）——一次只能等一个； 独立访问：地址提前算好，可以一次发十几个——成本摊薄成“延迟 ÷ 在飞条数”。 优化本质上都是把第一种改成第二种。

③ 写比读贵

只改 line 的一部分时，CPU 得先把整条读进来（RFO）。 A=16 恰好一整条 line，整行写不产生额外读——这是行拷贝族快的硬件前提。

03在飞窗口：一颗核到底能同时等几件事

用 memprobe mlp S 造 S 条互相独立的指针追逐链： 链内是依赖的（最多 1 条在飞），S 条并行就把“在飞条数”精确设定成 S。不是估，是直接设定。

为什么停在 16–20：每颗核里有一张 MSHR 表，记录“哪些 line 已发出、还没回来”。 表项用完，新的 miss 只能排队。能改的只有两件事：把窗口填满（预取、批量化） 或少发几条 line（提高 line 内利用率）。

误解 ① “延迟高 = 带宽低”

延迟是一次往返（137ns），带宽是稳态吞吐（随机 7.2GB/s/核、 单 node 读 168GB/s）。两者只通过“在飞条数”联系，不能互相换算。

误解 ② “加线程就能追上”

加线程只是把等待本身并行化：aten 1 线程一行 322 拍、 8 线程仍 318 拍。每核的在飞条数没变多，要缩短每行的等待只能提高每核的在飞条数。

误解 ③ “指令越宽 / 预取越远越好”

指令下界比实际实现低 1–2 个数量级；预取超过 MSHR 容量会把自己挤掉 （A=64 8t 的 D=16 崩到 115ns）。H6 实验证明这条循环根本不是发射受限。

04两种下界：同一段 gather，尺子差 8–9 倍

dst[k] = src[idx[k]] 的成本完全取决于源数组有多大—— 能不能装进缓存。这把“桶化”和“大值域 1D”分成两个族，各用一把尺子。

口径提醒（全文最重要的一条）：对裸探针下界的倍数（41x / 23x / 6.5x） 回答的是“离物理还有多远”，不是可得空间。把实测固定成本加回去得到 “实测地板”，三格只剩 1.9x / 2.4x / 1.8x。本文所有“还剩多少”都用后者。

05aten 为什么慢：窗口几乎没填

PyTorch 的 aten::index 用一套“通用性优先”的机器做这件 本质上很简单的事。实测它的行循环是依赖链形状——同时只有约一条在飞。

aten 自己的理论倍数（§3.3）：如果它能把窗口填满，随机行最多可快 15–18x、A=64 快 6.6x、A=256 快 2.7x、 1D 大值域 gather 快 5.2x。它拿不到的原因不是带宽也不是指令， 就是“一次只等一条”。

06本仓现在在哪：四个行宽档 + 两条元素族

同样取一行，本算子比 aten 快多少、离天花板多远，按行宽分档看最清楚 （1 线程，行拷贝族，§4.5）。

“已兑现”到上限的百分之几

三格各撞一面墙，必须分行说（§4.6）：A=16 还有 1.8x 但没有便宜的下手处 （H6 已证伪“砍指令”）；桶化只剩结构改动（H4/H7）与内核外的入口；1D 大值域有 3.9x 空间 但生产形态零覆盖。三句混成一句，会读出“还有 40 倍空间”或“这实现不行”两种相反的误读。

07三个天花板、三面墙

“无法进一步提升”必须分三句话说：每一面墙是什么、能不能推、怎么推，都不一样 （§6.5.9）。

墙 ① 指令墙

每条元素至少“读下标 → 检查 → 归一 → 写回”≈6 条指令，÷ IPC 2.6 ≈ 2.3–2.9 ns/元素，与内存无关。

基本不能推：单核向量化确实能快 1.84x（4B + 32 位下标， §1.5.4），但热点全是多线程跑的，38t 下 SVE 与标量持平（0.87–1.17x）—— 省下的指令不落在瓶颈上。

墙 ② 固定成本墙

每次调用都要付：入口 5.8µs（内核外）+ 一次 fork-join ≈ 3µs。小 K 时被摊到每元素上是几十 ns。

能推一部分（H4 单趟结构、H7 复用输出）；入口那 5.8µs 不在本仓代码里。

墙 ③ 覆盖率墙

三个热点格子只占各模型 23–40% 的调用， 长尾那 60–77% 目前约 0.9x（比 aten 略慢）。

不在内核里：热点全到地板，全程也只有 1.2–1.3x。要逐族修长尾。

08端到端：理论上限能换多少

单形态倍数 ≠ 用户感知。热点只占 23–40% 的调用，全程口径还要再打一次折。

为什么稳妥线是 1.6–1.9x 而不是 2.5x+：上一版用的地板（SGI 6–8µs）比 “空 parallel region 两趟 6.4µs + 入口 5.8µs”还小，Sonata 的 5x 要求整数账归零。 按实测地板重算，差的 0.5x 只能来自“连固定成本都换掉”（H7）。

09本轮已经兑现的两刀（A/B 实测）

都是改结构、不是改循环：第一刀免掉整趟值域扫描（源 ≤2048）， 第二刀跨度 ≤64KB 时连表都不建、直接查源（补丁 3b 加 K/size ≤ 32 门）。

10欠账清单 H1–H8：下一步砍哪

按端到端 Δ（加权）排序，不是按单形态倍数——所以固定成本（H4/H7） 排在最贵的单格（H2b 剩余）前面。

编号内容状态预期 / 结论
H1行拷贝软件预取（按行字节分档 D）已实做 1t 2.26–2.91x；剩 1.15–2.1x 不在预取本身 → H6
H2a大值域 1D 批量化（DRAM 下界）无用户 3.9x 空间真实，但 15 个生产形态 0 覆盖，端到端杠杆 ≈0

H3两遍模型的输出段（A≥128 高线程掉到 0.80–0.89x）未验证假设 预期 1.5–2.5x（宽行高线程，待证；H6 已证伪同款“指令墙”判断）

H5减少遍数与 fork-join（K<1024 短路悬崖）待做 不是提速是堵漏；堵住后小 K 的 1.5–3x 才拿得到
H6预取记账批量化（砍 26 条/行）负结果 指令 −13%→+13%、周期不动：不是发射受限；A=16 剩 1.8–2.1x 的下一刀未知
H7每调用固定成本（入口 + 两遍 fork-join）第一杠杆 预期 1.5–3x（小 K 场景）；入口 5.8µs 的一半不在本仓
H8路由悬崖（从 R1 提级）待做 见 headroom.md §7 / status.md §7

优先级结论：下一刀砍固定成本（H4/H7，SGI/PPT 共同的地板，实测 15.5/15.7µs）。行拷贝“砍指令”的路已试并证伪；A=16 剩余的 1.8–2.1x 目前没有已知下手处； Sonata 的回退已修（补丁 3b）。

11这些数是怎么测的

所有硬件数字来自探针（与本仓代码无关的独立 C 程序）， 所有实现数字来自两进程交替 A/B。核心原则：下界用最好值，体验用中位数，两者不能混。

交叉验证：带宽延迟积

7.2GB/s × 137ns ≈ 986B ≈ 15.4 条 line —— 与曲线给的 16–20 条对得上。 饱和吞吐与延迟是两个独立测量，互相印证说明曲线不是探针伪影。

三个常见坑（本文已避开）

  • 比值波动 20%+：aten 与本算子必须同轮交替跑，比值只用同一轮的两个数。
  • 共享箱噪声：以 node 5 定点矩阵为准，608 线程档只作参考。
  • 推算值都标了“±50%”读法；与实测冲突时以 RESULTS 为准。

复核清单（§9.7，照做一遍每个数字都能复现）

# 1. 缓存层级与 node 划分（别假设有 L3）
lscpu -C && numactl -H
# 2. 主频与单点延迟（对照 137ns）
memprobe freq 2e8 && perf stat -e cpu_cycles ./memprobe latency 256 3000000
# 3. 在飞窗口曲线（本文核心曲线）
for S in 1 2 4 8 16 32; do ./memprobe mlp 256 $S 1e8; done
# 4. 带宽顶（单 node 读 168GB/s 硬顶）
for t in 1 8 16 38; do ./memprobe bandwidth 2048 $t rd; done
# 5. L1 查表下界（桶化的尺子）
./memprobe idxgather ...
# 6. SVE 指令级上限
./sveprobe ...

完整命令与各探针的形状说明见 headroom.md §9 与 RESULTS §2.16–§2.20。
