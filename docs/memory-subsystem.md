# 内存子系统实测：这台机器到底给了什么

> **这份文档解决什么问题**：`aten::index` 的性能上限完全由内存子系统决定——
> 一次随机取数要等多少、一颗核能同时挂几条、带宽在哪饱和、跨 NUMA 要付多少。
> 这些数散在 `headroom.md` §1（教程版）与 `RESULTS.md` §2.16/§2.20（原始轮次）里，
> 本文把它们**收成一份可查的实测台账**，并补齐此前没测的四块：
> **NUMA 本地/远程**、**读写方向**、**硬件预取器的合并收益**、**L2 容量悬崖细扫**。
>
> **与 `headroom.md` §1 的分工**：§1 是"从零讲懂"的教材（含 MSHR、RFO、组相联、
> row buffer 的原理），本文只放**本机实测数 + 怎么测的 + 能拿它干什么**。
> 原理不懂时先读 §1，要引用数字时用本文。
>
> **口径**：`ns/访问` = 一次依赖链访问的墙钟（含探针自身的 ~0 开销，`chase` 已
> 去掉 `volatile` 税）；`line_GBps` = 64B ÷ (ns/访问)，即"单核一条 line 一条 line
> 地拿"能拿到的带宽；`拍 = ns × 2.0`（本机 1.99GHz，标称 2.0GHz，见 §2.16.1）。
>
> **轮次与硬件规格**：§2-§7 的表格是 **2026-11-04 上午轮**（node 5、8 线程口径）。
> 硬件规格（16 × 64GB DDR5-5600、16 条通道、node16-31 的真实身份）来自同日
> root 采集的 `dmidecode`/SRAT，见 §1；**§5.4（跨 socket）与 §5.5（封装内内存）
> 是下午轮**，各自标了轮次与口径。§11 列了还没结论的事。

## 1. 机器拓扑（先弄清"内存"指哪一段）

| 项 | 实测 | 怎么查的 |
|---|---|---|
| CPU | 608 核 = 2 socket × 304 核，**1.99GHz**，boost 关闭 | `lscpu`、`memprobe freq` + `perf stat -e cpu_cycles` |
| L1d | 32KB，**8 路 × 64 组 × 64B**，每核私有 | `lscpu -C`、`/sys/devices/system/cpu/cpuN/cache/index*` |
| L2 | 768KB，**12 路 × 1024 组 × 64B**，每核私有 | 同上 |
| **L3** | **无** | `lscpu -C` 只列到 index2；`/sys/.../cache/index3` 不存在 |
| 内存条 | **16 × 64GB DDR5-5600**，2 rank、Hynix、**80 位（64 数据 + 16 校验，ECC）**；`SOCKET 0/1 CHANNEL 0-7 DIMM 0`，16 槽全满 | `dmidecode -t 16/17`（root） |
| 内存通道 | **16 条**：每 socket 8 条、**每 SCCL 4 条**。DDR5 每条再分 2 个 32 位子通道，所以 `hisi_sccl*_ddrc*` 有 32 个 | `dmidecode` + `/sys/bus/event_source/devices/` |
| 每通道带宽 | 理论 **44.8 GB/s**（8B × 5600 MT/s），实测约 42 | PMU 计数 + `memprobe bandwidth` |
| NUMA | **32 个 node**：0-15 带 CPU（各 38 核，共 608），16-31 无 CPU、各 4GB | `numactl -H` |
| 每 node 内存 | node 0-15 约 63GiB（`numactl` 报 64506MB） | `numactl -H`、`/sys/.../node*/meminfo` |
| node 16-31 是什么 | **CPU 封装内内存**：`dmidecode` 里 `Form Factor: Die` / `Locator: CPU1MemoryOnChip`，每颗 CPU 32GB、10000 MT/s，被 SRAT 按 `hotplug` 切成 8 × 4GB | `dmidecode -t 17`、`dmesg \| grep SRAT`（root） |
| 距离 | 本地 10、同 SCCL 邻 node 20、同 socket 另一 SCCL 30、跨 socket 40；封装内内存 61-91 | `cat /sys/devices/system/node/node5/distance` |

> **node 0-15 的内存不是"一大块 16×64GB 随便分"**：每 4 个 node 共用同一个 SCCL 的
> 4 条通道（实测映射：node0-3→sccl0、4-7→sccl1、8-11→sccl8、12-15→sccl9）。
> 所以"多用一个 node"不等于"多一份带宽"，只有跨 SCCL 才加带宽。

**没有 L3 这一条经常被忘**：1MB-8MB 那段"缓坡"（46→95ns）不是 L3 命中，而是
**L2 miss 打到 DRAM 的延迟逐步爬升**（row buffer 命中率下降，§2.16.7 已用"命中率
饱和但延迟仍涨"排除缓存层解释）。所以本机上**没有"中间层"可以利用**——数据要么在
L2（7-9ns），要么付 128ns。

## 2. 延迟阶梯：`chase` 实测（本轮）

指针追逐，`memprobe chase SIZE_KB 30000000`，绑 `--physcpubind=190 --membind=5`：

| 工作集 | 4KB | 32KB | 256KB | 512KB | 768KB | 1MB | 2MB | 4MB | 8MB | 16MB | 32MB | 64MB | 128MB |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| ns/访问 | **2.01** | **2.01** | 7.38 | 8.57 | 22.79 | 46.77 | 76.74 | 85.99 | 95.28 | 111.18 | 123.31 | **127.79** | **147.70** |

读法（三段 + 一段爬坡）：

- **2ns 段（≤32KB）**：L1 命中，一行一次 4 拍。
- **7-9ns 段（256-576KB）**：L2 命中。
- **128-148ns 段（64MB 以上）**：本地 DRAM 往返，**这就是"一次随机取数"的价格**。
- **22-111ns 的中间段**：L2 装不下以后没有任何缓存层接住，直接进 DRAM，但访问在
  64MB 以内时部分命中 DRAM row buffer，所以延迟从 22ns 一路爬到 128ns 才封顶。

**与既有轮次的对照**：§2.16.1（2026-11-02 晚，快态）用同款探针记 32KB=2.0ns、
512KB=11.74、768KB=27.94、64MB=130.88。本轮 512KB=8.57、768KB=22.79、
64MB=127.79——**差别在探针税与 run-to-run 噪声，趋势一致**，说明这轮（机器部分恢复期）
的**延迟型测量仍然可信**。

## 3. 在飞窗口：一颗核能同时挂几条

`memprobe mlp 64 S 20000000`（64MB 工作集 → 每次访问都 miss 到 DRAM，S 条互相
独立的链）：

| S（独立链） | 1 | 2 | 4 | 6 | 8 | 12 | **16** | 20 | **24** | 28 | 32 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| ns/访问 | 133.5 | 67.1 | 34.4 | 23.5 | 18.0 | 12.5 | **9.95** | 8.83 | **8.62** | 8.79 | 8.76 |
| line GB/s | 0.48 | 0.95 | 1.86 | 2.73 | 3.56 | 5.13 | **6.43** | 7.25 | **7.42** | 7.28 | 7.31 |

三个结论：

1. **S=1 到 S=16 几乎严格按 `1/S` 摊薄**（133.5 → 9.95，13.4x）——硬件确实是
   "同时等"，不是"等得更快"。
2. **饱和在 S≈16-24，触底 8.6ns**。再多的链只是排队（S=32 反而 8.76，略回升）。
   等效在飞条数 = 133.5 ÷ 8.62 = **15.5 条**。
3. **交叉验证**：饱和带宽 7.42 GB/s × 133.5ns = **991B ≈ 15.5 条 line**。
   两条完全独立的路径（延迟摊薄曲线 / 带宽延迟积）给出同一个数——这就是
   `headroom.md` 里"16-20 条"那个区间的来历。

> **这解释了什么**：`x[idx]` 慢不是因为"取数指令慢"，而是因为**同一时刻只有 ~1 条
> line 在路上**（aten 实测 0.85-1.05 条）。天花板是 15.5，不是 1——中间这个差就是
> 全部可优化空间的来源。

## 4. 带宽：方向、线程、顺序 vs 随机

### 4.1 单线程：顺序与随机差 2.9x（= 硬件预取器 + row buffer 的合并收益）

| 访问模式 | ns/访问 | line GB/s |
|---|---|---|
| 顺序读（`bandwidth 1024 1 rd`） | — | **19.48** |
| 顺序 gather（`gathermt … seq`） | 3.32 | 19.29 |
| **随机 gather**（`gathermt … rand`） | **9.50** | **6.74** |

顺序比随机快 **2.86x**。这 2.86x 由两件事合成：DRAM **row buffer 命中**（同一排
连续读几乎免费）和**硬件预取器**（识别步长、提前取后面的 line）。随机访问两样都
吃不到，只能一条一条付 128ns ÷ 在飞条数。

> **为什么"排序索引"听起来很美但没用**：把随机变顺序确实能拿到 2.9x 的访存收益
> （每元素 9.5 → 3.3ns），但要付 `O(K log K)` 的排序代价；对 `K` 上万、每元素只有
> 几纳秒的 gather，排序本身的成本远超收益。这条在 `headroom.md` §8 列为负结果。

### 4.2 多线程与方向

| 线程 | 读 GB/s | 拷贝 GB/s（读+写合计） |
|---|---|---|
| 1 | 19.46 | 20.48 |
| 8 | **130.24** | **137.45** |

- 8 线程读到 130 GB/s ≈ 单核 16.3 GB/s × 8——**几乎线性**，说明单核 19.5 GB/s
  是被"一条 line 一条 line 地拿"限制的，不是被内存控制器限制的。单核这一格不同
  轮次报 19.0-19.5（`memory-hardware-primer.md` §2 用 `memprobe bandwidth` 得 19.0，
  本节同族探针得 19.46），**差 2-3% 属轮次波动，不要当两个结论**。
- **拷贝列是"读+写合计"**（探针按 `2×size` 计），所以 8t 拷贝的每方向流量约
  68 GB/s，比纯读的 130 低——写方向要额外付"把整条 line 读进来再改"（RFO）的
  代价。**这也解释了为什么 `stnt1d`（非临时写）收益为 0**：写侧 RFO 省掉了，但
  这里的瓶颈在"等数据"，不在"写回"（`headroom.md` §8）。

### 4.3 与本仓既有快态数的对照（可信性检查）

§2.16.2（快态）8t 读 127.4 GB/s、拷贝 132.3；本轮 **130.24 / 137.45**，
差 **+2.2% / +3.9%**。**结论：带宽类测量在当前（部分恢复）态下仍然可用**——
这也是"慢态只罚每次调用的固定成本、不罚稳态流"（RESULTS §2.22 第三起）的一个
独立佐证。

## 5. NUMA：本机最容易被忽略的一块（本次新增）

拓扑：node 0-15 带 CPU（各 38 核），node 16-31 无 CPU（是 CPU 封装内内存，
见 §1）。node 5 的距离表是 `本地 10 / 同 SCCL 邻 node 20 / 同 socket 另一 SCCL 30 /
跨 socket 40`；封装内内存是 61-91。

**测量方式**：核固定绑 node 5（`--physcpubind=190`），用 `--membind` 把内存放到
不同 node 上——这才是"跨节点访问"，只绑核不绑内存是测不出来的。

### 5.1 延迟（`chase 65536`，64MB）

| 内存所在 | 距离 | ns/访问 | 相对本地 |
|---|---|---|---|
| node 5（本地） | 10 | **129.4** | 1.00 |
| node 6（同 SCCL 邻 node） | 20 | **180.5** | **1.39x** |
| node 0（**同 socket，另一个 SCCL**） | 30 | **254.4** | **1.97x** |

**跨一个 SCCL 就要 254ns——接近本地两倍**。这不是"多一点点"，是直接翻倍。
（真跨 socket 的 354ns 见 §5.4。）

### 5.2 带宽（1GB，8 线程，读）

| 内存所在 | 读 GB/s | 相对本地 | 拷贝 GB/s | 相对本地 |
|---|---|---|---|---|
| node 5（本地） | **125.5** | 1.00 | 137.4 | 1.00 |
| node 6（同 SCCL） | **66.4** | **0.53x** | 99.6 | 0.73x |
| node 0（同 socket，另一 SCCL） | **48.3** | **0.38x** | 69.5 | 0.51x |

### 5.3 对本仓的含义

1. **绑核与绑内存必须成对**（`--physcpubind` + `--membind`）。只绑核时，内存落在
   哪个 node 取决于**首次触碰它的线程**——多线程建张量会让数据散在多个 node 上，
   **同一个程序能差 1.4-2.7 倍**。这就是 `headroom.md` §1.0.5 那条"不绑 NUMA 同一
   程序能差一大截"的实测依据。
2. **跨 SCCL 的 1.97x、跨 socket 的 2.7x 会掩盖所有内核优化**：如果生产上源张量
   落在远端 node，行拷贝再好也追不回来。**这是部署问题，不是内核问题**——先查
   `numastat`/绑核策略，再谈优化。
3. 本仓所有基准都钉在 node 5（`--membind=5`），所以本仓数字都是**本地访问口径**；
   引用给生产时要说清这一点。

### 5.4 补测：真正的跨 socket（距离 40，2026-11-04 下午轮）

上午那一轮把 node 0 当成了"跨 socket"，其实它只是**同 socket 的另一个 SCCL**。
真正的跨 socket 是 node 8-15（距离 40）。下午补齐了（核仍固定 node 5 的 CPU 190-227）：

| 内存所在 | 距离 | 延迟 | 1 线程读 | 8 线程读 | 38 线程读 |
|---|---|---|---|---|---|
| node 5（本地） | 10 | 130 ns | 19.1 GB/s | 128.7 | 163.3 |
| node 6（同 SCCL） | 20 | 181 ns | 9.1 | 64.9 | 149.3 |
| node 0（同 socket 另一 SCCL） | 30 | 255 ns | 6.4 | 47.8 | 127.8 |
| **node 8（跨 socket）** | **40** | **354 ns** | **4.4** | **17.2** | **17.2** |

三条读法：

1. **延迟阶梯是干净的**：130 → 181 → 255 → 354 ns，距离每 +10 大约 +50~100ns。
   "跨 socket"是 2.7 倍，不是之前写的 2.0 倍。
2. **跨 socket 的带宽是断崖**：8 线程和 38 线程都是 **17 GB/s**（本地的 1/8），
   加线程完全没用——那条互连不是给大流量设计的，它是给缓存一致性和小消息用的。
   所以 §5.2 的 0.38x 已经是"同 socket 跨 SCCL"，跨 socket 只有 **0.13x**。
3. **低线程看延迟、高线程看带宽**：跨 SCCL 在 1 线程时掉到 1/3（19→6.4），
   38 线程时反而只掉 22%（163→128），因为本地核已经把通道压满了，差距被掩盖。

### 5.5 封装内内存（node 16-31）：不是"共享一条 80 GB/s"（2026-11-04 下午轮）

这一节把上一版留在 §11 的"通道结构未测"结掉。原始数据（ACPI 表解析 + 实测）在
`docs/hw-report-open-items-20261104.txt`，原理版见 `memory-hardware-primer.md` §6.5。

**拓扑规律（解析 SLIT 原表得到）**：每个 CPU node 与一个封装内 node **1:1 配对**，
`node i ↔ node 16+i` 距离 **61**；同 SCCL 的另外三个 **71**；同 socket 另一 SCCL
**81**；另一个 socket **91**。四组正好是四个 SCCL：

| SCCL | CPU node | 配对窗口 | 同 SCCL 其余 |
|---|---|---|---|
| sccl0 | 0-3 | 16-19（61） | 71 |
| sccl1 | 4-7 | 20-23（61） | 71 |
| sccl8 | 8-11 | 24-27（61） | 71 |
| sccl9 | 12-15 | 28-31（61） | 71 |

**延迟**（`chase 65536`，64MB 足迹，不是上一版的 4MB）：

| SLIT 距离 | 实测 | 关系 |
|---|---|---|
| 61 | 141-145 ns | 配对窗口（比本地 124-132 只慢 10%） |
| 71 | 187-205 ns | 同 SCCL 其余三个 |
| 81 | 268-285 ns | 同 socket 另一 SCCL |
| 91 | 360-477 ns | 另一 socket |

**带宽取决于"核站在哪"**（32 线程/窗口、1GB 缓冲、2s 窗口）：同一个窗口，
配对的 CPU node 能拿到 **355-411 GB/s**，同 SCCL 的另外三个只剩 183-195，
同 socket 另一 SCCL 137-139，另一个 socket 只有 18（那是 socket 之间那条链路的墙，
和跨 socket DRAM 的 17 GB/s 同一面）。对照本地 DRAM node：167。

**聚合**（每窗口用自己的配对 32 核）：1 → 382、2 → 773、4 → 1544、
socket0 七个 **2719**、socket1 七个 **2614**、十四个 **5238 GB/s**。
同样 7×32 线程、每进程 512MB：摊到七个窗口 **2621**，全压一个窗口 **284**（9.2 倍）。

三条结论：

1. **"8 个 node 共享一条 80 GB/s"不成立**：摊开是全压一个窗口的 9.2 倍，十四窗口
   合计 5.2 TB/s。上一版算的"80 GB/s"来自 `10000 MT/s × 8B`，那个字段没有给位宽，
   换算不成立。
2. **"每个窗口一条 80 GB/s"也不成立**：单窗口 355-411，是 DRAM node 的 2.3 倍。
   上一版"单窗口 129-364、差 2.8 倍"是把窗口交给**不同 SCCL 的核**压出来的伪影，
   旧表自己的距离一栏就能对上（364 的配的是 61，192 的配的是 81）。
3. **DDRC 计数器证实这些字节不走 DDR5**：压 node30（389 GB/s）时，32 个 DDRC 的
   `flux_rd` 合计按 32 字节/事务只折出 0.59 GB/s。封装内内存有自己的接口。

多路能不能叠加，四条路径两种脾气（每路 32 核、1GB）：

| 路径 | 单路 | 多路同时 | 性质 |
|---|---|---|---|
| 配对（61） | 378-410 | 3 窗口 1050-1126、4 窗口 1535、14 窗口 5238 | 完全线性 |
| 同 SCCL 非配对（71） | 193-200 | 3 路 452-492、4 路 613 | 部分叠加 |
| 跨 SCCL（81） | 130-138 | 3-4 路 **173** | **链路硬墙** |
| 跨 socket（91） | 18 | 3 路 **19** | **链路硬墙** |

跨 SCCL 的 173 与哪一对 SCCL 无关（0→1、1→0、8→9、9→8 都是 173-174），双向同时
跑合计 250（近似全双工）。所以"跨 SCCL 慢"不是窗口端口不够，是那条链路就这么宽。

**一个窗口 = 一个 UC**：压 node30 时只有 `hisi_sccl9_uc2`（node14 的 UC）大幅计数，
其余 15 个只有背景。每 SCCL 4 个、每 socket 16 个、全机 32 个，与 16 个内存 node
1:1。`cring_txdat_cnt` 是这层的字节计数器（1 计数 = 256 B）；`ucN_0..3` 四个子设备
读数完全相同，是同一单元的多路读口，不是四条通道——**通道数从软件侧读不出来**。

关于线程：16 → 235、24 → 285、**32 → 423**、38 → 394；48/76 线程压在 34-38 条核上
掉到 314-376，是抢核，不是内存效率。

**HMAT 不能当物理量用**：延迟表 = SLIT 距离照抄（封装内 16 列统一减 30），带宽表
数据类型是规范外的 3、值 25:250（"10 倍"）。**倍数碰巧和实测差不多**（5238 / 678
= 7.7），但**绝对值对不上**：基本单位写着 1000ps / 1024MB/s，折出来是 10ns /
25.6 GB/s，实测是 130ns / 380 GB/s。内存侧缓存表全 0。

> 复现：`tools/finish-hw-open-items.sh`（root，导出并解析三张表 + 跑 B 段），
> `tools/parse-acpi-hw.py <目录>`（单独解析），`tools/probe-onpkg-bw.py`（带宽结构，
> 非 root）。注意本机 HMAT/SRAT 表头后各有 4/12 字节填充、HMAT 条目是 16 位。

## 6. L2 容量与组相联：为什么"总容量够 ≠ 装得下"

`chase` 细扫（本轮，20M 次）：

| 工作集 | 256KB | 320KB | 384KB | 448KB | 512KB | 576KB | 640KB | 704KB | 768KB | 896KB | 1MB |
|---|---|---|---|---|---|---|---|---|---|---|---|
| ns/访问 | 9.84 | 7.81 | 8.14 | 8.42 | 9.50 | 8.83 | **11.54** | **19.80** | 17.51 | 36.19 | 46.69 |

> 这张表是**下午轮**；与 `headroom.md` §1.1 的上午轮比，512-640KB 三档差 0.3-1.4ns，
> 704/768KB 两档差 3-4ns。后者还出现 19.80 → 17.51 的不单调，属于 run-to-run 噪声；
> 结论只取"640KB 开始掉、704KB 已在 16-20ns"，不要逐点插值，也不要拿它跟上午轮
> 做逐点比较。

- 512/576KB 两档都在 **8.8-9.5ns**（互有高低，是噪声量级；上午轮同一区间是
  8.6 → 10.3）。**640KB 起才真正掉，704KB 已到 16-20ns**。
- L2 标称 768KB，但按**延迟口径**，有效容量约 **640-704KB**（约 85%）。原因见
  `headroom.md` §1.0.1：**12 路 × 1024 组**——一个地址的组号由地址位决定，只能进
  那一组；12 路是"装满时每组的平均行数"，Poisson 涨落让部分组先满；4KB 页的
  **颜色**（物理页号低 4 位决定落进哪 64 个组）让分布更不均。
- **工程含义**：把工作集做到 512KB 以内是"确定在 L2"；做到 640KB 就已经有一半在
  赌运气。桶化那条路的表（8KB）远在这个门槛内，所以它的问题从来不是容量。

> **两个"有效容量"口径，不要混用**：`headroom.md` §1.1 用的是**命中率口径**——
> "L2 miss 还能低于 1% 的最大足迹" = **512KB**（实测 miss：512KB 0.1%、576KB 6.0%、
> 640KB 11.5%）；本节用的是**延迟口径**——"这一档的依赖链延迟还算不算 L2 速度"，
> 到 576KB 仍是 8.8-10.3ns。两者不矛盾但也不是同一个数：**做容量规划用 512KB，
> 判断"这一档算不算 L2"用延迟表**。
>
> 这里还留着一个没结清的观察：576KB 的 miss 率已有 6%，但两轮的依赖链延迟都还在
> 9-10ns 量级（上午轮 8.59 → 10.25）。按"6% × 128ns"应当涨到 16ns 左右。**说明这些
> miss 没有全部落在关键路径上**（探针本身有预取与多行补齐），但具体机制没有单独测过——**这是
> 一个待解释项，不要拿它去反推"L2 有多大"**。

## 7. TLB 与大页：一个"该优化却是负结果"的样板

- TLB miss 后要沿多级页表 page walk（最坏 4 次内存访问）。
- 但实测开/关 2MB 大页（THP）：延迟与 gather **都没有差别**（36t：11.76 vs 11.66µs，
  RESULTS §2.16.6）。
- **原因**：page walk 与数据 miss **并行**发生，藏在 128ns 后面。数据 miss 本来就要
  等 128ns，page walk 的额外几次访问被这段等待吸收掉了。
- **通用教训**（写进 `headroom.md` §8）：一个延迟如果**藏在更长的延迟后面**，
  优化它就是 0 收益。判断方法是"关掉它，看总时间动不动"，不是"算它能省多少"。

## 8. 这些数怎么用：把硬件参数映到三格上

| 格子（headroom §4.5） | 用到的硬件数 | 得到的下界 | 现状 | 差 |
|---|---|---|---|---|
| 整行 A=16 行拷贝 | **133.5ns** ÷ 15.5 = **8.6ns/行**；探针实测 11.4ns/行 | 11.4 | 24.0 | **2.1x** |
| 桶化（L1 常驻查表） | L1 命中 2.0ns + 每元素 6 条指令 ÷ IPC 2.6 | 0.66-0.71 ns/元素 | 1.8-2.5 | 1.8-3.5x（对实测地板 1.08-1.29x） |
| 1D 大值域 gather | 与行拷贝同一套（133.5ns ÷ 在飞） | 5.65 ns/元素 | 22.3 | 3.9x（但零覆盖） |

**一句话**：三格的"下界"来源只有两种——**要么在等 DRAM（看 15.5 条窗口），
要么在发指令（看 L1 的 2.0ns 与 IPC）**。搞错是哪一种，就会拿错尺子
（`headroom.md` §1.4 的"两把尺子"）。

## 9. 可信条件：什么时候这些数不能用

| 条件 | 影响 | 怎么判 |
|---|---|---|
| **机器慢态**（RESULTS §2.22，已发生三起） | **延迟/带宽类不受影响**；**每次调用的固定成本 +40µs**（`x1[i1]` 6→47µs） | 跑三项金丝雀（`benchmarks/canary.py`）；C 探针（本文这些）对慢态**失明**，不能当健康判据 |
| 不绑 `--membind` | 内存可能落在远端 node：跨 SCCL 延迟 ×2.0、带宽 ×0.37；**跨 socket 延迟 ×2.7、带宽 ×0.13**（§5.4） | `numastat -p <pid>` 或看距离表 |
| 不绑 `--physcpubind` | 线程可能漂到别的 socket | `taskset -pc <pid>` |
| 后台有编译/他人负载 | 带宽类显著偏低（共享内存控制器）；还会抬高 L2 的实测 miss 率 | `cat /proc/loadavg` + 金丝雀 |
| `chase` vs `latency` 探针 | `latency` 含 ~2.6ns 的 `volatile` 税，绝对值偏高 | 引数字时确认探针名 |
| **内存放在 node 16-31** | 那是 CPU 封装内内存（无核，10000 MT/s）：配对核 141ns / 355-411 GB/s，跨 SCCL 只剩 137-195，跨 socket 360-477ns 且只有 18 GB/s（§5.5） | 你显式 `--membind` 过，或策略里带了 interleave |

**本轮的可信性背书**：延迟阶梯与既有快态轮次同向（§2）；带宽与既有快态差 2-4%
（§4.3）；PMU 与墙钟互证（RESULTS §2.21.4）。所以本文数字**在部分恢复的机器态下
仍然可用**，但**绝对带宽不宜直接与"快态最好值"做 1% 级比较**。

## 10. 探针清单：想查什么跑哪条

```bash
gcc -O3 -fopenmp -o memprobe benchmarks/memprobe.c     # 一次编译
A="numactl --physcpubind=190-227 --membind=5"          # 绑核 + 绑内存，缺一不可

$A ./memprobe freq 200000000                 # 主频/健康（一次依赖加法）
$A ./memprobe chase 32768 30000000           # 单点延迟（指针追逐，无 volatile 税）
$A ./memprobe latency 1024 1000000           # 旧版延迟探针（含 ~2.6ns 税，仅对比用）
$A ./memprobe mlp 64 24 20000000             # 在飞窗口（S 条独立链）
$A ./memprobe bandwidth 1024 8 rd 3          # 顺序带宽（1/8/16/36 线程各来一遍）
$A ./memprobe bandwidth 1024 8 cp 3          # 拷贝带宽（读+写合计）
$A ./memprobe gathermt 1024 20000000 1 seq   # 顺序 gather（含预取器收益）
$A ./memprobe gathermt 1024 20000000 1 rand  # 随机 gather（纯延迟口径）
$A ./memprobe idxgather 100 1000000 1 16     # 内核形状下界（小工作集/L1 常驻）
$A ./memprobe rowgather 16 16 1 131072 pf16  # 行拷贝探针（A=16 的下界 11.4ns/行）

# NUMA：核固定 node 5，只动 membind
numactl --physcpubind=190 --membind=6 ./memprobe chase 65536 20000000
numactl --physcpubind=190-227 --membind=6 ./memprobe bandwidth 1024 8 rd 3
```

| 探针 | 回答什么 | 不能回答什么 |
|---|---|---|
| `chase` | 某工作集下的往返延迟 | 并发能力（它是单链） |
| `mlp` | 能同时挂几条、饱和点在哪 | 实际内核用了几条（要 perf） |
| `bandwidth` | 稳态吞吐上限（分线程/方向） | 小规模副本的能力（会被固定开销拖住） |
| `gathermt` | 顺序/随机差多少（预取器收益） | 内核实现的好坏 |
| `idxgather` / `rowgather` | 内核形状的下界 | 端到端收益 |
