# 路径收益矩阵：每条路由各值多少

**数据唯一出处：[`benchmarks/RESULTS.md`](../benchmarks/RESULTS.md) §2.14**
（由 `benchmarks/bench_path_matrix.py --ab` 一次产出，`--json` 出原始数据）。
本文只写裁决与读法，不复写数字——同一个数在两处各自漂移过一次，就再也没人知道
哪个是当前值。

> **这篇讲什么**：每条路由值不值得保留——按路由而非场景组织的收益矩阵。
> **读完你能回答**：某条路在什么条件下为正、为负？哪些结论会随线程数/规模/
> 源大小翻转？哪些路该合并或删除？
> **怎么读**：先看 §4 裁决表，再按 §3 的谓词找具体路径；改代码前看 §7 局限。
> **本篇代号**：S1/P1/M1/M2、R1，以及路由名。术语见
> [`glossary.md`](glossary.md)。

## 1. 这份文档解决什么问题

按场景测（§2.9 的 31 场景、§2.10 的生产形态）回答的是"这个 workload 快不快"；
按路径测回答的是"**这条路本身值不值得存在**"。两者不能互相替代：一个形态快，
可能是形态本身友好（源小、全在 L1），跟走上哪条路没关系。

所以本轮的产物是**路径 × 规模 × 线程**的矩阵，横向还有一组"兄弟对照"（§2）。
要判断"能不能删掉某条路"，看这张矩阵；要判断"某个模型快不快"，看 §2.9/§2.10。

## 2. 两条镜头（必须同时看）

| 镜头 | 问题 | 怎么读 |
|---|---|---|
| **路径 vs aten** | 落在这条路上的形态，比 aten 快多少 | 产品口径：>1 才是收益。这是"这条路径服务的人群是否受益" |
| **路径 vs 兄弟路径** | 同一份工作量，只差一个谓词，落到另一条路 | 归因口径：这才是"这条路径本身"的价值 |

**为什么第二条不可省**：本仓没有 per-route kill switch。把一条路关掉再测是做不到的，
能做的只有**找谓词、把谓词翻过来、其余变量不动**——于是"连续 vs 非连续下标"、
"dom=2048 vs 2049"、"run=10 vs run=2"、"线程 8 vs 16" 这类对照就成立。

**反面教材（本轮踩到）**：想给"raw 行拷贝 vs 两遍模型"造兄弟时，改 K 会同时改变
工作量与并行粒度——`K=65536` 与 `K=131072` 的 per-element 成本根本不可比（后者
反而更低，只是摊销更好）。**谓词本身是规模时，造不出干净兄弟**。这类只能退回
"per-element 成本 + 两条路各自的 aten 比值"来间接看，结论要写弱一点。

## 3. 路径清单与覆盖（改代码时按谓词找 case）

判据来自 `status.md` §3 的路由树；case key 就是 `bench_path_matrix.py` 里的名字，
`--routes` 可以列出全表。

| 路径（按判定顺序） | 判据要点 | 覆盖 case |
|---|---|---|
| mask 单遍压实 | 单 mask、覆盖前 m 维、连续、CPU | `e1_mask_k*` |
| `small_single` | 单整数下标、K≤4096、self 与 idx 均连续 | `e2_ss_k512/2048/4096` |
| `small_multi` | 多索引同 shape、连续、n≤65536 | `e3_sm_k1024` |
| `rowcopy_direct`（R10 直写） | out 非连续且 `rowcopy_direct_ok`（单索引/idx 连续/A≥4/K≥1024/f32-f64/SVE512/尾块同置换） | `r0_direct`、`r0_bypass` |
| `gather_direct` | 通用路径但 K<1024 | `r0_k512`、`r1_direct` |
| raw 行拷贝（M1） | 单索引、after 连续、A>1、`A≥4096 ∨ A<16 ∨ (A≤64 ∧ B*K≤65536)`、idx 连续、f32/f64/**i32/i64**（T16） | `r2_raw_k4097/8192/65536`、`r2_f32_a3`、`r2_i32_a64`、`r10_i32_a3`、`e2_ss_k8192` |

> `EXPECT MISMATCH`。本轮 101 个测量点全部对上——这一条比表里的数字更重要，
> 上一版探针就是靠它抓出"用例其实还在快路径上"的。

## 4. 裁决：哪些路径有实质意义

分档按"稳不稳、值多少"两个维度，不按代码行数。依据列指向 RESULTS §2.14 的表行。

| 路径 | 档位 | 依据（§2.14 表 A / 表 B） | 一句话 |
|---|---|---|---|
| `rowcopy_direct` | **强（最强）** | `r0_direct` + 兄弟 `r0_bypass` | 失去直写资格 = 慢一个数量级，这条路的判据本身就是最大的性能开关 |
| `small_single` | **强** | `e2_ss_k*` + 兄弟 `e2_ss_nc_k4096` | 收益全部来自"不进 normalize/通用路由"，1 线程处最亮，且随线程数衰减 |
| raw 行拷贝（M1） | **强** | `r2_raw_k*`、`r2_f32_a3`、`r2_i32_a64` | 全程为正，是行 gather 的主力；规模变大时变的是线程效率，不是"会不会赢" |
| `strided_rows` | **强** | `r3_run10*` + 兄弟 `r10_run2` | 有连续 run 就值得接管；但这条判据本身只值 1.1-1.5 倍，价值大头在"块拷贝 vs 逐元素" |
| `gather_fused` | **分情形** | `r10_run2`（强）、`r10_transpose`（≈1x） | 宽 A 的非连续小块靠它兜底很值；纯转置只是不掉队 |
| 桶化查表（T4） | **中** | `r5_bucket_*` + 兄弟 `r9_dom2049` | 稳定正收益，但只覆盖"B==1 ∧ A==1 ∧ 值域≤2048"这一窄带 |
| `small_multi` | **中** | `e3_sm_k1024` | 1 线程明显，线程数上去后收益迅速收窄 |
| 多索引 raw 行拷贝（线程门 16） | **中** | `r4_multi_t8` vs `r4_multi_t16` | 门的另一侧（8t）明显更慢，说明门的位置是对的；但这是"线程数不同"的对照，不是纯谓词 |
| `single_1d_sve`（T15-C） | **中偏弱** | `r6_sve_*` + 兄弟 `r9_big_i32` | 低/中线程为正，大 K + 16 线程处已经为负 |
| `single_1d` 标量单遍 | **弱（兜底）** | `r7_scalar_*` | 只是"比多跑一遍 linearize 强"，本身不构成收益 |
| 两遍模型 | **弱（且会变负）** | `r9_dom2049`、`r9_small_i32` | 1 线程还能赢，8/16 线程在 1D 小源上是负收益；这正是 M1/M2 要消的东西 |
| `gather_direct`（K<1024） | **仅兜底（可能为负）** | `r1_direct`、`r0_k512` | A=1 时与 aten 基本持平（略低）；A 大时是数量级的负收益——它不是快路径，是兜底 |
| mask 单遍压实 | **结论不稳** | `e1_mask_k*` | 小 mask 赢在 aten 的固定开销上，规模上去回到 1x 附近，且出现负值；结论要看 §2.10/§2.11 的生产形态，不能只看本表 |

读这张表要注意一件反直觉的事：**"强"不等于"可以继续加码"**，因为强档的收益大多
来自"少绕一圈"（跳过 normalize、跳过 linearize、跳过 tmp 缓冲），也就是**已经在
链条前端的路径**；链条后端的路径再优化，能省的东西本来就少。

## 5. 逐条读数（方向 + 什么时候会翻）

**`rowcopy_direct` / `rowcopy_raw`**：收益随线程数下降（aten 也会并行），但
**兄弟对照的差值不随线程数消失**——判据翻面就是数量级的差距。结论：这条路上的
守卫（`rowcopy_direct_ok`）值得写复杂，因为它一次判定守住了整条链路的形状。
需要注意它不是"快路径"，而是"唯一正确的写入方式"：不合格时不是变慢，而是错位写入，
所以**不能为了性能放宽它**。

**`small_single` / `small_multi`**：全部价值是"不进 normalize + 不进通用路由"。
所以它们的收益在 1 线程最大，线程数越高 aten 的并行越能追平；但**合并它们一定是
负收益**（等于把小调用降级成普通路）。兄弟对照（把下标改成非连续视图）说明：
这不是"某种形态天生快"，而是"这条路替调用方省掉了固定成本"。

**`gather_direct`**：A=1、K 小的时候与 aten 基本持平（aten 也有自己的 direct indexer），
一旦 A 变大就是数量级落后（标量逐元素 + 每元素一次行内边界检查，靠线程摊薄追不上
块拷贝）。所以它的定位只能是"K<1024 的正确性兜底"，**不要指望它带来收益**。

反过来说这里藏着一个真正的机会：`K<1024` 的短路**排在所有行拷贝路由之前**，所以
"K 小但 A 大"的单索引行 gather 根本到不了 `rowcopy_direct` / raw 行拷贝。表 A 里
cl4d 的 K=512 与 K=1024 就是这一对——K 减半、耗时反而翻几倍。这不是精度问题，
是**路由顺序造成的悬崖**；要修就得把"宽行"从 K<1024 短路里摘出来单独判，而不是
去优化这条兜底路径本身。

**桶化 / `single_1d_sve` / `single_1d`**：三条都服务"1D 纯 gather"，靠的是同一个
前置值域扫描。桶化的收益随 K 增大变稳；`single_1d_sve` 只在"i64 下标 + 大源 +
多线程"时才有意义，源小或线程多到 16 时会退化；标量单遍基本是兜底。
**兄弟对照（i64 vs i32 下标）是本轮最有价值的一条**：它说明那条"专用 SVE 门"不是
装饰——同一形态只换下标宽度，就会掉到两遍模型上去。

**两遍模型**：它是所有落选路径的汇合处，也是最应该被削的。在行 gather（A 大）上，
两遍的多余扫描被内存带宽摊掉，看起来还行；在 1D 小源上，多出来的两遍扫描直接
把正收益吃成负收益。**读这张表时不要用行 gather 的结论去推断 1D**——两者的成本
结构完全不同（每元素 vs 每行）。

**mask**：唯一一条"结论不稳"的路径。它的收益主要来自 aten `nonzero` 的固定开销，
所以小规模上很好看，规模一上来就回到 1x 附近，中间还会出现负值。**这条路的结论
必须按规模分档写**，不能给一个总倍数。

## 6. 与其它文档的关系

- **M1/M2 的目标就在这里**：§4 里"弱/会变负"的那条（两遍模型）正是 M1（值域判定
  下传）与 M2（探测失败别扔结果）要动的地方；`single_1d` 标量是它的兄弟路径，
  两遍模型省下的就是它多跑的那一遍。方法论与检查表见 `route-merge-analysis.md` §4。
- **R1（演进方向）**：`status.md` §7 的 R1"1D 小源跳过前置值域扫描"就是 §4 里
  两遍模型在 1D 小源上变负的那一格；本轮矩阵给它补上了"翻面以后能值多少"的基线。
- **新增路径之前**：`route-merge-analysis.md` §6 的五条检查表（同工作量兄弟、
  判据边界两侧、计数器分布、是否引入新的 O(K) 扫描、是否改变已有热形态的判定顺序），
  其中"计数器分布"现在有了固定脚本：`bench_path_matrix.py --routes`。

## 7. 已知局限

1. **没有 per-route kill switch**：所有归因靠谓词翻面，所以"兄弟对照"里的差值
   仍然可能混入"翻面本身带来的成本"（例如非连续下标读起来更贵）。表 B 的每行
   都标了翻的是哪个谓词，读的时候请把这一项算进去。
2. **4 条路径没有专属计数器**，它们的"实际路由"是计数器 + 谓词共同确认的。
   补计数（并立"计数器之和 == `dispatch_count`"不变量）是后续轮次的事。
3. **单机单 VL**：n20 / node5 / SVE512。换 VL 或换 NUMA 节点，B 里的绝对值会变，
   但"翻面即数量级"这类结构结论不受影响；A 里的比值会整体移动。
4. **16 线程那列噪声大**：三轮之间部分比值的极差在 22-35%（RESULTS §2.14.4
   逐个点名；中位极差 16t 18%、1t 6%）。另外 `e1_mask_k64k` 8t 本轮 451%、
   已作废，别引它的 2.55。所以本表只按"同带"下结论，不按小数点后两位。
5. **本表不覆盖 out= 变体**：`index_out` 走的是同一条 `index_into`，入口校验不同；
   要单独看它得另加 case（当前没有）。

## 8. 复现

```bash
# 路径 × 规模 × 线程矩阵（aten/hpc 两进程交替 × 3 轮，含 expect 校验与噪声列）
HPC_AFFINITY=190-227 HPC_THREADS=1,8,16 HPC_ROUNDS=3 \
  python benchmarks/bench_path_matrix.py --ab

# 只看每个 case 期望落在哪条路（不测时间）
python benchmarks/bench_path_matrix.py --routes

# 原始 JSON（每 case 每线程一行，含 route / expect / ratio）
HPC_THREADS=1,8,16 python benchmarks/bench_path_matrix.py --ab --json > path_matrix.json
```
