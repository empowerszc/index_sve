03三段模型：为什么旧基准只看到"几倍"

04强扩展效率（§6.1）

效率 = 加速比 ÷ 线程数，基准 = hpc 自身 1t。两个 1D 大 K 形态代表两种 扩展行为：f64 行放大 8x，8t 后撞带宽；f32 行放大 16x 但请求更多，延迟掩盖更充分。

x[:,i] 的反直觉：单线程已 2.0x，但 8t 后效率 67%→24%； aten 同样饱和，所以相对比值反而在高线程回到 1.9x——比值好看 ≠ 绝对变快。

06机理二：4B SVE gather 停在每线程发射下限

dom=1M 回退单遍 SVE 4B gather（f32+i64 下标、源 4MB>512KB 门槛）。 19t 时 aten 加速 45.4x 远超线程数——4MB 源摊进 19×768KB L2 聚合容量，每线程每元素 降到 13.1ns；hpc 只有 22.7x，停在 19.9ns/元素（§6.5.3）。

19.9ns 从哪来

§5.9.1 的 SVE 4B gather 微码/发射下限 ~18–23ns/元素。 一条 gather 指令内部 8 条 miss 是串行的 → "一条 gather 在飞" 等价一条依赖链： 137ns ÷ 8 lane ≈ 17ns/元素，与 19.9 吻合。

2026-11-02 复核修正（口径）

"19.9ns 是发射下限"只在 MLP=1 下成立。多条独立 gather 交错时 SVE 8B 只要 4.73–5.18ns/元素，比标量 8 路展开还快。结论改成：SVE gather 一批只给 8 条 lane， 收益上限 8–16 条在飞；真正的杠杆是把地址计算批量化到取数之前（headroom H2b）。 两条曲线量的是不同循环结构，引用必须带前提。

这不是带宽墙：行流量只到 168GB/s 的六成，也不是"节点被占满"—— 是每线程在飞请求数的差异。标量乱序窗口同时压 ~10 条 miss，SVE gather 一条指令 挂的请求数固定，线程再多只是线性叠加（§6.5.3）。

SGI 格 19t 两侧都在 32–37µs，每线程折算 44.8/50.6ns 高于 1t——由入口+并行固定开销决定，不是每元素成本（§6.5.3）。

0864B 行放大：1B / 4B 大 K 的硬上限

内存按 64B line 计费。随机取 1B，整条 64B 都被搬运——行放大 64x。 这不是实现问题，是随机访问的定义（§5.9.3 / headroom §2.2）。

09不劣化的对照：劣化不是全局的

同一张生产矩阵（§6.5.5），rowcopy 与 K≤2048 桶化全档 ≥1.24x—— 所以"生产劣化"精确地就是 A=1 + K∈[4096, 55296] + 线程≥6 这一族。

10缓解方向（§6.5.6，均未实现）

① 去掉桶化串行段

第一趟用原子 min/max 或每线程局部桶，"扫描+建表"合成一趟；已知 dom 时直接按 dom 建表。部分已兑现：免 pass 1（2026-11-03 上午）与免串行建表（跨度 ≤64KB，补丁 3b）已落地。

② 按每线程元素数限线程

A=1 且 K/线程数 < 2048 时减少有效线程。当前 adaptive_grain 只控 chunk 大小，不减线程数。

③ 提高 4B gather 的 MLP

把 PREFETCH_DIST 软件预取扩展到 4B 向量路径，或每线程交错多流 gather（headroom H2b 的地址批量化是同一族）。

④ 基准侧纪律

本节的形态矩阵纳入常规验收；任何"单算子 N 倍"的结论必须附 A=1+K∈[4096,55296]+6–19t 一族的数字，否则就是端点错觉（§6.5.4）。
