## 1. PyTorch 的世界：Python 皮、C++ 骨

**本章解决什么疑问**：我写的 Python 一行为何会进 C++？中间隔着什么、
为什么隔着？

### 1.1 两层架构

`pip install torch` 装来的其实是一个"双层应用"：

- **上层是 Python 包**：你 `import torch` 拿到的模块。它提供 `Tensor` 类、
  上千个函数、autograd、`torch.nn` 这些 Python 层的便利设施；
- **下层是 C++ 库**：真正干重活的地方。张量的存储、算术、内存管理全在
  C++ 里，Python 这层更像一个"遥控器"。

这个 C++ 核心有个名字：**ATen**（A Tensor Library）。你平时说的"算子"
（operator）——加法、卷积、索引——它们的本体就是 ATen 里的 C++ 函数。

为什么这样设计？性能是其一，但更根本的是**生态**：C++ 核心让 PyTorch 能被
C++ 程序直接嵌入（训练好的模型不回 Python 就能推理），也接得住 CUDA 这类
C++ 生态的加速器。

### 1.2 一行代码的四段旅程

```text
y = x[idx]              你写的一行 Python
      │
      ▼
 ① Python 层             x.__getitem__(idx) 被调用
      │
      ▼
 ② 绑定层（binding）      胶水代码：Python 对象 → C++ Tensor
      │
      ▼
 ③ 分发层（dispatcher）   "这是 CPU 上的 float32，走 CPU 实现"
      │
      ▼
 ④ ATen kernel            C++ 函数，真正读写内存
```

- **② 绑定层**：Python 和 C++ 是两个世界，对象模型完全不同（Python 侧一切
  皆 `PyObject`，C++ 侧是 Tensor 结构体）。绑定层就是那座桥，PyTorch 的
  Python 接口大部分由手写的 CPython C API 包装构成（部分模块用 pybind11）。
  对一次操作来说，"过桥"只发生一次；
- **③ 分发层**：同一个算子名（比如 `index`）在 CPU、CUDA、各种 dtype 上
  各有不同的实现。分发器按"什么设备、什么类型"挑出正确的那个。你可以把它
  理解成一个巨大的 switch——只不过它的 case 表是注册出来的、可扩展的：
  第三方库能塞进自己的后端，靠的就是这个设计；
- **④ kernel**：终于到了干活的 C++ 代码。标题里的 `aten::index` 指的就是
  这里——ATen 中名为 index 的算子实现。

这套机器看起来繁琐，但它买来的是**通用性**：一个 Python 接口后面可以挂
任意设备、任意类型、任意后端的实现。记住这个 trade-off，第 5 章讲"为什么慢"
时它会再次出现。

### 1.3 去哪里找这些代码：一张仓库地图

有 C++ 背景的读者看到这里多半想自己翻源码。PyTorch 仓库里三片区域与本文
直接相关：

```text
torch/csrc/            Python ↔ C++ 绑定层（第①站的代码住这里）
aten/src/ATen/         ATen 核心：算子声明、分发、TensorIterator（②–⑤站）
aten/src/ATen/native/  各设备算子实现（第⑥站的 CPU kernel 住 native/cpu/）
```

一个实用的深入方式：拿着深度版附录 A 的行号索引（每个函数精确到文件:行），
对照这三片区域读源码——本文六站与那里的六节一一对应。

> **深挖**：Python 入口到 ATen 的实际代码路径（`THPVariable_getitem` 等的
> 行号）→ 深度版 [§4 实现全链路](aten_index_aarch64_analysis.md#4-pytorch-cpu-实现全链路)
> （§4.1–4.3）。

## 2. Tensor 的数据模型：一块内存 + 一张说明书

**本章解决什么疑问**：`torch.randn(3, 4)` 在内存里到底长什么样？
"视图"（view）为什么可以零拷贝？

这一章是全文的地基——后面所有章节（索引语义、调用链、性能分析）都建立在
这同一个模型上。

### 2.1 Tensor = storage + 说明书

一个 Tensor 由两部分构成：

```text
Tensor
 ├── 数据：一块一维的、通常连续的内存（storage）
 └── 说明书（元数据）：
      ├── sizes    形状，如 [3, 4]
      ├── strides  步长：每个维度上，下标 +1 时地址跳多少个"元素"
      ├── offset   数据起点在 storage 里的偏移
      └── dtype    元素类型（float32 / int64 / …）
```

关键认知：**内存永远是一条平的一维数组，"形状"只存在于说明书里**。

用本文的主角举例（第 4 章还会用它走完整条链路）：

```python
x = torch.arange(12).reshape(3, 4).float()   # 值 0..11
```

它是一条 48 字节的一维内存（12 个 float32，每个 4 字节），说明书写着
sizes=[3, 4]、strides=[4, 1]（元素单位；换算成**字节**是 [16, 4]）：

```text
逻辑视图                       物理内存（storage，共 48 字节）
 x[0] = [ 0,  1,  2,  3]      ┌────┬────┬────┬────┬────┬────┬─
 x[1] = [ 4,  5,  6,  7]      │ 0  │ 1  │ 2  │ 3  │ 4  │ 5  │ …
 x[2] = [ 8,  9, 10, 11]      └────┴────┴────┴────┴────┴────┴─
                               字节: 0    4    8   12   16   20

地址公式（字节）：addr(行 r, 列 c) = r × 16 + c × 4
例：x[2][3] → 2×16 + 3×4 = 44 字节   ← 记住 44，第 4 章见
```

任何形状的操作最后都落到这条一维内存上：`x[2][3]` 的取数，物理上就是
"从 storage 开头走 44 字节，读 4 个字节"。

（写过图像处理的话：strides 就是行跨度 pitch/row-stride 的推广——
**每一维**都有一个。）

### 2.2 视图：改说明书，不动数据

理解了说明书，"视图零拷贝"就不再神秘：

```python
t = x.transpose(0, 1)   # 形状 3×4 → 4×3，数据一个都没动
```

`transpose` 只是把说明书改成 sizes=[4, 3]、strides=[1, 4]——同一块内存，
换一种读法。`reshape`（在能免费做的时候）、切片 `x[1:]`、`x[:, ::2]`
同理，全是改说明书。

PyTorch 甚至暴露了直接手写说明书的原语：

```python
v = torch.as_strided(x, size=(2, 3), stride=(4, 2), storage_offset=0)
```

意思是："给我一张说明书：形状 2×3，行步长 4、列步长 2，从 storage 开头
读起"。于是 `v[i][j]` 就是内存里第 `i×4 + j×2` 个元素。

视图是 PyTorch 性能设计的基石——切片和变形零拷贝、零内存分配。但天下
没有免费的午餐，它埋下了一颗种子：

### 2.3 题眼：任意说明书 ⇒ 通用性成本

既然说明书可以任意写，那么**任何**处理 Tensor 的通用代码，都必须面对
"任意 stride、任意形状、数据可能被多个视图共享"的最一般情况：

- 写 `y = x + 1` 的 C++ 实现时，你不能假设 x 连续（contiguous）；
- 写索引 kernel 时，你不能假设"第 i 行紧挨着第 i-1 行"；
- 连"这个 Tensor 是不是别人的视图"都要考虑（改它可能改到别人）。

`x[idx]` 的实现之所以要绕六站（第 4 章），根源就在这里：**它伺候的不是
"一个 [3, 4] 矩阵"，而是"任意一张合法说明书"**。

### 2.4 亲手摸一摸

"说明书"模型好不好使，跑五行代码就知道：

```python
x = torch.arange(12).reshape(3, 4).float()
x.stride()             # (4, 1) —— 元素单位的步长
x.t().stride()         # (1, 4) —— 转置只是换了说明书
x.is_contiguous()      # True
x.t().is_contiguous()  # False —— 同一块内存，说明书"换了个写法"

v = torch.as_strided(x, size=(2, 3), stride=(4, 2), storage_offset=0)
v[0]                   # tensor([0., 2., 4.]) —— 取第 0、2、4 个元素
v[1]                   # tensor([4., 6., 8.])
```

强烈建议亲手跑一遍——"转置不搬内存"这件事，亲眼看一次 `x.t().stride()`
比读十遍文字都牢。

## 3. `x[idx]` 承诺了什么：语义

**本章解决什么疑问**：`[]` 有时给我视图、有时拷贝数据，分界线在哪？
结果长什么形状？

### 3.1 基本索引 vs 高级索引：一条分水岭

`[]` 里放的东西分两族，行为天差地别：

| 你放的 | 学名 | 行为 |
|---|---|---|
| `x[1]`、`x[1:3]`、`x[:, ::2]` | 基本索引（basic indexing） | **视图**——改说明书，零拷贝 |
| `x[idx_tensor]`、`x[mask]` | 高级索引（advanced indexing） | **拷贝**——新分配内存，逐元素搬运 |

本文主角 `aten::index` 说的就是右边一族：**用 tensor（或 bool mask）作
下标的索引**。

分水岭的直觉：切片描述的是"规则可表达的子区域"（连续、等距），说明书
表达得了，所以给视图；tensor 下标是一张"任意无规则的清单"，说明书
表达不了，只能真搬数据。

**坑**：`x[1:3]` 是视图，改它会改到 `x`；`x[torch.tensor([1, 2])]` 是拷贝，
改它与 `x` 无关。混用两者是常见 bug 来源。

### 3.2 高级索引的心智模型：按清单取货

把 `idx` 想成一张**取货清单**，`x` 是**仓库**，结果 `y` 是按清单顺序装好的
**新箱子**：

```python
x = torch.randn(4, 5)                # 仓库：4 行 5 列
idx = torch.tensor([1, 3, 0])        # 清单：要第 1、3、0 行
y = x[idx]                           # 装箱：y 形状 [3, 5]
# y[0] 就是 x[1]，y[1] 就是 x[3]，y[2] 就是 x[0]
```

三个要点：

- **顺序即清单**：结果的第 i 项取的是清单第 i 项指的货——`y[i] = x[idx[i]]`；
- **可以重复取**：清单写 `[1, 1, 1]` 也行，同一行被取三次（gather 语义
  天然支持重复）；
- **可以倒着取**：负数遵循 Python 约定，`x[-1]` 是最后一行（实现上是
  "加上尺寸"的归一化，第 4 章会看到这条分支）。

顺带一个对照：若清单恰好是 `0..n-1` 顺序排列，gather 退化成 copy——
缓存最友好的情况。清单越乱，离这个理想越远。

这就是体系结构里的 **gather**（按索引收集）；它的镜像——把数据按清单散
出去——叫 **scatter**（PyTorch 里是 `index_put_` / `index_add_`）。

### 3.3 多张清单与广播

`x[i_idx, j_idx]` 用两张清单同时定位（行清单 + 列清单）：

```python
x     = torch.arange(12).reshape(3, 4).float()  # 同第 2 章的 x
i_idx = torch.tensor([2, 0])                    # 行清单
j_idx = torch.tensor([3, 1])                    # 列清单
y = x[i_idx, j_idx]        # y = [x[2,3], x[0,1]] = [11.0, 1.0]
```

两张清单**逐位置配对**（先广播对齐形状）：第 0 个输出元素 =
`x[i_idx[0], j_idx[0]]` = `x[2,3]`，第 1 个 = `x[0,1]`。

结果形状的规则，用几个例子就能归纳出来：

| 写法 | 结果形状 | 为什么 |
|---|---|---|
| `x[i_idx]`（x 是 [3,4]） | [2, 4] | 被索引的 dim0 → 清单长度 2；没被索引的 dim1 → 原样跟在后面 |
| `x[i_idx, j_idx]` | [2] | 两个维都被索引 → 清单（广播后）的形状替代它们 |
| `x[i_2d]`（i_2d 形状 [2,3]） | [2, 3, 4] | 清单自己的形状在前 + 尾随维在后 |

一句话总结：**清单的形状放在前面，没被索引的维跟在后面**。

（还有更深一层的规则——被索引维不相邻时，结果维的位置会挪动——本文不
展开，深度版 §3 有完整语义。）

### 3.4 bool mask：先找坐标，再取货

```python
mask = x > 5        # 与 x 同形状的 bool 矩阵
y = x[mask]         # 一维 tensor，装着所有 True 位置的值
```

它看起来是另一种东西，实现上却是**已知操作的组合**：`mask.nonzero()`
（找出所有 True 的坐标，得到一张下标表）→ 按表 gather。所以 mask 索引
天然比整型下标**多付一遍全扫描**（找坐标），而且结果必然一维
（坐标被摊平了）。

### 3.5 两个高频坑

- **视图与拷贝混用**：`x[1:3]` 是视图（改它会改到 `x`），`x[torch.tensor([1, 2])]`
  是拷贝（改它与 `x` 无关）——两者长相接近、行为迥异，是真实 bug 的常客；
- **混合索引的形状会更绕**：slice 与 tensor 同场（如 `x[1:3, idx]`）时，
  结果形状的推导还有几条附加规则；`x[mask]` 的结果则必然是一维。想按条件
  替换又保形，用 `torch.where` / `masked_fill` 家族。

> **深挖**：完整语义规则（相邻/不相邻被索引维、`...` 与 `None` 的作用）→
> 深度版 [§3 语义](aten_index_aarch64_analysis.md#3-atenindex-的语义它到底做什么)。

## 4. 一次 `x[i_idx, j_idx]` 的完整旅行

**本章解决什么疑问**：从敲下回车到内存搬运完成，中间的六站各做什么、
为什么需要？

本章沿用第 2/3 章的例子（它与深度版 §1 的例子完全一致——读完这里再看
深度版，不用换脑子）：

```python
x     = torch.arange(12).reshape(3, 4).float()   # 值 0..11；字节 stride = [16, 4]
i_idx = torch.tensor([2, 0])                     # 行清单，占 dim0
j_idx = torch.tensor([3, 1])                     # 列清单，占 dim1
y = x[i_idx, j_idx]                              # 期望 y = [11.0, 1.0]
```

总路线图：

```text
y = x[i_idx, j_idx]
   │
   ▼ ①绑定站       Python 对象 → C++ Tensor（第 1 章那座桥）
   │
   ▼ ②语义站       拆开 [] 里的内容，认出"这是高级索引"
   │
   ▼ ③归一化站     把五花八门的清单装订成统一格式
   │
   ▼ ④重步长站     改 x 的说明书，让"取哪"与"放到哪"解耦
   │
   ▼ ⑤遍历器站     通用遍历框架排好循环结构（TensorIterator）
   │
   ▼ ⑥内核站       真正的 C++ 循环：逐元素取货
```

下面逐站参观。每站先回答"**为什么需要它**"，再看"**它做了什么**"。

### 4.1 第①站：绑定——两个世界之间唯一的桥

**为什么需要**：Python 里 `x` 是 PyObject，`i_idx` 也是；C++ 这边要的是
Tensor 结构体。总得有人翻译，而且只该翻译一次。

**做了什么**：`x[...]` 触发 Python 的 `__getitem__`，进入 PyTorch 手写的
CPython 包装（函数名 `THPVariable_getitem`，深度版里有行号）。它解开 `x`
的 Python 壳拿到 C++ Tensor，把 `[]` 里的内容拆成一个下标列表，整包转交
C++ 侧的索引入口。

这一站每次调用只过一次，成本固定。真正有意思的在后面。

### 4.2 第②站：语义判断——认出你在做哪一种索引

**为什么需要**：`[]` 里可能是 `1`、`1:3`、tensor、`...`、`None` 的任意
组合，处理方式完全不同（视图 vs 拷贝）。

**做了什么**：逐个检查 `[]` 的内容——是 slice 就当场应用（改说明书，拿
视图）；发现 tensor 下标，认出"这是高级索引"，把整包规范化后转交高级
索引的专用入口。本例 `[]` 里是两个纯 tensor，干脆利落，直接放行。

### 4.3 第③站：归一化——把五花八门的清单装订成统一格式

**为什么需要**：到了这里，下标可能是 bool mask、可能是 int32/int64、
可能形状各异。第⑥站的内核只想伺候一种格式。与其让每个内核学会应付
一切，不如在中间设一个"装订台"。

**做了什么**（装订台的五道工序）：

1. **mask → 坐标**：bool 掩码换成 nonzero 坐标表（3.4 节说过）；
2. **广播对齐**：所有清单 broadcast 成同一形状（本例 [2] 与 [2]，已对齐）；
3. **补空位**：下标个数不足 x 的维数时补空，凑齐册子；
4. **挪前**：被索引的维若中间隔着没被索引的维（如 `x[a, :, b]`），把 x
   和下标一起 transpose，让被索引维连续排到前面；
5. **统一 int64**：所有下标转成 int64。

第 5 道工序值得**记账**：清单哪怕本来就是 int32，也会被整体复制成
int64——每次调用都转一遍。这个伏笔第 5 章兑现。

装订完的册子里有三样关键信息，第⑥站直接要用：

- **indexed_sizes**：每个被索引维的长度（本例 [3, 4]，判越界用）；
- **indexed_strides**：每个被索引维的**字节**步长（本例 [16, 4]，算地址用）；
- 统一格式后的清单们。

### 4.4 第④站：重步长（restride）——把"取哪"与"放到哪"解耦

**为什么需要**：输出 y 的形状是 [2]（清单形状），x 的形状是 [3, 4]——
两边形状对不上，没法"同步遍历"。

**做了什么**：给 x **换一张说明书**（就是 2.2 节的 as_strided！）：形状
改成与输出一致，被索引维的步长改成 **0**。步长 0 意味着"这一维怎么走，
数据地址都不动"。本例：x 换上形状 [2]、步长 [0] 的哑说明书（若还有没被
索引的维，如 `x[i_idx]` 的情形，那些维保留原步长：形状 [2, 4]、步长
[0, 4]）。

数据一个字节都没动。本例前后的说明书对比：

```text
restride 前：x            形状 [3, 4]   步长 [16, 4]（字节）—— 正常的 x
restride 后：x 的哑视图    形状 [2]     步长 [0]        —— 只为对齐输出形状
```

这一步纯粹为了**对齐形状**，让下一站的通用框架能把
"x 和 y 当作同形状的两个 tensor 同步走"。真正的取货地址计算，被移交给了
专用机关。

### 4.5 第⑤站：TensorIterator——所有按元素操作的公共底盘

**为什么需要**：`y = x + 1`、`y = x * z`、`y = x[idx]`……几百个算子都
需要同一套脏活：把形状各异的若干 tensor 排成可同步遍历的结构、合并相邻
维度、决定并行切分。PyTorch 把这套脏活抽成了公共框架——TensorIterator。

**做了什么**（对本例）：

- **维度重排**：把变化最快的维放到最内层；
- **维度合并**：能合并的维合并掉——本例两维连续，直接合成一个长度 2 的
  一维循环；
- **并行切分**：把循环切段分给多线程，每段约 3000 个元素。顺带解释一个
  现象：小 tensor 索引不并行——凑不够一段。

注意一个重要的分工：TensorIterator 只管"**往哪走**"（循环结构），不管
"**取什么**"（地址怎么算）。被索引维的地址计算是索引特有的，于是有了
最后一站的专用机关。

### 4.6 第⑥站：内核循环——真正的取货

**为什么需要**：总得有人真的去搬字节。

**做了什么**：ATen 的 `cpu_index_kernel` 拿到装订册后，核心循环去掉一切
包装就这几行：

```cpp
for (每个输出元素 i) {
    offset = 0;
    for (每个被索引的维 j) {
        v = index_j[i];              // ① 读清单：第 j 张清单的第 i 项（8 字节 int64）
        检查 v 是否越界;              // ② -size ≤ v < size，每个元素都查，关不掉
        if (v < 0) v += size_j;      // ③ 负数归一（x[-1] 的实现）
        offset += v * stride_j;      // ④ 换算字节偏移（stride_j 是字节步长）
    }
    dst[i] = src[offset];            // ⑤ 取货 + 放货
}
```

用我们的例子逐元素走一遍——**这就是全部真相，没有隐藏层**：

```text
输出元素 i = 0（该用 i_idx[0]=2、j_idx[0]=3 去 x 取货）：
  j=0: v = i_idx[0] = 2 → 检查 -3 ≤ 2 < 3 通过 → offset += 2 × 16 = 32
  j=1: v = j_idx[0] = 3 → 检查 -4 ≤ 3 < 4 通过 → offset += 3 × 4  = 12
  ⑤ dst[0] = src[32 + 12 = 44 字节] → 第 2 章算过的 x[2][3] = 11.0 ✓

输出元素 i = 1（该用 i_idx[1]=0、j_idx[1]=1）：
  j=0: v = 0 → offset += 0 × 16 = 0
  j=1: v = 1 → offset += 1 × 4  = 4
  ⑤ dst[1] = src[4 字节] = x[0][1] = 1.0 ✓
```

44 字节——第 2 章埋的地址公式 `r×16 + c×4`，在这里被 kernel 一步一步
算了出来。

负数清单（比如 `i_idx = [-1, 0]`）走的是 ③：`-1 + 3 = 2`，取到最后一行。
Python 里 `x[-1]` 的好用，代价是每个元素都要过这条分支。

### 4.7 变奏曲：尾随维改变一切

真实负载里，清单往往不在最后一维——`x[idx]` 选整行、`x[:, idx, :]` 选
中间维，它们后面都**拖着没被索引的尾随维**。旅程的差别集中在 ⑤⑥ 两站。

以 `x[idx]`（还是我们的 x，`idx = torch.tensor([2, 0])`）为例：

- ④重步长站：x 的说明书换成形状 [2, 4]、步长 [0, 4]——dim0 步长归零，
  尾随维 dim1 保留原步长；
- ⑤遍历器站：输出 [2, 4] 连续，最内层是尾随维 dim1；
- ⑥内核站：沿最内层 dim1，清单的步长为 **0**——整行共享同一个下标值！
  内核因此命中一个重要特化（`is_constant_index`，深度版 §4.7）：每行只需
  读 1 次清单、做 1 次检查，然后连续拷贝整行。

```text
row=0: v = idx[0] = 2 → 检查 → 基址 = src + 2×16 → 连续拷 16 字节（第 2 行）
row=1: v = idx[1] = 0 → 检查 → 基址 = src + 0    → 连续拷第 0 行
```

对照 4.6 的逐元素版：管理开销从"每元素一次"摊薄成"每行一次"，取货从
"逐件"升级成"整箱"。这就是 §6 表中 E 优化（块拷贝特化）的用武之地。

反过来，`x[:, idx]`（清单占最后一维、没有尾随维）是最不划算的形状——
每个元素都得完整过一遍 ①~④。**清单在前、尾随维在后**的负载天然好伺候。

### 4.8 站在终点回头看

六站加起来，一次 `x[i_idx, j_idx]` 的完整成本清单：

| 站 | 成本性质 | 量级感 |
|---|---|---|
| ①–③ 绑定/语义/归一化 | 每次调用固定开销 | 微秒级；小 tensor 频繁调用时才显眼 |
| ④ restride | 说明书操作，近似免费 | — |
| ⑤ TensorIterator | 一次性的结构计算 | 微秒级 |
| ⑥ 内核循环 | **每元素**：8B 清单读 + 2 次比较 + 分支 + 1 乘 1 加 + 随机读 + 顺序写 | 大 tensor 时占绝对主导 |

六站里真正可优化的，集中在 ⑥ 的每元素成本和 ③ 的转换/装订——这正是
深度版优化篇（§6/§7）的两大主题。

## 5. 为什么它慢：性能直觉

**本章解决什么疑问**：一个"查表搬运"的操作，凭什么能霸榜 profile？

对每个输出元素，第 4 章的循环做的是：读 8 字节清单 + 2 次比较 + 分支 +
1 乘 1 加 + 一次随机读 + 一次顺序写。慢的根源全在这份清单里，分三类说。

### 5.1 管理开销：搬 4 字节货，付 12 字节过路费

①~④ 是"管理成本"不是"搬运成本"——**数据全在 L1 里，它们也一分不少**：

- 每元素 8 字节的清单读（int64 的代价；③归一化站那笔整体 int32→int64
  转换，在这里兑现）；
- 每元素的越界检查 + 负数分支——安全性的代价，Release 编译也关不掉；
- 偏移的乘加与间接寻址。

对 4 字节的 float32 来说，管理与搬运接近 1:1；dtype 越小（bool/uint8），
管理占比越是灾难性地高。

### 5.2 随机访存：地址依赖链让延迟无处可藏

⑤ 的取货地址依赖 ①④ 的结果——清单值读出来之前，CPU **不知道**该向哪个
地址发 load。后果：

- 无法提前预取（硬件预取器学不会"清单驱动"的访问模式）；
- 无法重叠加载（下一个地址同样在等下一张清单值）；
- x 远大于 LLC 时，每个元素几乎独享一次完整 DRAM 延迟。

这是 gather 型操作的天性，也是优化空间最大的一块。

### 5.3 零 SIMD

一个通用 kernel 不挑场景：清单可能有负数（③ 的分支）、dtype 可能 1 字节、
维数可能任意——分支密度让编译器的自动向量化基本歇菜；4.7 节那个无分支的
行拷贝环，步长又是运行期值，编译器同样无从下手。就算你手写一个
同样形状的 C++ 循环，也不会快多少；要快，得像深度版 §7 那样专门为
gather 写向量代码（SVE 甚至有专门的 gather 指令）。

### 5.4 一笔字节账

把三类开销放到一个具体规模上看。100 万元素的 float32 gather（清单 1M 项）：

```text
清单读（int64）    1M × 8B = 8 MB   （顺序读，通常缓存友好）
数据读（随机）     1M × 4B = 4 MB   （5.2 的延迟全在这）
结果写（顺序）     1M × 4B = 4 MB
────────────────────────────────
必要流量          ≈ 16 MB
```

在有效带宽 200 GB/s 的机器上，纯搬运下限约 80 μs。实测常是它的 3~10 倍
——差值就是 5.1 的管理开销与 5.2 的延迟暴露。**profile 里的时间减去这个
下限，就是优化空间的第一手估计**。

### 5.5 亲手看一眼

```python
import torch

x = torch.randn(1_000_000)
idx = torch.randint(0, 1_000_000, (1_000_000,))   # 乱序清单 = 最坏情况

with torch.profiler.profile() as prof:
    y = x[idx]

print(prof.key_averages().table(sort_by="self_cpu_time_total", row_limit=10))
```

表格第一行大概率就是 `aten::index`。把 `idx` 换成有序清单
（`idx = idx.sort()[0]`）再跑一遍——你会直观看到 5.2 说的延迟差。

### 5.6 什么时候它才会成为瓶颈：核对清单

不是所有 `x[idx]` 都值得关心。以下条件命中越多，越可能霸榜 profile：

- 清单大（几十万项以上）——循环本身才有分量；
- self 远大于 LLC——随机访存真的在吃 DRAM 延迟；
- 清单乱序——缓存命中与预取双双失效；
- dtype 小（bool/uint8）——管理开销占比被放大；
- 小 tensor 高频调用——①~③ 站的固定开销反客为主。

反过来，小而连续的 gather（比如从嵌入表里查几行）根本不值得优化——
**先量，再动手**。

> **深挖**：每元素成本的逐指令定价、六个定性结论 → 深度版
> [§5 性能画像](aten_index_aarch64_analysis.md#5-性能画像时间都花在哪)；
> aarch64 构建现状（为什么现成编译连 NEON 都没用上）→ 深度版 §5.4。

## 6. 优化导游图

**本章解决什么疑问**：知道慢在哪了，全景的优化思路长什么样？

先给一个三字框架（深度版 §6 的主线），所有优化都挂得进去：

- **少算**——压缩每元素的管理开销（循环里的 ①~④）；
- **少等**——藏住随机访存的延迟（⑤ 的读）；
- **少搬**——降低数据流量本身。

然后是地图。每行一句话直觉 + 适用场景 + 深度版详情：

| 优化 | 一句话直觉 | 何时用 | 详情 |
|---|---|---|---|
| A 线性化 | ①~④ 提前批量做完，主循环只剩 `dst[i] = src[off[i]]` | 一切场景的地基 | 深度版 §6.1 |
| C 软件预取 | 提前几条手工发起取数，把 DRAM 延迟藏进流水线 | 大 gather、清单乱 | 深度版 §6.2 |
| E 块拷贝特化 | 单维整行取货退化为一次 `memcpy` | `x[:, idx]` 型 | 深度版 §6.3 |
| D int32 清单 | 清单体积减半，还省掉每次的 int64 转换 | 清单量大 | 深度版 §6.4 |
| F NUMA 亲和 | 双路机器把数据和线程放同一插槽，带宽翻倍 | 双路服务器 | 深度版 §6.5 |
| H 排序分块 | 乱序清单先排好，局部性和预取都活了 | 负采样类场景 | 深度版 §6.6 |
| I torch.compile | 不改 PyTorch 源码的白嫖路径 | 立即可用 | 深度版 §6.7 |
| SIMD 家族 | SVE 一条 gather 指令一次取 8 个元素（深度版的目标机非流式 SVE 即 512-bit） | Arm 机器 | 深度版 §7 |

**动手的顺序**（场景再特殊，这四步是通用的）：

1. **先量**——用 5.5 节那三行 profiler 代码确认瓶颈真的是 index，看清
   self/清单的规模与顺序（有序还是乱序）；
2. **零成本替换**——int32 清单、`index_select`、bool mask 换整型下标，
   这类一行改动先收割；
3. **结构审计**——问三个问题：清单（拓扑）能不能缓存复用？中间量能不能
   不落地？gather 能不能与邻居算子融合？；
4. **kernel 级手段**（A/C/E、SIMD）——到这一步就该深度参与深度版 §6/§7
   的完整方案了。

两个真实案例的故事版（完整推演在深度版）：

- **稀疏卷积（spconv）**：profile 里 `index`+`bmm` 霸榜，根因是 gather 的
  中间量（几百 MB/层）写一遍、读一遍。一行改动（`index` → `index_select`）
  先止血；根治靠让中间量根本不落地（gather-GEMM 融合）。→ 深度版
  [§9](aten_index_aarch64_analysis.md#9-实战案例spconv-submconv3d-中的-index-优化)
- **AI4S 点云 GNN**：邻居图半静态是最大红利（拓扑可缓存复用）；按 payload
  分档下药——坐标档（12B/边）省管理开销，特征档（256B/边）省带宽。→ 深度版
  [§10](aten_index_aarch64_analysis.md#10-实战案例ai4s-点云模型中的-index-优化)

两个案例的共性值得单独说一句：慢的根源都不是循环写得差，而是**结构**——
中间量落地、重复劳动。通用 kernel 不挑场景，也就不会替你做结构决策。

真要动手选型时，直接查深度版 §8.1 的场景决策表和 §8.2 的优先级总表。

### 7.1 常见问题

**Q：`index` 和 `index_select` 什么关系？**
`index_select` 是"单维、整行取"的专用通道：避开了通用机器的一部分成本
（比如 int64 强制转换），行拷贝走 `memcpy`/向量化的 copy 路径，搬运本身
更快，但只覆盖 `x[idx]` 这一种形状。深度版 §6.3 拆了
它的快车道；§9 的案例把它用作"一行改动的止血手段"。

**Q：训练时反向传播怎么办？**
gather 可微，反向是 scatter-add（把梯度按清单加回 `x`）。本文只讲前向，
但六站里的机关（restride、TensorIterator）训练推理共用；autograd 的
记账发生在第 1 章那套分发机器里——这也是它存在的另一个理由。

**Q：GPU 上也是这六站吗？**
骨架相同（Python 入口、语义、归一化与设备无关），kernel 不同——CUDA 侧
有专门的 gather kernel 和完全不同的性能特征。本文的性能讨论只针对 CPU，
深度版进一步聚焦 aarch64 CPU。

**Q：为什么全文到处都在提 stride？**
因为它同时决定三件事：语义（说明书怎么读）、性能（访问是否连续）、以及
kernel 必须多通用（任意 stride 都得伺候）。若还有疑惑，第 2 章值得回头
再读一遍。

**Q：反向操作 scatter（`index_put_` / `index_add_`）呢？**
它是 gather 的镜像：同样过六站、同样逐元素检查，只是"取货"换成"放货"；
清单里有重复地址时，还得靠原子加或串行兜底。本文的模型直接套用；深度版
§9/§10 的案例里，它常作为 gather 的搭档成对出现。

### 7.2 推荐阅读路线

### 7.3 术语速查

（与深度版附录 B 一致）

| 术语 | 一句话 |
|---|---|
| ATen | PyTorch 的 C++ 算子库（A Tensor Library） |
| 算子（operator） | ATen 里的一个 C++ 函数（add、index……） |
| 绑定（binding） | Python ↔ C++ 的翻译层 |
| 分发器（dispatcher） | 按设备/dtype 挑算子实现的机制 |
| storage / strides | Tensor 的一维内存 / 说明书里的步长 |
| 视图（view） | 共享同一 storage 的另一张说明书 |
| contiguous（连续） | strides 的顺序与内存排布一致——最"规矩"的说明书 |
| 高级索引（advanced indexing） | 用 tensor/mask 作下标 → 拷贝 |
| gather / scatter | 按清单收集 / 按清单分发 |
| restride | 改说明书（形状+步长）得到新视图 |
| TensorIterator | 按元素操作的通用遍历框架 |
