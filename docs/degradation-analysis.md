# 性能退化分析：线程扩展、微架构与逐案定位

本文回答三个问题：

1. 在 1/2/4/8/16/32/36 线程下，哪些场景比 torch 2.10 的 `aten::index` 慢？
2. 慢在微架构的哪一层（指令、缓存、内存、线程调度）？
3. 哪些是结构性问题，哪些只是共享机器的噪声？

适用构建（本文历史矩阵）：T15（T13 基础上加：raw 放行 `A<=64 && B*K<=65536`、
f32/i32+i64 大源直连 SVE `pure_gather_sve_4b_i64idx`、小 K 并行阈值线程缩放
`max(16384, 512×nt)`；T11 的 `gather_direct`/2B-1B-complex 单遍/非连续

§2.3；**当前值见 §2.9**。复现脚本见文末。

## TL;DR（30 秒版，T15 时点）

- **T13 之后没有系统性退化**：31 个场景里大多数 ≥1.0x；最强的是 RowCopy
  （S1/P1 1t 约 3.0x，run 间 3.0-4.5x；A=4/16 块 1t 1.9-2.1x）。
- **【历史·已修】**：`x[:,i]` 0.18x→2.0x；1 线程 A>=4 改回 raw rowcopy；2B 单遍；
  非连续下标 stride；T12 小行/grain；T13 多索引 K=512 从 0.67-0.73x 提到 1.3-3.4x；
  2D A=16 K=8192/65536 的 32-38t 从 0.73/0.76x 到 1.26-1.30x（hpc 绝对时间
  73-79µs 砍半到 36-37µs）。
- **仍 <1x（T15 时点；当前逐格见 §2.9.1）**：非连续 1D mask（1-16t 0.86-0.98x）、
  complex 1t（0.95x，2t+ 持平）、int8/uint8 8/16t（0.82-0.99x）、S4 8/16t
  （0.91-0.98x）、`x[i,j]` 8/16t（0.92-0.97x）、1D K=65536 小源
  （0.81-0.88x → 大源直连 SVE 后小源回标量 0.98-1.25x，**仍未修**，R1 待做）。
- **根因不是“大 K 内核变慢”**：一是每线程工作量只有 0.75-100KB，fork-join/
  调度成本超过并行收益；二是 1B 元素的 64B 行放大；三是 complex 和
  f32+i64 缺 SVE 内核；四是非连续 mask 仍走 `nonzero`+linearize 两遍；
  五是 1D K=65536 小源未命中最优路由（2D K=8192 已由 T15 修复）。
- **4B 大 K 随机 gather 的上限**是 64B 行放大 + 每元素成本 + 地址翻译
  （SVE 与标量持平）；36t 行流量 ~95-103GB/s，只有本机实测读带宽（~168GB/s）
  的 56-61%——没打满（旧文档的 73.3GB/s“上限”是计时口径错误，§6.4）。
- **残余劣化的硬件级根因**（微架构/系统结构/并行编程三层拆解，含 4B
  gather 微码/发射下限 vs 标量乱序重叠的每元素成本推导）见 **§5.9**；
  胜出侧的对称分析见 `performance.md` §4.3。

### 本文表格怎么读

- 所有“倍率”都是 **aten 时间 / hpc 时间**：`1.26x` = 快 26%，`0.87x` = 慢 13%。
- `1t/2t/.../36t` 是**线程数**，不是 CPU 型号；本机 pin 在 node 5 的 38 核上。
- **不要只看最大倍率**：32/36t 时 aten 自己可能变慢，倍率会被放大；本文同时
  给出 hpc 的绝对 GB/s 和“强扩展效率”（加速比 ÷ 线程数）来拆开这两件事。
- 表中“S1/P1/P2/P3/S4”是 5 个模型形态的代号，具体形状见 §3.2 或
  `benchmarks/bench_threads.py`。
- **32/36t 的倍率不可直接当收益**：aten 在带宽饱和后自己变慢，会放大比值；
  判断内核好坏看 1-16t 和 hpc 绝对时间/强扩展效率。

**给使用者的建议**：模型里以“整行/整块取数”为主（spconv、图消息、embedding
查表）时收益最大；纯 1D 随机单元素 gather 只略快于 aten，4B 大 K 大值域不要
期待加速；小张量不要开满线程：每线程 <64KB 效率已明显下降，<8KB 基本无收益
（T15 后仍适用：1D K=65536 小源 32-38t 0.90-0.92x；2D 空档【历史·已修】，见 §5.8）。

> `benchmarks/RESULTS.md` §2.9.1；本表的价值在"根因"一列，与时点无关。

| 场景 | 现象（修正后） | 根因 | 结论 |
|---|---|---|---|

一句话：**T13 之后没有大范围的系统性退化**；剩下的是非连续 mask

（0.73-0.88x）。`x[:,i]` 已从 0.18x 修到 1.1-2.0x。

## 2. 测试平台

- CPU：鲲鹏 920F（Kunpeng 920F），aarch64，SVE2，VL=512-bit。
- 拓扑：608 个逻辑 CPU，1 thread/core（无 SMT），32 个 NUMA 节点。
- 本文固定节点 5：CPU 190-227（38 核），本地内存 64GB。
- 缓存（sysfs 实测）：L1d 32KB 8-way，L1i 32KB 4-way，L2 768KB 12-way，
  64B cache line；未暴露统一 LLC（按 NUMA/簇分布）。
- 页表：base page 4KB；THP 策略 `always`（2MB huge page），但大块 `aligned_alloc`
  不保证立即折叠，随机访问仍会看到明显 dTLB 压力（见 §6.4）。
- NUMA 距离（node 5 行）：本地 10，相邻 node（4/6/7）20，较远 30-40，
  最远 61-91。所有测试用 `numactl --membind=5` 或首触分配固定在本地。
- SVE：`/proc/sys/abi/sve_default_vector_length = 64` 字节（512-bit），与
  `svcntb()==64` 门控一致。
- 频率：lscpu 标称 1.2-2.0GHz（随负载/功耗浮动）；本文只用 ns 与比值，
  不用频率换算绝对时间。同模式探针的单次访问 cycles 为 40/124/407
  （8/64/256MB），可直接横向比较，不依赖频率。
- 软件：BiSheng clang 19.1.7，torch 2.10.0+cpu，OpenMP 由 BiSheng libomp 提供。

> 为什么固定一个 NUMA 节点：跨节点访存会把延迟和带宽都搅乱；38 核足够观察
> 1→36t 的扩展，又不会引入 608 线程的调度噪声。

## 3. 测量方法（以及一个曾经让所有线程数据失真的坑）

### 3.1 两个 OpenMP 运行时

PyTorch 用 **libgomp**，扩展用 BiSheng **libomp**，两者各自维护线程数 ICV：

- `torch.set_num_threads(t)` → 只改 libgomp 的 ICV（影响 ATen 自己的算子）。
- 扩展里调用的 `at::parallel_for` 是**头文件内联模板**，其 OpenMP 实现随扩展
  一起编译，因此由 libomp 执行 → 默认 team = 进程可见 CPU 数（本机 affinity
  到 38 核时就是 38）。注意扩展源码里没有手写 `#pragma omp`，坑正来自这个
  内联模板。

因此在 T11 之前，标着 "2t/4t/8t..." 的 HPC 行实际都用了 38 个 worker，而
aten 行确实只用 t 个 → **相对加速比被严重高估**。这也是旧 RESULTS §3.6.1/§3.9
"每个线程都 ≥1.06x" 的来源。

修正：

1. 基准脚本用 `ctypes` 找到 `/proc/self/maps` 里的 libomp，调用
   `omp_set_num_threads(t)`；
2. T11 起内核入口（`index_impl` / `index_out_impl`）调用
   `sync_omp_threads()`，把 libomp 的 team 同步为 `at::get_num_threads()`，
   使用户的 `torch.set_num_threads(t)` 对扩展生效；
3. `at::parallel_for` 在 `t==1` 时本身会串行短路，所以 1t 数据一直是对的。

### 3.2 主矩阵

`benchmarks/bench_threads.py`：

- 同一进程内交替执行 aten 与 hpc：`HPC_INDEX_NO_OVERRIDE=1` 时 `x[i]` 是真
  aten，hpc 用 `index_sve.index`（pybind）直调同一内核；小 K 的 pybind 开销由
  §3.3 的两进程真实 `x[idx]` 补测。
- 每格 25 次中位数，预热 5 次；固定 node 5；`HPC_THREADS=1,2,4,8,16,32,36`。
- 31 个场景覆盖：S1/P1/P2/P3 模型形态、S4、1D f32/f64（含 idx32/idx64）、
  2B/1B/complex、A=2/3/4/16 rowcopy、非连续 self/idx、mask 三种、`x[:,i]`、
  小值域 range2048。

### 3.3 小 K 真实路径（两进程）

K≤1024 时单次调用只有几微秒，同进程的 pybind 包装（Python 调用 + list 转换）
会污染比值。`bench_smallk_driver.py` 交替启动 aten/hpc 两个子进程，各自跑
真实 `x[idx]`，取中位数后再比。覆盖 K=0/1/64/512/1023/1024/4096/8192/65536。

### 3.4 perf

`perf stat/record`（`perf_event_paranoid=-1`）在 node 5 上跑同一 case；计数
包含 Python/torch 启动（约 10-12 CPU·s），因此只做同 case 的 hpc vs aten
相对比较，不看绝对 cycles。关注指令数、IPC、frontend stalls、LLC miss。
`perf stat -D` 的单内核延迟窗口在本机不稳定（部分事件 `<not counted>`），
未用于本文结论。

### 3.5 噪声与判读

共享箱上绝对时间会漂移（同格多轮可差 2-3x）。本文规则：

- 只信**同一轮交替**得到的比值，不跨轮比较绝对值；
- 单格 <1x 但相邻线程 >1.2x、且重复后消失 → 判为噪声；
- 所有结论至少用两种线程数或两次独立运行复核；
- `mask empty` 这类微秒级 case 的比值没有意义（计时器/调度主导）。

## 5. 逐案分析（【历史·T11/T15】数据 + 与时点无关的根因）

### 5.1 `x[:, i]`：从 0.18x 修到 1.1-2.0x

**形态**：`x[200000, 64]` f32，`i[64]`，输出 `[200000, 64]`。每一行从 256B
（4 条 cache line）里按 64 个随机下标取 64 个 float。

**为什么不是"随机 DRAM"**：源行连续、每行只有 4 条 line，取完 64 个元素后
这些 line 仍在 L1/L2。所以它是**指令/循环开销 + 顺序写 51MB**，不是 DRAM
延迟问题；SVE gather 在这里帮不上忙（数据本来就在缓存里）。

**修复前**：`gather_direct` 每个元素都调用 `at::Tensor::data_ptr/strides/
element_size/dtype`（引用计数 + 间接调用），1t 315ms（0.18x）。`perf` 显示
`gather_direct<float>` 的 lambda 占 29.7% 的样本。

**修复 1**：属性循环外提取 + 增量推进 `r/k` → 1t 144ms（0.40x）。

**修复 2（T11）**：`A==1 + 单索引 + 全长连续`（`K<1024`，走 `gather_direct`）时，
先把 K 个下标校验/归一化
一次到小缓冲，再跑无检查的紧凑循环 `dst[p] = src[row_off[r] + v[k]]`，等价
aten `index_select` 的内层。K=64，预处理可忽略。结果：

| 线程 | 1t | 2t | 4t | 8t | 16t | 32t | 36t |
|---|---|---|---|---|---|---|---|
| 相对 aten | 2.02x | 1.88x | 1.69x | 1.43x | 1.12x | 1.55x | 1.87x |
| hpc 绝对时间 | 28.1ms | 15.0ms | 8.5ms | 5.3ms | 3.6ms | 2.9ms | 3.2ms |

**并行扩展**：hpc 28.1→5.3ms（1→8t，5.3x，效率 67%）；aten 56.5→7.5ms
（1→8t，7.5x），16t 时 aten 4.1ms、hpc 3.6ms 已接近饱和，相对比值在 1.1-1.9x
之间波动。**结论**：已不再是退化项；继续优化只能争取高线程的 10-20%，优先级低。

### 5.2 2B/1B/complex：单遍标量后，差距只剩行放大/边界开销

**旧路径**：这些 dtype 没有 SVE gather 内核，统一走
`linearize`（物化偏移）+ `dispatch_scalar`（逐元素标量）。对纯 gather 来说，
linearize 是纯额外开销：小 K 时占比尤其大。

**修复**：`fast_1d`（单索引、B==1、A==1、连续）且无 SVE 内核时，所有线程数
直接走 `gather_single_1d` 单遍标量（读 idx → 检查 → 归一 → load/store）。

**结果**：

| dtype | 修复前（代表值） | T13 1-16t |
|---|---|---|
| float16 | 0.75-0.94x | 1.23-1.36x |
| bfloat16 | 0.52-0.97x | 1.24-1.37x |
| int8 | 0.57-0.68x | 0.82-1.03x |
| uint8 | 0.58-0.66x | 0.94-1.09x |
| complex64 | ~0.64x | 1t 0.95x；2-16t 1.00x |

**为什么 int8 仍略低于 1**：1B 元素随机读，每条 64B line 只用 1B（64x 放大）；
aten 也是标量 + 同样的行放大。两边都到硬件上限，差距只剩边界检查/归一化的
几条指令和循环形态。16t 时 hpc/aten 都在 0.7-0.9 GB/s 有用带宽量级，差别
主要来自 64B 行流量与线程调度；没有 1B SVE gather 能绕过行放大，继续优化
收益很低。

**complex 只在 1t 慢约 5%**：`gather_single_1d` 每个元素做 `normalize`/边界
检查；aten 的 `index` 内核在 1t 把这些摊得更薄。2t 起两者都受行放大和内存
延迟支配，比值为 1.00x。没有 complex SVE gather 的必要。

### 5.3 `x[i, j]`：4B 随机 gather，基本持平

`x` 2D，两个全长 int64 下标，输出 100k 个 f32。T13 路径是入口预校验 + 预计算
偏移，再逐行拷贝/标量首元素。T13 矩阵：1-4t 1.04-1.20x，8/16t 0.97/0.92x，
32/36t 1.70/1.98x（高线程倍率含 aten 退化）。focused 复测 8/16t 为
0.98/0.92x，说明 8/16t 下探可重复，但幅度只有 2-8%。输出仅 400KB，8t 时
每线程 50KB、16t 时 25KB；调度和索引解码的固定成本接近并行收益。
T13 已把 1t 从 0.67x 提到 1.20x，剩余是阈值问题，不是解码热点。

### 5.4 `x[perm]` f64 N=200k：小工作量强扩展

T13 矩阵：1t 1.28x、2t 1.41x、4t 1.18x、8t 0.98x、16t 0.91x、32t 0.85x、
36t 1.17x；focused 复测 8/16t 为 0.94/0.86x，32t 1.13x。8/16t 的轻微
下探可重复，32/36t 不稳定。

- 总数据 1.6MB 源 + 1.6MB 输出；16t 时每线程只有 12.5k 元素（100KB）。
- hpc 绝对时间从 1t 4.24ms 降到 16t 0.70ms（6.1x，效率 38%）；aten 从
  5.40ms 降到 0.60ms（9.0x，效率 56%）。差距在**扩展效率**，不在 1t 内核。
- 线程启动 + 任务切分 + 随机访问延迟的固定成本超过并行收益；aten 在 16t
  也接近饱和，但它的内核/循环形态在 12.5k 元素/线程时摊得更薄。
- 32t 矩阵 0.85x、focused 1.13x，说明该点受放置/频率影响，不应作为持续趋势。

**规律**：每线程工作量低于 ~64-128KB 时，强扩展效率明显下降；低于 ~16KB
基本没有收益，甚至比 1t 更慢（§6.3 实测）。S4 在 100KB/线程仍为 0.86-0.98x，
说明除了字节数，还要看绝对访问次数和固定开销。`adaptive_grain` 已按
`n/(t*8)` 切分，但对“每线程字节数”没有下限；后续可按每线程 64KB 限制
**有效线程数**，而不是继续提高 grain。

### 5.5 非连续 mask：T8 的已知边界

T8 `gather_mask` 要求 mask 与 self 都连续；非连续 mask 回退到
`nonzero`（生成 int64 下标）+ normalize/linearize + gather。用矩阵同形状
（1D self 2M，mask 由 4M 抽样 `[::2]`，nnz≈600k）做分解实测。T13 轮
矩阵为 1t 0.98x、2t 0.96x、4t 0.94x、8t 0.91x、16t 0.86x、32/36t ≈1.01x；
下表是 T11 的耗时分解，用来解释“慢在哪”：

| 形态 | 线程 | hpc | aten | 比值 | `nonzero` | normalize+linearize | gather（差） |
|---|---|---|---|---|---|---|---|
| 连续（T8 融合） | 1 | 13.83 ms | 16.47 ms | 1.19x | 融合，不单独物化 | — | — |
| 非连续 stride2 | 1 | 16.67 | 16.40 | 0.98x | 16.76 | 17.46 | ≈0（全被 nonzero 占满） |
| 连续（T8 融合） | 8 | 1.95 | 3.11 | 1.59x | 融合 | — | — |
| 非连续 stride2 | 8 | 2.97 | 2.57 | 0.86x | 1.88 | 2.74 | 0.24 |
| 连续（T8 融合） | 16 | 1.10 | 1.44 | 1.31x | 融合 | — | — |
| 非连续 stride2 | 16 | 2.03 | 1.48 | 0.73x | 0.94 | 1.59 | 0.44 |
| 连续（T8 融合） | 36 | 1.04 | 6.04 | 5.80x | 融合 | — | — |
| 非连续 stride2 | 36 | 3.08 | 5.21 | 1.69x | 3.40 | 3.12 | ≈0 |

读法：8t 时非连续路径 = `nonzero` 1.88 + linearize 0.86 + gather 0.24 ≈
2.97ms；连续 T8 融合只要 1.95ms。**多出来的 ~1ms 主要是 nonzero 物化 int64
下标（1.88ms）和随后的一遍 linearize（0.86ms）**，不是 gather 本身。
16t 同样多 ~0.9ms。1t 时两边都被 `nonzero`（16.7ms）支配，所以比值接近 1；
32/36t 恢复是因为 aten 自己退化更快，并不代表路径变好。

连续 mask 的 T8 路径是 1.20-3.76x。**优化方向**：让 T8 直接按 mask 的 stride
读（计数与压实两遍都按 stride），覆盖 `mask[::2]` 这类形态；按上表估算，
可省掉 nonzero + linearize 的 ~1ms，8t 从 0.86x 提到约 1.5x、16t 从 0.73x
提到约 1.3x。

### 5.6 其余 <1x 单元：噪声/微秒级

- **mask 4t 0.97x**：1t 1.21x、16t 2.29x，4t 是并行任务粒度/共享箱抖动。
- **range2048 16t 0.93x**：1t 1.22x、8t 1.06x、32t 1.29x；focused 受 aten
  退化影响反而 >1，单点不作为退化。
- **uint8/complex 1-16t 0.86-1.00x**：1B/complex 的天然行放大，属于“持平或
  略低”，见 §5.2。

### 5.7 非连续下标：一个被"性能"掩盖的正确性 bug

修复线程数时顺带发现：`bucket_gather_pure_raw` 与 `gather_single_1d` 原先
直接平坦读 `idx[k]` / 用 `src[v]`，忽略了索引 stride 和
`indexed_strides[0]`。后果：

- `i[::2]`（K≥1024，1t）会读到错误的 idx；
- 非连续 1D self（如 `x[::2][i]`）会读错源地址；
- 旧矩阵里 "noncontig idx 1t 1.37x" 正是这个**错误路径**跑出来的假加速。

修复：raw 路径加 `stride0`，并在 `fast_1d` 上要求 idx 连续；非连续输入回退
linearize 通用路径。修复后 1.01-1.57x（正确结果），并补了两进程回归用例。

**教训**：性能表格里的"异常快"必须先用非连续/边界用例验证正确性。

### 5.8 T13 后残余退化：多因素定位

T13 只影响多索引且 `n<=65536` 的入口；31 场景里多索引 100k 不进新路径，
大 K/RowCopy 也不受影响。T13 后仍 <1x 的持续项按机理分类如下
（A-F 来自矩阵定位，E2/G 为后续聚焦复测与 T14 realpath 对拍补充）：

| 类别 | 单元（1-16t） | 比值（T15 时点） | 绝对时间/线程 | 可修性 |
|---|---|---|---|---|
| A. 小工作量强扩展 | S4 8/16t | 0.98/0.91x（focused 0.94/0.86x） | 0.70-0.95ms；100KB/线程 | 阈值，可少开线程 |
| A. 小工作量强扩展 | multi 8/16t | 0.97/0.92x | 0.72-1.11ms；25-50KB/线程 | 阈值 |
| B. 1B 行放大 | int8 8/16t | 0.85/0.82x（focused 0.98/0.94x） | 2.7-5.6ms；≈0.7GB/s 有用 | 硬件上限 |
| B. 1B 行放大 | uint8 8/16t | 0.99/0.94x（focused 0.97/0.86x） | 3.4-6.4ms | 硬件上限 |
| C. 缺 SVE dtype | complex64 1t | 0.95x；2t+ 1.00x | 78ms/2M 元素 | 不值得 |
| C. 缺 SVE dtype | 1D K=65536 16-36t | **T15【历史·已修】**（大源直连 SVE；小源标量本就不劣于 aten，见 §5.8-C 注） | 42-61µs | 【历史·已修】（T15-C） |
| D. 非连续 mask | 1D mask 1-16t | 0.86-0.98x | nonzero 1.9ms + lin 0.9ms（8t） | 可扩 T8 stride |
| E. 路由空档 | 2D A=16 K=8192 32/36t | **T15【历史·已修】**：0.73/0.76x → 官方 1.26-1.30x（聚焦 A/B 2.12-2.49x；hpc 绝对时间 73-79µs 砍半到 36-37µs），raw 放行 `A<=64 && B*K<=65536` | 36-42µs（官方） | 【历史·已修】（T15-E） |

**A. 每线程工作量太小（S4 / multi）**：S4 的 hpc 绝对时间 4.24ms(1t)→
0.70ms(16t)，6.1x/16=38% 效率；aten 5.40ms→0.60ms，9.0x/16=56%。multi
的 hpc 4.54ms→0.72ms（6.3x，39%），aten 5.50ms→0.66ms（8.3x，52%）。
1t 内核是快的（1.20-1.28x），16t 被 fork-join、OMP barrier、任务切分和
随机访存延迟吃掉。32/36t 倍率回升主要是 aten 自身退化（S1/P1 同现象），
不是 hpc 又变快。修法是按“每线程有效字节”限制线程数，而不是继续加 grain。

**B. 1B 元素的 64B 行放大（int8/uint8）**：2M 个随机 1B 读，理论上要碰
2M 条 64B line；16t 2.7ms 对应有用字节仅 0.7GB/s，但行流量约 45-47GB/s
（约本机读带宽 168GB/s 的 27%）——限制在每元素成本（每元素一条 line + 标量
循环开销），不是节点带宽。aten 也是标量、同样放大，所以 1-8t 基本 1.0x；
16t 差 6-18% 来自循环形态/边界检查/调度。加 SVE 1B gather 也绕不过行
放大，不值得。

**C. 缺 SVE 的 dtype 组合**：complex64 没有 SVE gather，走
`gather_single_1d` 标量；1t 每元素多一次 `normalize`/边界检查，慢 5%；
2t+ 内存延迟占主导，回到 1.00x。1D K=65536 是 f32 数据 + int64 下标：
`gather_index` 的 4B SVE 分支要求 int32 下标，于是落标量单遍；16-36t 只剩
7-16KB/线程，fork-join 固定成本 ~10-20µs，比值 0.81-0.88x。**T15【历史·已修】**：
新增 `pure_gather_sve_4b_i64idx` 直连单遍内核（uzp1 收窄后复用 u32index），
但仅对**源>512KB（L2 实测 768KB，取其下保守界）**启用——A/B 发现小源
（16KB，L1 常驻）下 4B SVE gather 每线程每元素 ~18ns（微码/发射下限，两个
独立内核、两轮复现 17.9/18.3）反而高于标量 ~7.1ns（1t 官方与 16t 扣扫描
双口径一致），smallk 的 K=65536（源 16KB）保持标量（T15 轮实测
0.98-1.25x，不劣于修复前）；大源收益显著（K=10M idx64 源 8MB：8t
1.32→2.22x，hpc -40%；大源标量 ~19ns vs SVE ~10ns，机理与推导见 §5.9）。
小源格若要再快，剩余空间是跳过 `gather_bucket_pure_raw` 的前置值域扫描
（~15µs，未来工作）。

**D. 非连续 mask 回退**：T8 只看 `mask.is_contiguous()`；`mask[::2]` 回退
`at::nonzero`（物化 int64，串行段 + 并行扫描），再 normalize/linearize，
最后 gather。8t 分解约 nonzero 1.88ms + linearize 0.86ms + gather 0.24ms，
而连续 T8 融合只要 1.95ms；多出来的 ~1ms 就是两遍中间物化。按 stride 读
mask 可直接省掉，预计 8/16t 从 0.91/0.86x 提到 1.2-1.5x。这是五个残余项里
最值得做的一个。

**E. 小 K 路由空档（2D A=16 K=8192）**：总数据 832KB，32/36t 每线程
输出 14-16KB/线程。多线程路径因 `A=16` 不满足 raw 条件（`A<16` 或 `A>=4096`），走
linearize + rowcopy；1t 有 raw（1.74x），32/36t 反而 0.73/0.76x。**T15【历史·已修】**：
条件放宽为 `A<16 || A>=4096 || (A<=64 && B*K<=65536)`，官方 smallk 32-38t
**1.26-1.30x**（聚焦 A/B 2.12-2.49x；hpc 绝对时间 73-79µs 砍半到 36-37µs）。
注意不能放宽到全部 A——大 K 下 raw 的逐行检查/地址链在冷源
行拷贝下慢 12-32%（A=64 E=1M 8t +30%），故限 `B*K<=65536`（optimizations §19）。

**E2. 38t fork-join 边界（2D A=16 K=1024）**：`n*A=16384` 恰好触发并行，38t
下 fork-join 净亏 ~17µs（1.46x vs K=1023 串行 2.49x）。**T15【历史·已修】**：并行阈值
改为 `max(16384, 512×线程数)`，36/38t hpc 17.1µs 与 K=1023 完全拉平。

**F. 测量因素**：32/36t 的 1.7-9.9x 多数是 aten 退化；同一单元在矩阵与
focused 间可差 10-20%（S4 32t 0.85 vs 1.13、int8 8t 0.85 vs 0.98）。判据
应看 1-16t 的中位趋势 + hpc 绝对强扩展，不以 32/36t 单点定性。

**G. realpath 对拍交叉验证（2026-10-26，T14）**：真实 workload 基准
（RESULTS §2.5）在五类之外发现过一个新退化：shortq A=3（12B 短行）
K=512-1023 全线程 0.84-1.69x（i64 0.84-1.22x）—— `small_single_index` 对 A=2/3 走逐元素标量
循环，A=3 每行耗时 ~2x 于 memcpy（aten 对 A=2/3/4 一律 ~33µs）。T14 把
memcpy 阈值放宽到 A>=2 后修复（2.6x+，`optimizations.md` §18）。既有基准
看不见此问题：`bench_threads.py` 的 A=2/3 场景 K=200k 不走该路径，smallk
只有 A=1/A=16 —— 只有真实尺寸 shortq 才暴露，这正是补 realpath 基准的动机。
另两个判读结论：v1 轮 M1 (27,256,8) i64 38t 0.95x 经 7 轮聚焦复测为
1.23-1.28x（hpc spread 1.04），判为共享箱单轮噪声；aten 自身在 16/38t 对
K=1023×A≥3 有 539-615µs 的 fork-join 病理（我们串行路径免疫），realpath
表中 22-26x 的格子是 aten 退化，不作收益宣传。

### 5.9 T15 后残余劣化的硬件根因（微架构 / 系统结构 / 并行编程）

§5.8 回答"慢在哪、还剩多少"；本节回答"为什么在硬件上必然慢"。每元素成本
一律按 **墙钟 ÷ 每线程元素数** 折算（并行路径若除以总元素数会低估 8-38
倍，曾据此得出错误的 0.63ns/1.2ns 口径，见 5.9.5）。胜出侧的对称分析见
`performance.md` §4.3。

| 残余场景 | 现象 | 微架构 | 系统结构 | 并行编程 | 缓解 |
|---|---|---|---|---|---|

#### 5.9.1 4B SVE gather 的微码/发射下限 vs 标量乱序重叠（小源家族根因）

实测每线程每元素成本：

| 内核 | 源 16KB（L1） | 源 8MB（L3/DRAM） |
|---|---|---|
| 标量单遍 | **~7.1ns**（1t 官方 465.4µs/65536；16t (48.0−19)/4096，双口径一致） | **~18.8ns**（K=10M 8t 基线 23456µs/1.25M） |
| 4B SVE gather | **~18ns**（直连内核重载轮 17.9；既有 flat 内核安静轮 18.3，双内核复现） | **~10.0ns**（(14075.6−1600)µs/1.25M，1600µs≈80MB idx 扫描） |

（16t 口径中的 19µs 为该线程数下扫描+开销的估计值；1t 官方含串行扫描
约 20-40µs，扣除后 ~6.5ns，不改变结论。）

两条曲线的**形状**比数值更重要：

- **标量成本随源延迟增长（7.1 → 18.8ns）**。标量循环每元素一条 gather load：
  L1 命中（~4-5 拍）时，乱序执行把多条独立迭代的延迟完全藏住，瓶颈退化为
  发射带宽（每元素 ~7ns，含下标读取/检查/归一/存回的完整 µop 序列）；源退
  到 L3/DRAM（几十-上百拍）后，单核能维持的在飞负载数（乱序窗口 + LSU/
  MSHR 深度）不足以摊平延迟，成本逼近"延迟 ÷ 有效 MLP"。
- **SVE gather 成本对源延迟不敏感（~18 → ~10ns）**。一条 `svld1_gather` 蕴含
  8（f64）/16（f32）个独立 lane 负载，一条指令就是深 MLP——源远时占优
  （18.8/10.0 ≈ 1.9x，即用户可见的 8t −40%）。但 gather 在核内逐 lane 展开
  为地址生成 + TLB 查询 + 数据返回的微码序列，retire 依赖全部 lane 完成；
  源近（L1）时没有延迟可摊，微码/发射吞吐成为下限——两个独立内核、两轮
  （一安静一重载）都复现 ~18ns/元素，量级可信。此外小源下 `svprfw` 预取
  全部命中 L1，每向量 8 条无效预取纯占发射槽，是小源劣势的一部分（已被
  源大小门规避，不值得再优化）。
- **交叉点 ≈ L2**。标量 7.1→18.8ns 的增长曲线与 gather ~10-18ns 的平台在
  L2 附近相交；sysfs 实测 L2 = 768KB（§2），路由门取 512KB（L2 之下的
  保守界）正落在实测分界上：16KB 源标量快 ~2.5x，8MB 源 SVE 快 ~1.9x。

#### 5.9.2 fork-join 固定成本：小 K 高线程家族的共性根因

OpenMP 并行区进入 = 唤醒 worker（futex/自旋 + 私有 L1/L2 冷启动）+ 静态
分块 + barrier（跨核一致性广播）；成本近似与工作量无关、随线程数增长。
38 核单 NUMA 节点实测：

- 每遍 `at::parallel_for` ≈ **5-15µs**；
- K=1024 边界（T15 修复前）fork-join **净亏 10-17µs**（修复后 17.1µs 与
  串行拉平）；32t 设计内边界 hpc 22.5 vs 串行 17.7µs（净亏 4.8µs）；
- 1D 小源 K=65536 总时长 42-53µs，扫描 + gather 两遍的 fork-join 合计
  ~10-30µs，**占 30-50%**——0.90-0.92x 的主要来源：内核不慢，慢在
  "两遍并行"这个结构。

两条设计规则由此而来（T15 已兑现其一）：并行阈值按线程数缩放
（`max(16384, 512×nt)`）；每一遍 parallel_for 都要问"能否并进相邻遍"
（T15-C 直连内核、T8 单遍压实的共同动机）。aten 自身对 K=1023×A>=3 在
16/38t 有 539-615µs 的 fork-join 病理（§5.8-G），我们的串行路径免疫——
同一成本的另一面。

#### 5.9.3 cache line 放大与 dTLB：64B 传输粒度（1B / 4B 大 K 的硬上限）

L3/DRAM 的传输与一致性粒度都是 64B line：随机取 1B 只用 1/64，取 4B 只用
1/16。**这是系统结构层的硬上限，与指令选择无关**——SVE 1B gather 同样拉
整行，换指令无收益（SVE 与标量已实测持平）。实测：1B 行流量 45-47GB/s vs
有效 0.7GB/s；4B 36t 行流量 ~101GB/s，是本机读带宽（~168GB/s，§6.4）的 60%
——那条线由每元素成本（下标读+检查+地址+store，~19-23ns/元素）决定，不是节点带宽；随机大地址
空间再叠 dTLB miss ≈1.1 次/访问、本地 DRAM 97-138ns（§6.4）。只有
改变**访问结构**能绕：值域桶化（T4，值域局部化）、上层排序/分块——均属
未来项（§8）。

#### 5.9.4 地址生成链与 MLP：raw vs linearize 的大 K 分界（T15-E 教训）

A∈[17,64] 且 K>=100k 时 raw（单遍、逐行内联检查/负归一/imul）比
linearize+rowcopy（两遍）慢 12-32%（rc A=16 K=200k 8t 实测 **+2.8ns/行
≈ 9 拍**）；K<=65536 时 raw 反赢（省一遍 fork-join）。机理（**推断**，实测
现象为锚）：两条路径调用**同一个**行拷贝函数，差异只在调用前的地址链——
raw 是"读下标 → 比较/分支 → cmov 归一 → imul → 加基址"共 5-7 条 ALU µop。
宽发射核 1-2 拍就能发射完这些 µop，不足以直接解释 9 拍；更可能的机制是
**链长加大了下一行拷贝的发射距离**，在冷源（延迟受限）下压低了每核维持
的在飞负载数（run-ahead 深度）。linearize 第一遍是纯流式变换（顺序读
idx、顺序写 i32），带宽型而非延迟型，每元素成本极低；第二遍行循环只依赖
"读预计算偏移 → 加基址"的单依赖短链，乱序窗口能同时挂几十行。一句话：
**用一遍便宜的流式换一个访存更深的高延迟遍**——大 K 划算，小 K 不划算
（多付一遍 fork-join）。

#### 5.9.5 口径与箱态（方法学根因）

- **每元素成本必须除以每线程元素数**：历史上一度按"墙钟÷总元素数"得出
  0.63ns/1.2ns 的错误口径（把 8-16 线程的墙钟当成单线程串行时间），T15
  复盘已全量修正（§5.8-C、optimizations §19、kernels/RESULTS/status 同步）。
- **aten 绝对时间随箱态漂移**：共享 608 核/32 NUMA，其他租户争 DRAM 带宽
  与 LLC，DVFS 随负载浮动。可靠证据 = 同轮交替比值 + hpc 绝对时间；32/36t
  部分高比值是 aten 退化（§5.8-F、§6.2），不作收益宣传。

## 6. 并行扩展与线程选择（机制与轮次无关；具体数字为 T15 时点）

### 6.1 强扩展效率

以 hpc 自身 1t 为基准（GB/s，`bench_threads.py` 原始列）：

| 场景 | 1t | 8t | 16t | 32t | 36t | 8t 效率 | 36t 效率 |
|---|---|---|---|---|---|---|---|
| 1D f64 K=10M | 0.54 | 3.46 | 6.43 | 9.11 | 9.23 | 80% | 47% |
| 1D f32 K=10M | 0.24 | 1.89 | 3.69 | 6.84 | 7.11 | 98% | 82% |
| S1（模型行拷贝） | — | — | — | — | — | 高 | 高 |
| `x[:,i]`（时间） | 28.1ms | 5.3ms | 3.6ms | 2.9ms | 3.2ms | 67% | 24% |

（效率 = 加速比 / 线程数。）

读法：

- 1D f64 在 8t 为 80%、36t 47%：每线程 10M/8=1.25M 个 8B 随机读，行放大 8x，
  内存带宽开始成为主约束。
- 1D f32 在 8t 98%、36t 82%：4B 的行放大 16x，但源更大、请求更多，
  延迟掩盖更充分。
- `x[:,i]` 单线程已经很快（2.0x），但 8t 后效率降到 67%→24%；aten 同样
  饱和，所以相对比值反而在高线程回到 1.9x。

### 6.2 为什么 32/36t 有时反而更快

在 32/36t，aten 的 GB/s 经常**下降**（例如 1D f64 K=10M：16t 6.25 →
32t 4.54 → 36t 4.75，hpc 同期 6.43 → 9.11 → 9.23）。原因：

- 38 核节点上 32/36 线程时，两边的行流量已到节点读带宽的四到六成
  （§6.4 实测 ~168GB/s），**但并没有打满**；
- aten 的 GB/s 在这个区间反而下降，更像它自己的并行行为（任务切分/争抢），
  不是节点带宽到顶——具体机理没有单独定位，本文只记录现象；
- hpc 的 SVE gather + prefetch 在高线程下仍能维持更多在飞请求。

所以 32/36t 的"高加速比"部分是 aten 退化贡献的，不能简单理解为 hpc 的
绝对性能提升。文档中的绝对带宽列就是为了区分这一点。

### 6.3 小规模并行阈值（实测）

从 S4（8/16t 0.98/0.91x）、1D K=65536 小源（32-38t 0.90-0.92x，T15 轮）与
2D A=16 K=1024（T14 轮 38t 并行 1.46x vs 串行 2.49x，T15 阈值线程缩放【历史·已修】）
可以看到：**每线程工作量太小时，多线程接近甚至低于 1t**。为了量化，固定
node 5，用本算子直调（排除 aten 噪声），每格把
1t 与 t 线程交错测 7 轮（每轮 31 次中位数），报告轮间比值中位数的“相对 1t
加速比（效率）”。下表是 T13 复测：

| 形态 | 总输出 | 1t | 4t | 8t | 16t | 36t |
|---|---|---|---|---|---|---|
| 1D f32 K=8192 | 32KB | 1.00x（100%） | 1.29x（32%） | 1.37x（17%） | 1.23x（8%） | 1.04x（3%） |
| 1D f32 K=65536 | 256KB | 1.00x（100%） | 3.72x（93%） | 6.59x（82%） | 7.88x（49%） | **8.06x（22%）** |
| 2D A=16 K=8192 | 512KB | 1.00x（100%） | 3.61x（90%） | 5.19x（65%） | 5.67x（35%） | 4.86x（14%） |
| 2D A=16 K=65536 | 4MB | 1.00x（100%） | 1.99x（50%） | 3.64x（46%） | 8.14x（51%） | **14.05x（39%）** |

对应的每线程输出字节：K=8192 在 8t 只有 4KB、36t 只有 1KB；K=65536 在 8t
是 32KB、36t 是 7KB；2D K=8192 在 8t 是 64KB、36t 是 14KB；2D K=65536 在 36t
仍有 114KB。可以看到：

- **≥64KB/线程**：效率约 40-90%，值得并行；
- **16-32KB/线程**：仍有收益，但效率降到 15-50%；
- **≤8KB/线程**：效率 <15%，接近 1t；若再叠加 fork-join 固定开销，就会
  出现 0.73-0.88x（2D K=8192 32/36t、1D K=65536 16t；绝对时间仅 53-80µs）。
- 例外：1D 随机 gather 是延迟受限，K=65536 在 36t 只有 7KB/线程仍有 8.2x
  加速；所以“64KB”是保守的效率阈值，不是绝对收益门槛。
- 方法：每格把 1t 与 t 线程**交错**测 7 轮（每轮 31 次中位数），再取轮间
  比值的中位数，避免频率漂移把 1t 和 t 的基线拉偏；单次顺序测量会得到
  0.47-1.3x 这种不稳定结果，不能作为结论。

现有实现：小 K（≤4096）且 `n*A < 16384` 串行（T9）；T12 把 `adaptive_grain`
下限提到 64；T13 加多索引 n<=65536 入口。2D 小 K 的并行判断必须用 `n*A`，
只看 `n` 会让 A=16、K=4096 误判为串行。剩余的两个空档不是“没并行”，而是
**并行粒度太细**：1D K=65536 每线程输出 7-16KB、2D K=8192 每线程输出 14-16KB。
下一步应按“总字节数 / 每线程 ≥64KB”限制**有效线程数**，或扩展 raw 路由；
对 1D 延迟受限形态可放宽到 16KB。

### 6.4 内存系统实测（硬件上限）

用独立 C 探针（`gcc -O3`，`numactl --membind=5 --physcpubind=190[-227]`）测量，
避免 Python/torch 启动噪声。

> **数据轮次：2026-10-30 复核（n20，load 0.9、2 用户）｜当前。** 本文其它节是
> T15 时点的矩阵；硬件这节必须取"现在这台机器"的数。**复核纠正了一个计时口径
> 错误**：旧探针在 `#pragma omp parallel` **之前**取时间戳，单遍计时把**冷
> OpenMP 建队**算进窗口。实测建队成本 2t 0.3ms / 8t 1.8ms / 32t 5.8ms，而
> 256MB 在 8t 下真实扫描只要 ~1.6ms——于是"读带宽上限"被压成 73.3GB/s，还
> 造出"超过 8t 反而下降"的假象。现在 `memprobe.c` 在同一个 parallel 区内重复
> `REPS` 遍取最好一遍（`bandwidth SIZE_MB THREADS RD|CP [REPS]`），建队只发生
> 一次。本节末尾保留旧值作追溯。

**指针追逐延迟**（随机依赖链，单线程）：

| 工作集 | 4KB | 32KB | 256KB | 1MB | 8MB | 64MB | 256MB |
|---|---|---|---|---|---|---|---|
| 延迟（2026-10-30） | 5.1 ns | 5.4 ns | 10.4 ns | 47.7 ns | 97.4 ns | 131.7 ns | 138.3 ns |
| 旧值（T15 时点） | 5.0 | 5.3 | 10.4 | 47.0 | 114.9 | 157.2 | 192.3 |

判读：L1（~5ns）、L2（~10ns，L2=768KB/核）、"L2 未命中转本地 DRAM"的拐点
（1MB 47ns）完全复现；DRAM 侧从 115-192ns 降到 97-138ns——旧值含着当时的
共享箱争用。**138ns 是"下一个地址要靠上一个值"的依赖链成本，不是独立随机流
的吞吐**，两者差一个数量级，见下面的 gather 表。

**流式带宽**（2048MB，`REPS=3` 取最好一遍，node 5 本地）：

| 线程 | 1 | 2 | 4 | 8 | 16 | 32 | 38 |
|---|---|---|---|---|---|---|---|
| 读 GB/s | 19.4 | 37.8 | 71.4 | 127.4 | **169.2** | 168.5 | 168.0 |
| 拷贝 GB/s（读+写） | 28.9 | 56.5 | 104.4 | 132.3 | **145.0** | 141.7 | 116.3 |

判读：读带宽 16t 起进入平台 ~168GB/s（1t 19.4 的 8.7 倍），拷贝 ~145GB/s，
38t 略回落。**"8t 饱和、再加线程反而掉"是旧口径的假象**，真实曲线是
19/38/71/127/169/169/168。"每线程工作量太小则 fork-join 不划算"的结论不受
影响（那是任务粒度问题），但不能再拿"节点带宽只有 73GB/s"当解释。

**随机 4B gather 吞吐**（单线程，8 路独立流；种子用 splitmix 拉开）：

| 源大小 | 8 MB | 64 MB | 256 MB |
|---|---|---|---|
| ns/访问 | 10.3 | 11.0 | 12.0 |
| 行流量 GB/s | 6.2 | 5.8 | 5.3 |

判读：单线程随机读的**吞吐**是 10-12ns/访问（约 10 条 miss 在途），对应
5-6GB/s 行流量。旧表把"依赖链延迟"和"独立流吞吐"混为一谈（59ns/访问），
既低估 MLP，也把"DRAM 延迟决定 1t 下限"说过头了——真实内核 1t 是 ~19ns/访问
（下表），落在两者之间。另外旧探针的 8 路种子直接取 1..8，xorshift 序列
相关，8 条"独立流"会落到相邻行上，现改为 splitmix 派生。

**真实内核的绝对带宽**（2026-10-30 复核，脚本 `benchmarks/bench_hw_traffic.py`，
1D K=2M、idx int64、15 次中位、四个独立进程）：

| 形态 | 线程 | 时间 | 有用 GB/s | 行流量 GB/s（按 64B/元素） |
|---|---|---|---|---|
| 1D f32 K=2M（8MB 源） | 1 | 38.7-39.0 ms | 0.21 | 3.3 |
| 1D f32 K=2M | 36 | 1.24-1.36 ms | 5.9-6.5 | **94-103**（中位 100） |
| 1D f64 K=2M（16MB 源） | 1 | 41.1 ms | 0.39 | 3.1 |
| 1D f64 K=2M | 36 | 2.02-2.10 ms | 7.6-7.9 | 61-63 |

关键点：

- 本机（node 5，38 核 / 64GB）实测：读 **~168GB/s**、拷贝 ~145GB/s、
  依赖链 DRAM 延迟 ~138ns、单核随机行吞吐 5-6GB/s。
- 4B 路径 36t 的行流量 94-103GB/s（四次运行），是节点读带宽的 **56-61%，没有打满**；
  也没到"核数 × 单核上限"（38 × 6.2 ≈ 235）。**每元素成本几乎不随线程变**
  ——1t 19.3ns、36t 23-24ns——总吞吐只涨 28-31x（36 线程），所以 36t 仍然是
  "每元素成本 × 线程数"受限（§5.9.1 的发射下限），只在最后一段被存储系统
  轻微压住。
- 8B 路径 36t 61-63GB/s ≈ 4B 的 62%，每元素成本 37ns（4B 是 23ns），与"同样
  条数 line 装 2x 有用字节、但要多搬一倍字节"一致；不能用来证明"8B 的 MLP
  更高"。
- 所以"4B 大 K 修不动"的正确表述是：**16x 行放大 + 每元素成本**决定上限，
  换指令/回退标量都无效（同构建 A/B 已证）；但"已经撞到节点带宽墙"是错的，
  节点还有 40% 余量，减少行数（桶化/排序/行 gather）仍能换到收益。
- 36t 列在共享箱上有 ±20-40% 波动；**趋势**（读带宽 16t 进平台、4B 约为上限
  六成、RowCopy 随行数增长）比单个绝对值可靠。
- RowCopy 的"有用 GB/s"就是行流量（每行 64B 全用上），36t 到 54.1GB/s
  （T15 时点，本轮未重测该 case）。

**历史值（T15 时点，口径有误，仅作追溯）**：读 18.2/34.8/56.9/73.3/58.3/
39.2/44.4、拷贝 28.7/50.2/83.9/92.2/84.8/63.5/50.0（1/2/4/8/16/32/38t，
256MB 单遍）；DRAM 延迟 114.9/157.2/192.3ns（8/64/256MB）；随机 4B gather
15.1/26.0/59.0ns（8/64/256MB）；IPC 0.34-0.48、dTLB miss ≈1.1-1.2/访问。
偏低的原因见本节开头：冷建队成本进了计时窗口，且当时是共享箱重载期。

## 7. 微架构证据（perf，与时点无关）

方法：真实内核用 `perf stat`（`perf_event_paranoid=-1`），node 5。注意计数
包含 Python/torch 启动（本机启动约 10-12 CPU·s，且是多线程），因此**绝对
cycles/instructions 只用于同 case 的 hpc vs aten 相对比较**；事件比例
（IPC、frontend stalled、LLC miss rate）更可靠。需要干净绝对计数时，用 §6.4
的同模式 C 探针（无 Python 启动、内核循环占进程 90%+）。

代表性结果：

| case | IPC（hpc / aten） | frontend stalled（hpc / aten） | LLC load miss（hpc / aten） | 判读 |
|---|---|---|---|---|
| `x[:,i]` 1t | 0.42 / 0.41 | 47% / 47% | 69% / 70% | 两边都是低 IPC + 高写带宽；hpc 快在**每元素指令更少**（2.0x），不在 miss 更少 |
| S1 1t | 0.40 / 0.44 | 48% / 39% | 68% / 74% | hpc IPC 更低但快 4.4x：SVE rowcopy 每轮搬 256B，**bytes/cycle** 才是关键 |
| bf16 1t | 0.43 / 0.53 | 36% / 38% | 66% / 74% | hpc 的标量单遍指令更多（cycles +28%），但省掉 linearize 后仍 1.2-2.4x |
| 非连续 mask 8t | 0.47 / — | 36% / — | 67% / — | `nonzero` 物化 + linearize 两段 + 随机 gather，IPC 低、LLC miss 高 |
| S4 f64 16t | 0.44 / — | 36% / — | 72% / — | 小工作量 + 随机行，后端停顿为主 |
| `x[i,j]` 8t | 0.45 / — | 39% / — | 75% / — | 4B 随机 gather 的 64B 行放大 |

统一结论：所有 case 的 IPC 都 ≤0.5，说明瓶颈不在算术；`frontend stalled` 高是
分支/标量循环的表现，LLC miss 高是随机 gather 的表现。**性能差异主要来自
“每字节有用数据搬了多少条 cache line”和“每元素多少条指令”**，与 §2 的模型一致。

§6.4 的干净 C 探针进一步量化了这条链路（perf 计数为 T15 时点）：随机 4B
gather 的 IPC 0.34-0.48、后端停顿 58-78%、LLC miss 66-90%、dTLB miss ≈1 次/
访问；36t 时 4B 路径的
行流量 94-103GB/s，为本机读带宽（~168GB/s）的 56-61%。这三组数字分别对应
“算术不是瓶颈”“等内存/地址翻译”“每元素成本到顶”，比单看倍率更能解释为什么
4B 大 K 随机 gather 无法靠换指令或回退解决。

修复前 `x[:,i]` 的 `perf record` 里，`gather_direct<float>` lambda 占 29.7% 的
样本；修复后该符号退出热点（时间减半以上），这是"去掉逐元素 `at::Tensor`
调用"的直接证据。

## 8. 优化优先级

1. **1D 小源跳过 bucket 前置扫描**（K=8192/65536 小源 36-38t 0.90-0.95x，
   残余劣化主要是 ~15µs 值域扫描 + 两遍 fork-join）：把值域扫描改懒执行或
   并入 gather 单遍。当前最值得做，能把小源家族拉回 ≥1x。
2. **非连续 mask 的 T8 扩展**（1D 0.73-0.98x → 预期 1.2-1.5x）：计数与压实
   两遍都按 mask 的 stride 读，去掉 nonzero 中间量（8t 实测可省 ~1ms）。
   工作量中等，收益明确。
3. **f64+i32 下标**：`svunpklo` 把 i32 加宽到 i64 后可走 8B gather（当前
   落标量，相对 aten 基本持平，收益小）。
4. **`x[:,i]`**：【历史·已修】到 1.1-2.0x，剩余高线程 10-20% 收益，优先级低。
5. **1B/complex 不再投入**：行放大是硬限制，aten 同样是标量。

> 已完成：小规模并行阈值线程缩放（T15：`n*A < max(16384, 512×nt)` 串行，
> K=1024 高线程 1.84→2.83-4.57x）；2D A=16 K=8192/65536 高线程空档与
> f32+i64 大源 SVE 路由（T15，optimizations.md §19）。

```bash
source ~/.bashrc

  python benchmarks/bench_threads.py

  python benchmarks/bench_realpath_driver.py

HPC_AFFINITY=190-227 python benchmarks/degrade_probe.py

  -e cycles,instructions,LLC-load-misses,dTLB-load-misses \
  /tmp/memprobe gather 256 4000000 rand

perf stat -e cycles,instructions,cache-misses,LLC-load-misses,dTLB-load-misses \
  env MODE=hpc python benchmarks/perf_one.py col 1 5
```
