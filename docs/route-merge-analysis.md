# 路由合并与探测成本分析

> 面向：要在**结构相同、行号不同**的一版实现上判断"该不该把几条路合起来"、
> "路径是不是太多了"、"再加一条路会不会拖慢所有调用"的 agent。
>
> 结论先行：**路径条数不是固定开销的来源；会遍历数据的资格判定（探测）才是。**
> 所以"合并"的价值分两种——省时间的是**把重复的探测消掉**，其余只是省代码和
> 省维护风险，不要用性能理由去做。

本文不给死行号（各版行号必然不同），定位一律靠符号名，配方见 §7.1。

[`benchmarks/RESULTS.md`](../benchmarks/RESULTS.md) §2.13（由
`benchmarks/bench_route_probe.py` 一次产出），这里只写结论 + 指针。

> **这篇讲什么**：路由该不该合并、探测失败要付多少、怎么把“路径数”和“开销”
> 分开测。

## 1. 三层成本模型

把一次 `x[idx]` 的代价拆成三层，就能把"路径多不多"和第几层挂钩：

| 层 | 包含什么 | 量级出处 | 与路径条数的关系 |
|---|---|---|---|
| 入口必经 | dispatcher、`normalize_index`、输出分配、线程同步 | RESULTS §2.13.1 | 无关 |
| O(1) 判定 | 路由 if 链、dtype/线程/A/阈值比较 | 测不出来（§2.13.1 的差值里量不到） | **无关**（每调用只物化一条） |
| O(K) 探测 | 值域 min/max 扫描、下标物化、stride/run 分析 | RESULTS §2.13.3（每遍的裸价） | **正相关**（失败一次 = 白付一遍） |

由此得到两条可直接用的判断：

- 新增一条**只看 `IndexSpec` 字段**的路：几乎免费，代价只在代码维护面。
- 新增一条**要先扫一遍数据**才能判定的路：每次调用只要它判失败，就白付一遍
  O(K)。这类门要么别加，要么把探测产物留下来给下游用（§4.1、§4.2）。

## 2. 方法论：怎么把"路径数"和"开销"分开测

四个实验，每个都冲着"把两个变量拆开"去设计；§2.5 / §2.6 是复现用的骨架和
"怎么数 pass"，不属于实验本身。

### 2.1 先确认"到底走了哪条路"（否则测的是别的变量）

比较链深之前，必须用计数器确认两个用例分别走了哪条路。本仓实测过程栽过两次，
都不报错、只是测的量完全不同：

- `torch.randn(n)` 在 CPU 上默认 **f32**，想测 f64 必须显式 `dtype=torch.float64`
  ——否则你以为在测"f64 走哪条路"，实际测的是 f32。
- `torch.arange(0, 8, 2)` **是连续张量**（新分配），想要非连续视图得写
  `torch.arange(8)[::2]`——否则"非连续下标"的用例其实还在快路径上。

确认之后再看链深：入口快路径（`mask` / `small_single` / `small_multi`）会在进入
`index_into` 之前吃掉大部分小调用，所以"11 条路会不会拖慢短调用"这个问题，对
这些形态**根本不成立**——它们走不到链上。链深只在"被快路径排除"的形态上才有
意义，而那类形态的代价主要由一次 `normalize` 和通用内核的簿记决定（§3.1）。

设计链深实验时仍要固定这些变量：输出形状/dtype、Python 侧写法（`x[[i]]` 与
`x[i]` 的差异比链本身大一个量级，见 RESULTS §2.13.1）、线程数、以及**是否命中
快路径**。

### 2.2 门边界挪一格——隔离"探测失败"的成本

要让差值只反映探测，**必须让两侧的源访问局部性相同**：把值域恰好等于阈值
和"阈值+1"做成同一 cache 窗口内的随机访问（源都只有几 KB）。这样 gather 侧的
访问模式不变，差值 ≈ 失败的那次探测 + 多绕出来的 pass。

> **反面教材（本仓踩过）**：第一版粗测拿"值域窄 vs 值域宽"当探测成本，看起来
> 探测很贵。其实窄值域同时把源访问变成了 L1 命中，两个变量混在一起——
> **值域宽窄首先是局部性变化，不是探测成本**，必须换成"阈值两侧同局部性"才能比。
> RESULTS §2.13.2 就是按这个要求做的（门两侧同带、只挪阈值）。

### 2.3 单遍扫描的裸价——给差值找参照

`torch.aminmax(idx)` 近似一遍并行 min/max（少了逐元素边界检查和负值归一），
用来判断上面测到的差值是"一遍"还是"三遍"。同一 K 下换个下标宽度（i32 → i64）
再测一次，能看出探测成本首先是元素宽度的函数。

### 2.4 语料普查——回答"哪些路可以删"

对语料里每个形态调用一次，读计数器增量，统计分布。本仓 8 个计数器覆盖大部分
路由，但**还有 4 条路没有专属计数器**（`gather_direct`、桶化、两遍模型、
`gather_fused`），且 `rowcopy_raw` 把四种行拷贝入口并成一个。这类缺口要么补计数，
要么用 `debug_spec` + 负向断言钉住。没有普查就删路，等于凭手感。

**补计数之后值得顺手立一条不变量**：每次进 `index_into` 恰好落一条路由，所以
"路由计数器之和 == `dispatch_count` 增量"。它能把"路由悄悄换了一条"变成测试红，
比任何单点断言都省事（缺的那 4 个正是让这条不变量现在立不起来的原因）。

### 2.5 最小测量骨架

四个实验都可以用下面这段骨架复现（`C` 是 pybind 调试出口模块）。本仓把这套骨架
固化成了脚本 `benchmarks/bench_route_probe.py`（四组一次跑完、`--json` 出原始
数据），要照抄的话直接用那个，别再各自写一份。

```python
def bench(fn, reps, warm=100):
    for _ in range(warm):
        fn()
    best = float("inf")
    for _ in range(5):
        t0 = time.perf_counter()
        for _ in range(reps):
            fn()
        best = min(best, (time.perf_counter() - t0) / reps)
    return best * 1e6          # µs


def route_of(fn, keys):        # keys = 各路由的计数器名
    before = {k: getattr(C, k)() for k in keys}
    fn()
    return {k: getattr(C, k)() - v for k, v in before.items()
            if getattr(C, k)() - v}
```

要点：先 `torch.set_num_threads(t)` 并用 `numactl` 绑核；`warm` 必须够（线程池
自旋态与热态是两个不同的量级，见 RESULTS §2.11.1）；比值只在同一进程内背靠背测，
跨进程比绝对值没有意义。

### 2.6 怎么数"一次调用跑了几遍扫描"

判据不是 if 的条数，是**有几遍 `at::parallel_for` 真的从头摸到尾**。三种办法，
按代价排序：

1. 读代码列 pass：从入口到落地内核，数"读全量下标"或"写全量输出"的循环。
   本仓一个落选的 1D 形态是 4 遍（探测 → 物化 → 再探测 → gather）。
2. 临时计数器：在疑似重复的循环入口 `fetch_add` 一个全局计数，跑一次调用看增量。
   **临时加的计数器必须能在提交前删掉或并进正式计数器**，否则下一个人会把它当
   语义的一部分。
3. 采样剖析：`perf record` 看热点是否集中在同一段循环上（同一段出现多次宽峰
   ≈ 同一批数据被重复扫）。

## 3. 实测结论（数据出处：`benchmarks/RESULTS.md` §2.13）

本节只写结论；**所有 µs 数字、路由分布表、「两次复测区间」都在 RESULTS §2.13**，
那边由 `benchmarks/bench_route_probe.py` 一次性产出，可原样重跑。

### 3.1 短调用根本进不了链

K≤4096 且下标连续的形态（含 2D A=8）**全部被入口快路径 `small_single` 吃掉，
不会进入 `index_into` 的路由链**；只有被快路径排除的形态（例如把下标换成非连续
视图）才进链，代价是一次 `normalize` + 通用路由 + 内核簿记——如果链本身有成本，
也是一两个数量级更小的东西，在这条差值里看不出来。

推论有三条：讨论"路多会不会拖慢短调用"对这些形态**前提不成立**；用短调用论证
"链太长"是测不出结论的，只能论证"有没有快路径"；真正能走完长链的形态必然 K>4096
或 A 大，那时单次取数已是几十到几百 µs，几十 ns 的判定占比可忽略。

（数据：RESULTS §2.13.1 的四行 chain 表，路由列由计数器读出。）

### 3.2 探测失败要付一整条四遍的路

值域门（2048）**以内**与**以外**是两个平台：以内 512 与 2048 同带、以外 2049 与
4096 同带，两者之间是约 2 倍的台阶。台阶的内容不是"值域变大查表变慢"（源都只摸
前十几 KB，全在 L1），而是落选后换成"扫描作废 → `linearize` → 再扫描 → SVE"这条
四遍的路。裸价见 §2.13.3，但**别逐项相加核对**——两侧内核本身也不同（SVE gather
vs 标量查表），相加只能验证量级。

这条 2 倍不能整段算成"探测成本"（还含两种内核本身的差异），但"落选后要多跑一两遍
全扫"这个结构结论不受影响——它正是 M1/M2 要消掉的东西。

### 3.3 语料里只用到 4~5 条路

26 个生产/SGI 形态的分布见 RESULTS §2.13.4：绝大多数落入口小 K 快路径，其余是
行拷贝与大源单遍 SVE，还有 6 个形态落在**没有专属计数器**的路上（桶化 /
`gather_direct` / linearize 后 `rowcopy_sve`，分布表里逐个点名）。

所以"删一条路"的前提是它在 trace 里确实不出现、且退化后没有代价——两条都要数据，
不是凭条数。补那三条缺失的计数器需重编译，属待办。

## 4. 可合并项

按"能不能换到时间"排序。每条都在 RESULTS §2.13 的形态上量过，换形态/换机器会变。

### 4.1 M1：把已经算出来的值域判定往下传（真省一遍）

> **2026-11-03 更新**：`size ≤ 2048` 的 1D 纯 gather 已经**完全不走探测**——
> 免 pass 1、跨度 ≤64KB 时连表都不建（RESULTS §2.21-§2.21.3）。本节 M1/M2 的
> 讨论范围因此缩小到 `size > 2048` 的形态（值域可能远小于 `size`，扫描仍有价值）。

**现状**：1D 纯 gather 的值域探测（`bucket_gather_pure_raw`）在 `index_into`
里跑一次，落选后若落到两遍模型（`linearize` + `gather_index`），
`gather_index` 里的 `bucket_gather_pure` **又对物化后的偏移重扫一遍**，得到的
结论几乎必然是同一个（"值域太大，桶化不可用"）。注意只有落到两遍模型的形态才
有这第二遍；落到单遍标量 / 单遍 SVE 的形态（`gather_single_1d`、
`gather_single_1d_sve`）没有第二个探测，M1 对它们无收益。

**为什么可以合并**：探测本身要求单索引且 `B==1`，此时物化后的偏移 =
`row_off[0] + 下标值 × stride0`，即"原始下标值域"经一个仿射变换得到。于是：

- 原始下标域 **> 阈值** ⇒ 偏移域 ≥ 原始域 > 阈值（`stride0 ≥ 1` 时）⇒ 第二个
  探测**必然落选**，可以直接跳过。
- 原始下标域 **≤ 阈值** ⇒ 本来就在第一个探测里接管了，走不到这条路。

还有一条容易被忽略、但正是它让"M1 只跳过探测而不跳过检查"成立的：**第一个探测
的扫描已经覆盖全部下标并逐个做过边界检查**，所以省掉第二个探测不会漏检查。

**落地方式**：把探测结论做成三态往下传（`unknown` / `definitely_reject` /
`maybe_accept`），默认 `unknown`。**不要用 bool**——`gather_index` 还有别的调用方
（如 `rowcopy_direct` 分支、1 线程分支），它们没跑过探测，把它们误判成
`definitely_reject` 会静默跳过桶化，属于"性能悄悄退化、测试全绿"的那类 bug。
三态建议沿调用链显式传参，**不要塞进 `IndexSpec`**——`IndexSpec` 是
`normalize_index` 的产物，而探测发生在它之后，混进去会让"这个字段谁负责填"
永久说不清。

**先影子验证再改行为**：第一次提交只做"两个探测的结论都记下来"，在语料上比一遍，
确认真实差异恒为 0（即"第一个探测拒绝 ⇒ 第二个也拒绝"）。差异不为 0 说明有形态
违反了上面的仿射假设（广播维、多索引、`B>1`），此时**不该**动收益假设，而是把
这个形态排除在传递之外。这一步比事后看比值便宜得多。

**收益**：落选侧少跑一遍全扫（能用 RESULTS §2.13.2 的台阶与 §2.13.3 的裸价换算，
源越大占比越低）。
**风险**：`stride0 == 0`（`expand` 出来的广播维）时偏移域恒为 1，传递不成立——
需显式排除；同理 `B>1` 时偏移域是逐行 `row_off` 的并集，不能用单行结论推。
**验收**：同一形态在"值域 = 阈值+1"上比值改善，且"值域 = 阈值"**不退化**（后者
证明没有把本该命中的路也跳过）。

### 4.2 M2：探测失败别把结果扔掉（比"抽样早退"更稳）

**现状**：探测扫了一遍下标，算出 min/max 后判定"值域太大"，然后**把结果丢掉**，
下游从头再读一遍下标。同样的模式在本仓已有正确示范：`gather_direct` 在小 K 上
先"校验 + 归一化"物化一份 `vbuf`，再跑免检的紧凑循环——**探测的产物留下来给
干活用**。

**落地方式**：探测阶段顺手把归一化后的下标写进一个缓冲，失败时把它交给标量/
行拷贝路径复用（省掉它们自己的归一化，且探测不再是纯浪费）。

**替代方案（更激进，需额外论证）**：抽样提前拒绝——只看前 N 个元素，
`样本域 > 阈值` 就立刻放弃。因为样本是全集子集，**"样本超界 ⇒ 全集超界"是可靠的**，
所以判定不会错。但它有一个必须写进注释的前提：

> **边界检查不能一起被跳过。** 本仓的探测扫描是**唯一**覆盖全部下标的检查点；
> 表驱动内核（`bucket_gather_pure_raw` 的成功分支）与 `linearize` 之后的
> `rowcopy_sve` / `bucket_gather_pure` **都不检查下标**。因此抽样早退必须保证
> 落到一条仍然检查的路径上（标量单遍、4B SVE + i64 下标内核、`linearize`），
> 否则越界下标会变成 UB 而不是报错。

**收益**：抽样把"落选"从一遍降到 1/16 遍（K=64k、N=4096）；**风险**：早退后
的路径必须自带检查（上面那条）；**验收**：构造越界下标，确认仍然抛
`index out of bounds`（负向测试比性能测试更重要）。

### 4.3 M3：三处 `gather_rowcopy_raw` 调用点收成一个

**现状**：同一个内核在 `index_into` 里有三个调用点，各自带着一份近似但不相同的
资格判定（直写分支 / 大块跳过 linearize 分支 / 1 线程单索引分支）。

**收益**：**零性能收益**（判定都是 O(1)，每调用只走一条）。收益是"改一处忘一处"
的风险——本仓 [debugging-playbook.md](debugging-playbook.md) §5.5 复盘过的假通过，正是这类重复 guard
造成的。**落地方式**：`try_rowcopy_raw(spec, out)` 内部判定并返回是否接管，
调用方只写 `if (...) return;`。**风险**：三处判定条件的差异是**有意**的
（1 线程分支不要求 `A>=4`），合并时必须把差异写成参数或内部条件，**不能抹平**。

### 4.4 M4：两处 `linearize` + `gather_index` 收成一个 helper

同 M3：零性能收益，纯收拢。风险同样是"两处的 `use_i32` 条件必须逐字相同"——
一处写错就是 int32 溢出的静默错算。

### 4.5 M5：1D 家族三入口合一（有间接收益）

**现状**：`B==1 && A==1` 单索引有三分支——桶化探测 / 标量单遍 / 大源 4B 单遍 SVE，
三份几乎相同的 guard 顺序散在 `index_into` 里。

**落地方式**：合成一个 `gather_1d(spec, out)`，内部按 dtype / 线程数 / 源大小 /
值域选内核。**收益**：省代码 + 让"加第四种 1D 内核"只有一个地方要改；**不省调用
开销**（每调用还是只走一条）。**风险**：合并时很容易顺手改掉**判定顺序**，而顺序
就是本仓的热路径优先级——改完必须用 RESULTS §2.13.4 的普查对比计数分布，确认热形态没换路。

### 4.6 M6：`gather_fused` 的两处尾巴

`index_into` 末尾有两处 `gather_fused` 收尾，语义相同。合并成一条尾巴即可，
不影响判定顺序。**收益**：纯可读性。

## 5. 不该合并的两类

**mask 快路径**：语义不同——它跳过 `nonzero` 的物化，不是整数索引的子集。合并
只能靠"内部再分支"，既要多一条分支，又让 `nonzero` 这个 O(self.numel) 的成本
失去独立的文档位置（它是唯一能到毫秒级的路径，见 RESULTS §2.11.3）。

**`small_single` / `small_multi`**：它们的**全部价值**就是跳过 `normalize_index`
与通用路由。RESULTS §2.13.1 量过这两条路的差价：合并等于把它们降级成普通路，
是负收益。

判断标准只有一句：**合并之后，还有没有调用方能因此少做一件事？**
能少做（少一遍扫描 / 少一次 normalize）就值得拆出来；只是少写几行，就别动热路径。

## 6. 加新路之前的检查表

1. 这条路的资格判定需要**摸数据**吗？需要 → 它每次失败都白付 O(K)，请先证明
   这个形态在语料里真出现，且失败率低。
2. 能不能复用上游**已经算出来的**结论（值域、stride、run）？能 → 走 M1/M2，
   不要新加一遍扫描。
3. 它是否要求"跳过 `normalize`"或"跳过边界检查"？前者说明必须放在最前面
   （入口探针层），后者说明必须有一条下游路径仍然检查（见 §4.2 的前提）。
4. 贴进来的位置会不会改变**已有热形态的判定顺序**？会 → 先跑一遍 RESULTS §2.13.4
   的普查拿到基线分布，改完再对一次。
5. 有没有计数器能证明它被走到/没被走到？没有 → 先加，否则这条路的测试只能
   靠"结果对不对"，测不出"路由选错了"。

## 7. 跨版本落地

### 7.1 按符号名定位（不要抄行号）

各版实现结构相同、行号不同，用下面的符号名在你那一版里 grep：

| 用途 | 符号 |
|---|---|
| 入口 / 出口 | `index_impl`、`index_out_impl` |
| 大路由 | `index_into` |
| 入口快路径 | `mask_fast_path`、`small_single_index`、`small_multi_index` |
| 值域探测 | `bucket_gather_pure_raw`、`gather_bucket_pure_raw`、`bucket_gather_pure` |
| 物化 | `linearize`、`linearize_i64` |
| 二级分发 | `gather_index` |
| 行拷贝内核 | `gather_rowcopy_raw`、`gather_rowcopy_fused`、`gather_strided_rows_raw` |
| 单遍内核 | `gather_single_1d`、`gather_single_1d_sve`、`gather_fused`、`gather_direct` |
| 内部向量内核 | `rowcopy_sve`、`pure_gather_sve_flat`、`pure_gather_sve_4b_i64idx` |
| 调试出口 | `debug_spec`、`dispatch_count` 及各族计数器 |

```bash
# 在你的版本里把上面这批符号一次性定位出来
grep -n "index_into\|bucket_gather_pure\|gather_rowcopy_raw\|gather_single_1d" index_sve/*.cpp
```

### 7.2 阈值是标定值，不是常数

`2048`（桶化值域上限）、`512KB`（大源 1D SVE 门）、`4096`（small_single 的 K 上限）、
`65536`（rowcopy 放行行数）、`16`（多索引 raw 的线程门）都是在 920F/node5 上标定
的。换机器（L2 容量、fork-join 成本、单核带宽不同）必须重跑聚焦 A/B 再定，
**不要因为"看起来是个整数"就沿用**。

### 7.3 改完的验证顺序

1. 值级对拍（对真 aten）：先确认没算错。
2. 负向测试：越界下标仍抛错、非连续/广播形态仍走原路（生产能力最容易在这里退化）。
3. 计数器分布：改前改后各跑一遍 RESULTS §2.13.4 的普查，**形态换路必须能被解释**。
4. 门两侧各钉一个点：阈值两侧同一形态都跑（RESULTS §2.13.2 的做法），只看单侧
   会漏掉"收益变成退化"。
5. 最后才看比值表。

## 8. 优先级建议

| 顺序 | 项 | 预期 | 工作量 |
|---|---|---|---|
| 1 | M1 值域判定下传 | 落选形态少一遍全扫（RESULTS §2.13.2/§2.13.3 可换算） | 小 |
| 2 | M2 探测产物留存 | 同量级，且消掉"探测纯浪费"的结构问题 | 中 |
| 3 | M5 1D 家族合一 | 无直接收益，降低后续加内核的出错面 | 中 |
| 4 | M3 / M4 / M6 收拢 | 纯维护收益 | 小 |

前两项与 [status.md](status.md) §7 的 R1（"1D 小源跳过前置值域扫描"）是同一个问题的三种解法：
**先扫描再决定 / 抽样早退 / 扫描与干活合一**。R1 选第三种的做法是对的——它把
探测消掉而不是加快探测——本文的 M1 是它更保守的版本：不删探测，只禁止重复扫描。
