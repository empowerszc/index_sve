### 1.1 内存与缓存：数据放在哪、搬多快

| 术语 | 白话解释 | 例子 |
|---|---|---|
| **cache line（缓存行）** | CPU 和内存之间搬数据的最小单位，本机 64B。哪怕只读 1 个字节，也整条 64B 一起搬——像超市牛奶只按整箱卖，你要一瓶也得扛一箱 | 随机读一个 4B 的 f32，实际搬 64B，有用的只占 1/16 |
| **行放大（line amplification）** | 实际搬运字节数 ÷ 有用字节数 | 4B 元素 16x、8B 元素 8x、1B 元素 64x；随机 gather 的硬上限 |
| **L1d / L2 / LLC** | 一级数据缓存 / 二级缓存 / 末级缓存：几块"最近用过的数据"的小快存储藏室，离核越近越小越快。本机 L1d 32KB、L2 768KB（都每核私有），**没有 LLC** | L1 命中 2.0ns、L2 命中 8.6ns、本地 DRAM 137ns——差 20-70 倍，全部分析都从这张阶梯出发 |
| **命中 / 缺失（hit / miss）** | 要的 line 正好在这一级（命中，快）；不在（缺失），得往下级要 | L2 命中率 99% 的 512KB 工作集，几乎每次访问只花 8.6ns |
| **有效容量** | "装到多少还能跑满速"的容量，比物理容量小（见下条组相联） | L2 物理 768KB；装到 512KB 时 miss 才 0.1%，装到 768KB 已 14.3%——建模口径取 512KB |
| **组相联（set-associative）/ 组（set）/ 路（way）/ tag** | 缓存不是随便放的：每个地址只能进"编号固定"的那个组，组里有若干路位置。可以想成 1024 排货架、每排 12 格——总格子够，不等于每排都够 | 12 路的 L2，随机足迹下总有组先满、先往外扔——这就是 768KB 装不满还有 14% miss 的原因 |
| **LRU** | 组满了扔"最久没用过的"那条（的近似） | 同上：替换策略决定谁被扔 |
| **延迟 vs 带宽** | 延迟 = 一次往返多久（ns）；带宽 = 稳态每秒搬多少（GB/s）。两者不能互相换算，只通过"在飞条数"联系 | 单核顺序 19.4GB/s 但一次随机往返要 137ns；"延迟高"不等于"带宽低" |
| **在飞负载 / MLP / MSHR** | 已发出、还没回来的访存请求数（memory-level parallelism）。MSHR 是核里记这些"未完成订单"的硬件表，表多大就能同时在飞几条 | 本机每核能挂 16-20 条：137ns ÷ 16 ≈ 8.6ns/条，这就是随机访问能摊到的下限 |
| **依赖链 vs 独立访问** | 下一个地址要靠上一个读回的数据算出来（链表、`dst[k]=table[idx[k]]`）= 一次只能等一个，付满延迟；地址能提前算好 = 可多条并发 | 同样 137ns 的内存：依赖链 136.6ns/次，16 条独立链并行就摊到 8.9ns——预取/批量化都是在把前者改成后者 |
| **RFO（read-for-ownership）** | 只写 line 的一部分时，得先把整条读进来再改——"写比读贵"的来源 | A=3 的行只占一条 line 的 12B/64B，写它要付一次额外读；A=16 恰好整条覆盖写，免 RFO |
| **write-back / 脏行（dirty）** | 写命中只改缓存、标成"脏"，等被替换时才写回内存 | 连续写同一行只付一次内存流量 |
| **DRAM bank / row buffer / ACT / PRE** | 内存不是平坦数组：按存储体（bank）分行（row）组织。同一行再读几乎免费（row buffer 命中），换行要先关旧行再开新行（ACT+PRE，几十 ns）——像书架（bank）上的一排书（row），换排就要先把手上这排放回去 | 顺序扫几乎全命中 → 单核 19.4GB/s；随机跳几乎全 miss → 7.2GB/s |
| **硬件预取器** | 硬件自己发现"你在按地址递增读"，提前把后面的 line 拉进缓存。只对规律访问有效 | 顺序 memcpy 免费吃到；随机 gather 没规律可循，所以要手工发预取（prefetch） |
| **TLB / page walk / dTLB miss** | 程序用虚拟地址、内存用物理地址，翻译靠查页表；TLB 就是页表的缓存。TLB 缺失要沿多级页表走一遍（page walk），最坏 4 次内存访问 | 大范围随机访问会打爆 TLB；但本机实测 page walk 与数据 miss 并行、藏在 137ns 后面（开/关大页无差） |
| **大页（THP）** | 默认页 4KB；大页 2MB，一个 TLB 项覆盖 512 倍范围 | 听着该有用；本机实测收益 0（被上面的并行掩盖）——负结果也记录在案 |
| **NUMA** | 内存分节点，每个节点有自己的内存条；访问别的节点要过片内/片间互联，越远越贵 | 全部基准固定 `--physcpubind=190-227 --membind=5`（线程和内存都在 node 5）；不绑延迟差 1.4-2.7 倍（130→181→255→354ns），带宽最狠只剩 1/8 |
| **first-touch（首次触碰）** | 新分配的页在第一次被写时才真正拿到物理页，谁第一次写谁付缺页钱 | 8MB 输出 = 2048 次缺页，是"固定账"的主要来源之一 |

### 1.2 CPU 内部：一秒能做多少事

| 术语 | 白话解释 | 例子 |
|---|---|---|
| **拍（周期）/ 频率** | 拍 = 时钟的一格；频率 = 每秒多少拍。2.0GHz 即 1 拍 0.5ns | L1 命中 2.0ns = 4 拍；DRAM 137ns = 274 拍；"拍 ↔ ns"按 2.0GHz 换算 |
| **IPC** | 每拍真正完成（退休）的指令数，硬件上限 4（每拍最多取 4 条）。IPC 低通常是在等数据，不是核不会算 | aten 的行循环 IPC 0.71（在等内存）；预取后 2.14 |
| **超标量 / 乱序 / ROB** | 现代核每拍取多条指令、并打乱顺序执行（只要数据依赖允许）；ROB（重排序缓冲）是"能同时在途的指令"的窗口，几百条 | 短循环体（A=1）能让乱序窗口同时塞下 4-5 次迭代 → 4 条随机 load 真的重叠了 |
| **发射 / 端口** | 发射 = 指令进入执行单元；端口 = 执行单元的窗口数，load/store 每拍只有 1-2 个窗口 | L1 常驻的查表循环 0.66-0.71ns/元素 ≈ 1.3-1.4 拍，贴着"每拍 1-2 条 load"的端口上限 |
| **SVE / SVE2 / VL** | ARM 可伸缩向量扩展 / 向量长度。一条向量指令对一整排数据做同一个动作 | 本机 VL=512-bit：一条 `ld1d` 搬 64B = 16×f32 或 8×f64，正好一条 cache line |
| **lane（向量通道）** | 向量寄存器里的一个格子；一条向量指令 = 所有 lane 同时做同一个动作 | 512-bit 向量 = 16 个 32 位 lane；SVE gather 一条指令同时发 16 个独立 load |
| **微码 / µop** | 一条复杂指令（如 SVE gather）在核内展开成的微操作序列 | 4B SVE gather 逐 lane 展开成"地址生成 + TLB 查询 + 取数"，源在 L1 时没有延迟可摊，微码吞吐成为下限（~18ns/元素 vs 标量 7.1ns） |
| **retire（退休）** | 指令真正完成、离开流水线。乱序执行可以先做后面的，但退休要按序 | SVE gather 要全部 16 个 lane 都回来才能退休——一个 lane 慢，整条指令等着 |
| **FMA** | fused multiply-add：一条指令同时做一次乘和一次加，按 2 次浮点算 | 算峰值浮点用它：2 条 FP 流水 × 8 lane × 2 flop × 2GHz ≈ 64 GFLOPS/核 |
| **SMT / 超线程** | 一个物理核跑多个逻辑线程 | 本机 1 thread/core，无 SMT；38t = 38 个真核 |
| **DVFS** | 动态电压频率调节：主频随负载/功耗浮动，不是恒定值 | `CPU max MHz 2000` 但实测会在 1.55-2.0GHz 间浮动；sysfs 读数不可信，只信 PMU 实测 |

### 1.3 多核与 OpenMP：怎么分工、分活的代价

| 术语 | 白话解释 | 例子 |
|---|---|---|
| **fork-join** | `parallel_for` 的起停成本：把活分给 worker 线程、最后汇合。每次进并行区都要付一遍，**与工作量基本无关** | 每遍 5-15µs；小 K 高线程时"两遍 fork-join"占 30-50%——内核不慢，慢在"分活"上 |
| **barrier（栅栏）** | 并行区末尾的"全员到齐才放行"；到齐这件事要在核间广播确认，所以随线程数变贵 | fork-join 成本的大头之一 |
| **grain / chunk** | 每个并行任务分到的元素数。太小 → 调度开销吃光收益；太大 → 负载不均 | `adaptive_grain` 取 `n/(t*8)`、下限 64；每线程低于 ~16KB 时并行基本不赚 |
| **ICV** | OpenMP 的"线程数"内部配置副本——改它才知道该用几个 worker | libomp 和 libgomp **各有一份、互不相通**：`torch.set_num_threads(12)` 只改 libgomp，扩展的内核还在用 libomp 的默认值——本项目最大的方法学坑 |
| **OpenMP team / libomp / libgomp** | 一组被拉起来干活的线程 / 两个 OpenMP 运行时实现（PyTorch 用 libgomp，本扩展用 BiSheng libomp），同一进程里可能共存 | 入口处 `sync_omp_threads()` 把两边的线程数对齐 |
| **虚假共享（false sharing）** | 不同线程写同一条 cache line 的不同字节：核间一致性让这条 line 来回失效，性能骤降 | 本仓内核各写各的输出段，天然避开；写并行代码要永远检查这一点 |
| **加速比 / 强扩展效率** | 加速比 = 1t 时间 ÷ Nt 时间；效率 = 加速比 ÷ 线程数（固定规模加线程） | 效率 <100% 说明并行有开销或带宽饱和；判断"加线程还值不值"的直接指标 |
| **每元素成本（每线程口径）** | 墙钟 ÷ **每线程**元素数。并行路径除以总元素数会把每元素成本低估 8-38 倍 | 跨线程数比较只能用这个口径 |

### 1.4 本算子的访问形态与口径

| 术语 | 白话解释 | 例子 |
|---|---|---|
| **gather** | 按一串下标把元素取出来（`dst[k]=src[idx[k]]`），地址随机 | `x[idx]`、`features[inp_idx]` 底层都是它 |
| **RowCopy / rowcopy** | 一次取一整段连续元素（A>=4），整块搬，接近 memcpy——一条 64B line 里有用字节多，随机性被"整行"摊薄，最快的形态 | `w[ki]` 取权重块：1t 可到 12.7-13.6x |
| **PureGather** | 一次只取一个元素（A==1），每个元素都可能拉一条 64B line，受行放大限制 | 4B 大 K 随机 gather：有用带宽只有 1/16 |
| **A / B / K** | A = 每次访问的连续元素数（行宽）；B = 索引广播出的前导行数；K = 下标元素数 | A 大走 RowCopy、A==1 走 PureGather、K 小走快路径——路由只看这三个量 |
| **源（source）/ 源驻留级** | 被索引的张量 / 它常驻的缓存层级（L1/L2/DRAM） | 源 >512KB 走 SVE 单遍内核；16KB 小源标量反而更快（L1 命中 7.1ns/元素） |
| **linearize（两遍模型）** | 第一遍把多维/广播下标换算成一维偏移并物化成数组（含检查），第二遍按它取数 | 大 K 值得（摊得薄）；小 K 是纯固定开销——T 系列优化多是"跳过/合并这一遍" |
| **fused（融合单遍）** | 不物化偏移，边解码边 gather | 省一遍内存，但解码在热循环里 |
| **bucket（桶化）** | 值域很小（≤2048）时把用到的源元素收进一张 L1 常驻小表，查表代替随机大数组访问 | 生产三格（SGI/PPT/Sonata）都是它；跨度 ≤64KB 且 `K/size ≤ 32` 时连表都不建、直接查源（`stride0==1` 走免乘法特化；内核 A/B：SGI/PPT +1.27-1.30x、Sonata 门后回持平——headroom §6.5.8） |
| **下界（可达下界）** | 同机同工作集下，探针能跑出的最好合法写法——不是厂商峰值 | 两种下界差 8-9 倍：L1 常驻 0.66-0.71 vs DRAM 5.62-5.98 ns/元素；套错下界会把空间估错一个数量级 |
| **固定账** | 每调用一次都要付的成本（入口 + fork-join + 输出 first-touch），与 K 无关 | 入口 5.8µs + 一次 fork-join ~3µs；K 小时它把 ns/行 抬 2-3 倍 |
| **BDP（带宽延迟积）** | 带宽 × 延迟 = 要打满带宽必须有这么多数据在飞（像水管：流量 × 长度 = 管里存的水） | 7.2GB/s × 137ns ≈ 986B ≈ 15 条 line，与实测 16-20 在飞互相印证 |
| **算术强度 / 机器平衡点** | 做的浮点数 ÷ 搬的字节数（flop/byte）；平衡点 = 越过它才撞算力墙的强度 | 本算子 0；本机平衡点 ≈0.07——所以谈 GFLOPS 没有意义，只看 GB/s 和在飞条数 |
| **prefetch（预取）/ D** | 提前把 cache line 拉进缓存、不等它（`prfm`）。D = 预取距离，提前 D 行 | A=16：52.6 → 11.4ns/行（4.6x）；D 太大会挤爆 MSHR（A=64 的 D=16 反而崩） |
| **NT store（非临时存储）** | 绕过缓存直接写内存的指令，适合只写一次的大输出 | 听着该有用；本机实测收益 0（写侧 RFO 不是瓶颈）——负结果 |
| **warmup / median / interleaved** | 预热 / 取中位数 / 两臂交替测量 | 共享机器上对抗漂移的标准做法：要相除的两个数必须同一轮取 |
| **对拍** | 覆盖态与非覆盖态两进程，比对 true-aten 参考值 | 正确性验收口径，44/44（`tests/verify_against_aten.py`） |
| **smallk / realpath** | 小 K 两进程基准 / 真实 workload 两进程基准 | 短调用结论的首选依据（RESULTS §2.3 / §2.9.4） |
| **T0-T15 / R1-R9** | 优化轮次代号 / 路线图优先级代号 | "T15 起"指该轮之后；见 `optimizations.md` 与 `status.md` §7 |

行 ≤16KB）、M2（代表形态）、M5（标量循环）、**A1**（单元素高频，N=200k、
K=1）、**shortq**（短行查询，A=2-4、K=64-1023，x (20000, A)）。

**矩阵场景行名读法（RESULTS §2.1=T11、§2.9.1=R10，行名相同）**：`1D f32 K=2M` = 1D f32 源按 2M 个
随机下标取元素；`rowcopy A=16 f32 K=200k` = 2D f32 源（行宽 16）按 200k
个随机行下标取行；`noncontig self` = 源是非连续视图（stride 2）、
`noncontig idx` = 下标张量非连续；`col x[:,i]` = 整列选取；`range2048` =
下标值域 ≤2048（命中桶化）；`mask empty` = 全 False 掩码（零输出边界）；
`multi x[i,j]` = 两个全长下标（广播后 2D）。

**形状记号**：A（或 C）= 每行元素数（行宽）；K（或 E）= 下标元素数
（取多少行）；B = 被索引维之前的前导维度积；nnz = mask 非零数；值域 =
下标取值的范围宽度。B·K·A 描述一次调用的输出形状。

## 3. 代号冲突警示（读文档前必看）

- **"M1" 有两套含义**：`fallback-analysis.md` §1 的 **M1-M4 是机制代号**
  （M1=行放大+DRAM 延迟、M2=两遍开销、M3=串行段、M4=无 SVE 内核）；而
  上表的 **M1-M6 是负载代号**（权重块、spconv…）。两套互不相干，按上下文
  区分："受 M1 限制"多指机制，"M1 1t 8-10x"指负载。
