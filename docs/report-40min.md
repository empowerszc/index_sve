# 40 分钟深场：`aten::index` 的性能空间——从硬件窗口到三面墙

> 这份文档是 15 分钟短场的完整版：同一主线，补上硬件背景、测量方法论、负结果，
> 并把本轮 H6 实验当活案例复盘。也适合作为"从零读懂这份性能分析"的学习材料。
>
> **口径**：`比值 = aten ÷ 本仓`（>1 本仓更快）；**下界** = 同机、同形态、同线程数
> 下探针能跑出的最好合法写法；**实测地板** = 下界 + 该形态摊到的固定成本；
> **推断** = 有实测支撑的机理判断（文中标明用什么实验可以推翻它）。

## 0. 三条线，一张地图

1. **硬件线**（§1）：一颗核能同时等多少件事——本机 16-20 条 line，所以随机访问
   的下界是 `137ns ÷ 16 ≈ 8.6ns`。
2. **算子线**（§2-§3）：`aten::index` 实测只有 ~0.85 条在飞；本仓把它抬到 5.7 条。
3. **空间线**（§4-§5）：三把尺子、三面墙——"离上限远"与"能拿到"是两回事。

## 1. 硬件速成：只需要五个概念

### 1.1 延迟阶梯与"在飞窗口"

| 数据在哪 | 一次访问要多久 | 直观感受 |
|---|---|---|
| L1（32KB，紧挨着核） | **2.0ns** | 从桌上拿一张纸 |
| L2（768KB，同核） | **7.4-8.6ns** | 走到隔壁房间 |
| 本地 DRAM（16×64GB DDR5-5600，node5） | **128-148ns** | 下楼去仓库取 |

一次随机取数要等 137ns；但一颗核能**同时挂 16-20 条**未完成的 line（MSHR 表，
电路决定）。所以：

```
一次随机访问的成本 = 137ns ÷ 同时在飞条数 = 137 ÷ 16 ≈ 8.6ns
```

**例子**：仓库一趟往返要 137 分钟；但你派 16 个人同时去、每人各取一件，
平均每件只要 8.6 分钟。加线程是"多派人"，不是"跑得更快"。

两条独立证据互证这个 16-20：S 条独立链的吞吐曲线（`mlp`），以及
`带宽延迟积 = 7.2GB/s × 137ns ≈ 986B ≈ 15.4 条 line`。

### 1.2 缓存不是"一个大桶"：组、路、有效容量

L2 是 **1024 组 × 12 路 × 64B**：一个地址的组号指定位决定了它**只能进哪一个组**。
容量 768KB，但装到 **512KB** 时命中率就已经在掉（miss 0.1% → 576KB 时 6.0%）。

三个原因：泊松涨落让部分组先满（12 路刚好等于装满时每组的平均行数）；4KB 页
的"颜色"（物理页号低 4 位决定落进哪 64 个组，内核不保证均匀）；旁路流量抢 way。

**例子**：货架总格数够用，但每本书只能放进编号固定的那一格，每格只有 12 个
位置，而每个编号下的书数是随机的——**总格数够用 ≠ 每格都够用**。

### 1.3 一次 miss 走的路：MSHR 是"未完成订单本"

```
核发 load → 命中 L1（2ns）
  └ miss → 申请 MSHR 表项 → 问 L2
       ├ 命中 L2（8.6ns）→ 填 L1
       └ miss → 问内存控制器 → DRAM（约 130ns）→ 填 L2、L1 → 唤醒等待的指令
```

MSHR 有两个作用：让多条 miss **同时在飞**（窗口的物理基础）、**去重**（同一
条 line 只发一次请求）。表项用完，新的 miss 只能排队——**这是代码改不了的**；
所以一切"提高在飞条数"的软件手段，本质都是"别让 MSHR 空着"。

### 1.4 写为什么贵：RFO，以及"整行写"的特例

只改一条 line 的一部分时，硬件要先把整条读进来（read-for-ownership），改完
再写回。但 **A=16 恰好 64B = 一整条 line**，整行写不需要 RFO——perf 的
"L1 缺行/行 = 1.00"（只读源行）就是这条一致性的证据。

非临时存储（`stnt1d`，绕过缓存直接写内存）听起来很美，实测收益 **0**
（29.1 vs 29.1 @1t）——写侧 RFO 本来就不是这里的瓶颈。

### 1.5 DRAM 内部：bank / row / column——随机为什么慢

DRAM 按 bank（书架）→ row（一排书）→ column 组织。读同一排几乎免费
（row buffer 命中）；换一排要付 ACT+PRE（几十 ns）。顺序访问大概率命中同一排，
还有**硬件预取器**提前取后面的行；随机访问两样都吃不到。

| 访存模式 | 单核带宽 |
|---|---|
| 顺序扫（吃到 row buffer + 硬件预取） | 19.4 GB/s |
| 随机跳（每次付 ACT+PRE+往返） | 7.2 GB/s |

### 1.6 虚拟内存、TLB、大页：为什么"该优化"的项是负结果

TLB miss 后要沿多级页表 page walk（最坏 4 次内存访问），但它通常与数据 miss
**并行**发生，藏在 137ns 后面。实测开/关 2MB 大页（THP），延迟与 gather 都没有
差别（36t：11.76 vs 11.66ns）。**不是所有"看起来该优化"的项都值得动。**

### 1.7 乱序窗口与 IPC：核在算还是在等

- 4 宽发射、乱序执行，窗口由 ROB（几百条）决定；IPC 上限 4。
- 本机实测：aten **0.71**、本仓 8t **2.69**。IPC 低通常意味着**在等数据**。
- **SVE**（512-bit）一条 `ld1d` 搬 8 个 f64 = 64B，省的是**指令条数**，不是延迟
  ——所以"用向量指令就能快"这个直觉在这里不成立（§6 负结果）。

## 2. 算子解剖：aten 的三条硬事实

1. **逐元素走 `TensorIterator`**：循环体 = 读下标 → 越界检查 + 负索引归一 →
   取数 → 写。perf 确认热点在 `cpu_index_kernel` 的 `loop_2d_from_1d`。
2. **每行只算一次下标**：内层 A 个元素共用一次 offset——这是 aten 唯一的
   "批量化"，所以 A 变大只摊薄、不改善（A≥3 后每行成本基本是常数）。
3. **int32 下标先转 int64**：多一遍 K×12B 的读写（本仓不交这个税）。

实测位置（1t）：A=3/8/16 时每行 132-155ns；perf 给出 **322 拍/行、0.85 条在飞、
L1 缺行 1.07 条/行**。8t 时仍是 **318 拍**——多线程只是把同样的等待并行了 8 份。

## 3. 我们的方案与账

### 3.1 H1：软件预取（把地址计算从取数链上摘下来）

提前 D 行读下标、对行首发 `prfm pldl1keep`。A=16 1t：83.0 → 28.5ns/行（2.9x）。
边界同样重要：A=64 用 D=16（4KB/轮×8t）会把缺失队列挤爆，8t 反而崩到 115ns
——**预取是提示，占的是同一个 MSHR 池**。

### 3.2 两遍模型：省检查，多读一遍下标

先扫一遍下标压成紧凑行号（顺带检查/归一），第二遍块拷贝。1t 收益 1.1-6.8x；
但 8t 时每行 290 条指令、IPC 2.89——**原先判为"已贴 4 宽发射上限、对手变成指令数"
（§5.2 的"指令墙"）。H6 证伪了这个判断**：把指令加到 310 条（+7%），周期反而
100→98 拍、IPC 2.89→3.15。**8t 的对手不是发射端口，而是"每核仍只有 2.8 条 line
在飞"**。

### 3.3 桶化的两刀与一次回退（指令墙的现场证据）

生产最贵的三格都是"小值域桶化"（源 ≤2048，查表本来就是 L1 命中）：

1. **免 pass 1**（源 ≤2048 时表直接按 `[0,size)` 建）：内核 A/B
   SGI 1.31x / PPT 1.33x / Sonata 1.45x。
2. **免串行建表**（跨度 ≤64KB 直查源）：SGI 1.17-1.23x、PPT 1.15-1.22x，
   但 **Sonata 回退 13-17%**——分布完全分离。
   根因：直查循环每元素多一个乘法（`v*stride0`），而这条循环是**指令发射受限**的
   （IPC 2.5-2.6、每元素约 6 条指令）。`stride0==1` 特化只追回一半，最后靠
   `K/size ≤ 32` 的直查门绕开：SGI **1.28-1.30x**、PPT **1.27-1.28x**、
   Sonata **0.99-1.02x 回持平**。

这一轮是全文最好的"指令墙"教材：**每元素多一条乘法，就能吃掉十几 µs**。

> **注意这两种"指令多"不是一回事**：桶化查表那条循环是**真的**发射受限（每元素 6 条、
> IPC 2.5-2.6，加一条乘法就反亏 13-17%，改了就见效）；行拷贝那条不是（IPC 2.17-2.57，
> 加 13% 指令周期不动，§5.3）。**同一句"指令墙"不能套在两个循环上**——判据是
> "改动后周期动不动"，不是"IPC 离 4 有多远"。

### 3.4 为什么行拷贝能 6.3x、桶化只有 1.3-1.5x

三个族的地板完全不同：随机行是 `8.6ns/行`（DRAM 窗口）、桶化是
`0.7ns/元素`（L1 发射吞吐）、小 K 还要再叠"每次调用 5.8µs 的固定成本"。
**同一个比值（vs aten）在三族里根本不可比。**

## 4. 怎么量：这些数字为什么可信（方法论）

### 4.1 五条原则

1. **先量下界，再看实现**——没有下界的性能数字没有意义（24ns/行是好是坏？）。
2. **一次只改一个变量**——造出"除了被测项以外全都一样"的两个版本。
3. **交叉验证**——重要结论至少两条独立证据（S 曲线 + 带宽延迟积）。
4. **要相除的两个数必须同一轮取**——跨轮误差可到 20% 以上。
5. **原始表只有一个出处**——文档只写推导，冲突以 RESULTS 为准。

### 4.2 探针要分三种形状

| 形状 | 回答什么 | 探针 |
|---|---|---|
| 依赖链 | 一次往返多久（延迟） | `latency`、`mlp S=1` |
| 受控并发 | 能同时等几件（窗口） | `mlp S`（S 条独立链，在飞条数= S） |
| 真实内核形状 | 内核实际能拿多少 | `idxgather`、`rowgather` |

### 4.3 一次从"怀疑"到"定案"

问：1-4MB 那段"没那么快也没那么慢"的缓坡，是不是某一级缓存？
答：不是——4MB/8MB/16MB/64MB 的 L2 miss 率已饱和（0.85→1.00），但单次 miss
的代价还在涨（99→128ns）。**命中率饱和 + 延迟上涨 = 不是缓存层**（推断是
DRAM row buffer 命中率下降；TLB 已用大页实验排除）。

### 4.4 坑与守门

- `volatile` 下标把 store→load 转发放在依赖链上 → 小尺寸延迟普遍抬高一个
  常量（2.6ns 加在 2ns 上就是 130%）。
- 指针追逐的"工作集"是**置换的环长**，不是数组大小。
- 不绑 NUMA，同一程序能差 1.4-2.7 倍（130→181→255→354ns）；`--physcpubind` 与 `--membind` 必须成对。
- **机器会"变慢"**（OS 层不可见）：跑基准前先过金丝雀门
  （`benchmarks/canary.py`：empty512、aten K512、aten K2048，任一超基线 1.5x
  即作废）；A/B 两臂必须同态。

## 5. 还剩多少：三把尺子与三面墙

### 5.1 三把尺子

同一个格子（Sonata 桶化）用三种口径量，答案差 5 倍：

| 尺子 | 答案 | 回答什么 |
|---|---|---|
| 裸探针下界（0.7ns/元素） | 6.5x | "如果整数与固定成本都不要钱" |
| 实测地板（2.5ns/元素） | 1.8x | "同样的结构与固定成本下，把串行查表在飞化" |
| 端到端加权 | +0.23x | "用户能感知到多少" |

**三把尺子都合法，混用才不合法。**

### 5.2 三面墙，各管一格（对应 §4.5 的三个 <50% 格子）

| 墙 | 卡谁 | 能不能推 |
|---|---|---|
| **在飞条数墙**（原写"指令墙"） | 整行 A=16（每核只有 5.7 条 line 在飞，天花板 16-20） | **H6 已证伪"砍指令"这条路**：加 13% 指令、周期不动 |
| **固定成本墙** | 桶化三格（入口 5.8µs + fork-join ≈3µs） | 部分：H4/H7 改结构；入口不在本仓 |
| **覆盖率墙** | 1D 大值域（有 3.9x 空间、零生产覆盖） | 不在内核里；端到端 = 0 |

> **最值钱的一条心态**：`离上限远` ≠ `有空间`。SGI 对裸探针看是 41x，但固定
> 成本摊到每元素 13.5ns（比下界大 19 倍）——39x 是付不起的账；对实测地板只剩 1.9x。

### 5.3 活案例：本轮 H6（想摊薄"记账"，结果被证伪）

- **假设**：A=16 每行 105 条指令，其中约 26 条是预取记账（D=0 时 80 条），
  §5.1 把这 8ns 差距里的约 6ns 记在记账上——所以"砍记账就能省时间"。
- **改法**：整段增量 `(r,k)` 走（免掉每行 `p/K`、`p%K` 的运行时整除）+ 每 4 行凑
  一批预取、背靠背发射；运行时旋钮 `HPC_PF_BATCH`（0 = 逐行旧写法），**同一个 .so、
  同一个进程**做 A/B，消掉 .so 布局差这个变量。
- **结果（RESULTS §2.21.4，A=16/K=131072，三臂轮次）**：
  - 墙钟 `vs 旧写法` 六格 = **1.02 / 0.98 / 0.99 / 0.97 / 1.01 / 0.94**——无一为正。
  - PMU：指令 **104.4 → 117.6（+13%）**，周期 **48 → 46**，IPC **2.17 → 2.57**；
    8t 同样（290.6 → 309.7、100 → 98、2.89 → 3.15）。
- **判读**：记账确实砍掉了，但省下的那次 `sdiv` 抵不过新增的进位分支与第二份下标
  算术；**而"加了 13% 指令、周期不动"才是关键证据——这条循环不是发射受限**，
  补进来的指令被访存等待吸收了。1t 的 48 拍/行 = 等效在飞 5.7 条，天花板由
  **在飞条数**定，不由指令数定。
- **处理**：默认关闭（`HPC_PF_BATCH=0`），批量路径留作复现；连带作废"8t 已贴 4 宽
  发射上限、砍指令就是砍时间"的推断。**剩下的 1.8-2.1x 目前没有已知下手处**
  （D 扫描已到最佳点）——这是明确的欠账，不是"再等等"。

### 5.4 端到端的反解

热点三格只占各模型 23-40% 的调用；长尾 60-77% 现在约 0.9x。设热点占全程一半，
由 `全程 = 0.5×热点 + 0.5×长尾` 反解：热点从 1.3 到 1.9，全程也只有 ~1.25x。
**"再优化 1.5 倍"和"用户感知再快 1.5 倍"差着覆盖率。**

## 6. 负结果清单（为什么这些都不做）

| 看起来该做的事 | 实测结论 |
|---|---|
| 大页（THP） | 收益 0（page walk 藏在 137ns 后面） |
| SVE gather | 不比标量展开差，但一批只有 8 lane；4B gather 在 L1 常驻源上**输给**标量查表（64B 行放大） |
| 非临时存储（`stnt1d`） | 收益 0（写侧 RFO 不是瓶颈） |
| 排序/通用桶化 | 随机变顺序能到 168GB/s，但 `O(K log K)` 的代价远超访问本身 |
| 加线程 | 每核的在飞条数不变，每行该等的拍数一拍不少（1t 322 拍 → 8t 318 拍） |
| 按线程数收缩预取距离 | 实测无收益；真正的变量是行字节 |
| 把 32KB 工作集当 L1 常驻 | 组冲突 + 下标流冲刷，实测反而慢 |
| 用 145GB/s 的拷贝上限给小副本建模 | 8MB `clone` 在 8/16t 只有 53/72GB/s，会高估收益 |
| **砍行拷贝的预取记账指令（H6）** | 记账砍了，指令反 **+13%**、周期 48→46 **不动**、墙钟 0.94-1.02x——**这笔账是免费的**，该循环不是发射受限（RESULTS §2.21.4） |

## 7. 欠账与下一刀

按端到端 Δ 排序（不是单形态倍数）：

1. **H4/H7 固定成本**（桶化，改结构）：三格同时做完，热点加权到
   SGI 1.43x / PPT 1.39x / Sonata 1.46x 的基础上还能再动；其中入口 5.8µs
   不在本仓代码里。**这是现在唯一"有明确下手处"的第一优先级。**
2. **长尾覆盖**（60-77% 的调用约 0.9x）：把它做到 1.2x 的收益，比把 Sonata
   从 1.8x 做到 3.5x 更大——**这是覆盖率墙，不是内核问题**。
3. **A=16 剩余 1.8-2.1x**：H6 已证伪"砍记账"（本轮），要提只能提高每核在飞
   条数，而 D 扫描已到最佳点——**目前没有已知做法**，属"没有下手的欠账"，
   不要排进计划。
4. H3 宽行高线程（指令墙假设待验证，H6 已证明同款判断在 A=16 上不成立）、
   H5 减遍数、H8 路由悬崖（判据顺序，不是内核）。

## 8. 速查表

| 换算 | 式子 | 例子 |
|---|---|---|
| 拍 ↔ ns | `ns = 拍 ÷ 2.0GHz` | 274 拍 = 137ns |
| 周期 → 在飞条数 | `在飞 = 274 ÷ 每行周期` | 322 拍 → 0.85 条；49 拍 → 5.6 条 |
| line ↔ 带宽 | `GB/s = 64B ÷ (ns/line)` | 8.9ns/line → 7.2GB/s |
| ns/行 ↔ 带宽 | `GB/s = 行字节 ÷ (ns/行)` | 64B ÷ 24ns = 2.7GB/s |
| 剩余 / 已兑现 | `现状 ÷ 下界`；`现状比值 ÷ 可达上限` | 24.0 ÷ 13.1 = 1.8x；6.33 ÷ 13.3 = 48% |
